# GitHub Repository Setup

![GitHub Repository Setup textbook visual](/course-art/deep-exemplars/cat100-supplement/06-03-github-repository-setup.png)

## Why This Section Matters

A GitHub repository (repo) is a folder whose entire history is tracked. Setting one up correctly is what turns the loose files on your laptop into a published, recoverable, shareable project. Two setup decisions in particular have consequences that are hard to undo later: the exact name of the repository, which determines your live URL, and what you allow into version history, because anything committed once lives in the history even after you delete it.

This section walks the real commands (`git init`, `git add`, `git commit`, `git remote`, `git push`) and the two guardrails beginners most often skip: naming a user site so it serves from the clean root URL, and using a `.gitignore` so secrets never enter history in the first place. Getting these right now prevents the most painful failures in publishing (06.04) and maintenance (06.07).

## Opening Case

A student wants her portfolio at the clean address `mlopez.github.io`. She creates a repo called `portfolio`, pushes everything, and enables Pages. Her site appears, but at `mlopez.github.io/portfolio/`, not the root she wanted, and worse, every absolute stylesheet path she wrote now points to the wrong place. Separately, in her rush she committed a `token.txt` file holding an API key. She deletes the file in her next commit and assumes it is gone. It is not: the key still sits in the repo's history, visible to anyone who looks, which means it must be rotated, not just deleted.

Both problems trace to a single setup moment. The repository name fixed the URL shape, and the first commit fixed what entered history. This section teaches you to make those two decisions deliberately.

## Core Concept

Repository setup rests on a few mechanics that beginners can learn in one sitting.

**Repo name determines URL.** GitHub Pages distinguishes a user site from a project site by the repo name. A repo named exactly `username.github.io` publishes at the root, `https://username.github.io/`. Any other name publishes as a project site at a subpath, `https://username.github.io/reponame/`. The subpath is not wrong, but it changes how your asset paths must be written (the cause of the broken-CSS case above), so choose the name with the URL you want in mind.

**The commit pipeline.** Git tracks changes in three stages. The working directory is your files as they sit. `git add` moves chosen files to the staging area, a holding pen for the next snapshot. `git commit` records that snapshot permanently with a message. `git push` uploads commits to GitHub. Understanding the stages explains why `git add` then `git commit` are two separate steps: staging lets you choose precisely what goes into each snapshot.

**History is permanent; `.gitignore` is prevention.** A commit is a permanent record. Deleting a file later removes it from the current snapshot but not from past commits. The correct defense is to never commit secrets: a `.gitignore` file lists patterns (like `token.txt` or `.DS_Store`) that Git will refuse to stage. Prevention beats cleanup because cleaning history is hard and, for a leaked credential, insufficient (you still have to rotate the key).

These mechanics meet ISTE digital citizenship directly: committing a key is a real security exposure, and knowing that history is permanent is the difference between a recoverable mistake and a published one. NACE career readiness applies too, because version control and not leaking credentials are baseline expectations in any technical workplace.

## Worked Example

Maria wants her site live at https://mlopez.github.io. Follow the repository setup command by command.

**Step 1. Name the repository to match the target URL.** A user site must use the exact repo name username.github.io:

```text
Repository name: mlopez.github.io   (correct)
Repository name: portfolio          (wrong: would publish at /portfolio)
```

**Step 2. Initialize and connect the local folder.**

```bash
cd my-portfolio
git init
git add index.html about.html assets/
git commit -m "Initial portfolio"
git remote add origin https://github.com/mlopez/mlopez.github.io.git
git push -u origin main
```

**Step 3. Protect secrets before the first push.** Maria notices a file token.txt in the folder. She adds a .gitignore:

```text
# .gitignore
token.txt
.DS_Store
```

If the token had already been committed, removing it would not be enough; she would also rotate the key because it now lives in history.

**Step 4. Confirm the entry file.** The root URL serves index.html in lowercase. A file named Index.HTML would return a 404, so she renames it.

The repository is now named correctly, the secret is ignored before it can leak, and the lowercase index.html guarantees the root URL resolves. Each setup choice is traceable to a specific publishing rule.

Order the setup steps so the irreversible decisions happen before the first push. The repo name and what enters history are both hard to undo, so they must be settled first.

## Decision Rule

Before your first push, run three checks in this order, because each one is hard to reverse afterward:

1. **Name check:** Does the repo name produce the URL you want? Use `username.github.io` for a root user site; accept a subpath only if you have written your asset paths to suit it.
2. **Secret check:** Is there any credential, key, token, or private path among the files? If so, add it to `.gitignore` before you stage anything. If a secret was already committed, plan to rotate it, not just delete it.
3. **Entry-file check:** Is there a lowercase `index.html` at the level GitHub will serve? The root URL looks for `index.html`; a file named `Index.HTML` returns a 404 on case-sensitive servers.

A failure here is not cosmetic. The wrong name means rebuilding URLs; a leaked secret means a real exposure; a missing index means a blank live site.

## Common Misreadings

The most damaging misreading is "I deleted the file, so the secret is gone." Git history keeps every committed version. Deleting a file in a new commit hides it from the current snapshot but leaves it readable in history, which is why a committed key must be rotated. Treat the first commit as a one-way door for anything sensitive.

A second misreading is assuming any repo name works the same. The exact string `username.github.io` is special; everything else becomes a subpath site with different path requirements.

## Textbook Walkthrough

Apply the rule to a clean setup. A student named Maria wants `mlopez.github.io`. She names the repo exactly that, satisfying the name check and the root-URL goal in one decision. Before staging, she scans the folder and spots `token.txt` from an earlier experiment; she writes a `.gitignore` containing `token.txt` and `.DS_Store`, satisfying the secret check before anything sensitive can enter history. She confirms the entry file is lowercase `index.html`, satisfying the entry-file check.

Only then does she run the commit pipeline: `git add index.html about.html assets/`, `git commit -m "Initial portfolio"`, connect the remote, and `git push`. Because she checked the three things first, the live site appears at the clean root URL, the token never reaches GitHub, and the root request resolves to her home page. The order of operations is the lesson: the checks come before the push, not after.

## What Strong Reading Looks Like

A strong reader can predict the consequence of each setup choice before running it. As you read the worked example, pause at the repo-name line and ask what URL it produces; pause at the `.gitignore` and ask what would have happened without it. If you can state the downstream effect of each command, you understand setup as a chain of consequences rather than a recipe to copy.

A strong reader of repository setup can answer four questions:

1. Given a repo name, what will the live URL be, root or subpath?
2. What is the difference between staging and committing, and why are they separate?
3. If a secret was committed three commits ago, what does it take to truly remove the risk?
4. What single file prevents secrets from entering history, and how does it work?

## Stronger Artifact Standard

Your repository is strong when a reviewer cloning it finds no secrets in any commit, a sensible `.gitignore`, a clear commit message, and a lowercase `index.html` that the root URL serves. The history should read as deliberate: each commit groups related changes rather than dumping everything at once.

A strong submission documents one prevention you made on purpose: "I added token.txt to .gitignore before the first commit, because once a key is in history, deleting the file is not enough and I would have had to rotate it."

## Transfer Case

Take the same setup skills to a different project: a small Python script you want to share rather than a website. The URL concern disappears (you may not publish Pages at all), but the history and secrets concerns are identical. You would still write a `.gitignore`, this time excluding a `config.py` with database passwords and a `__pycache__` folder, and you would still treat the first commit as permanent. The specific patterns in `.gitignore` change with the project type; the principle that history is permanent and secrets must be kept out of it never changes. Carrying that principle to a non-web project is the test that you learned version-control hygiene, not just one portfolio recipe.
