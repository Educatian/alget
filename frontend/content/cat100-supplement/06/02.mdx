# Starter HTML and CSS

![Starter HTML and CSS textbook visual](/course-art/deep-exemplars/cat100-supplement/06-02-starter-html-and-css.png)

## Why This Section Matters

HTML and CSS are two different languages with two different jobs, and most beginner errors come from blurring them. HTML (HyperText Markup Language) describes structure and meaning: this is a heading, this is a paragraph, this is an image. CSS (Cascading Style Sheets) describes appearance: this heading is dark blue, the body is centered at 640 pixels wide. Mixing the jobs (using a heading tag just to make text big, for example) produces pages that look acceptable but read poorly to screen readers and search engines.

This section teaches you to write a minimal, valid HTML document and one stylesheet that controls its look, with two specific skills that beginners most often get wrong: writing accessible image markup and predicting which CSS rule wins when two rules conflict. These are the foundation for everything you publish in the rest of the module.

## Opening Case

A student writes his first About page, opens it in a browser, and it looks fine: a big title, a photo, a short bio. He submits it. The reviewer runs a screen reader and hears: "About Me, heading. Image. First-year data student." The photo announced only the word "image" because the markup had no alt text, so a blind visitor learns nothing about it. Later the student adds a second CSS rule for the heading color and is surprised when the heading turns red instead of the navy he wanted; he did not know the later rule overrode the earlier one.

Both problems are invisible when you only judge a page by how it looks on your own screen. This section makes them visible by teaching you to read markup and the cascade, not just preview the result.

## Core Concept

Three mechanics carry most of the weight in starter HTML and CSS.

**The minimal valid document.** Every HTML page needs a small, fixed skeleton: a `<!DOCTYPE html>` line, an `<html>` element with a `lang` attribute, a `<head>` for metadata the visitor does not see (the `<title>`, the character set, the stylesheet link), and a `<body>` for the content they do see. The `<title>` lives in the head and controls the browser tab and the bookmark name; it is not visible on the page itself. Getting this skeleton right is what makes a file a web page rather than a text file.

**Accessible images.** The `alt` attribute on an `<img>` is the text a screen reader announces and the text a browser shows when an image fails to load. `alt` should describe the image's content or function, not repeat the word "image." A decorative flourish can use empty `alt=""` so screen readers skip it; a meaningful photo needs a real description. WCAG accessibility guidelines treat missing alt text on informative images as a failure, which is why this is not optional polish.

**The cascade and specificity.** "Cascading" in CSS means rules can conflict, and the browser resolves conflicts with predictable rules. When two rules target the same element with the same specificity, the one written later wins. When specificity differs, the more specific selector wins regardless of order (an id beats a class, a class beats a bare tag). Understanding this is what separates "I changed a color and the whole page broke" from "I know exactly which rule is in charge."

These mechanics connect to the course anchors. ISTE digital citizenship makes the alt-text requirement an equity issue: a page without it excludes blind visitors. NACE career readiness reframes clean, valid markup as a professional habit; sloppy HTML is the kind of thing a technical reviewer notices immediately.

## Worked Example

You are building the starter page for your About section. Follow the markup from a broken first pass to a working, accessible version.

**Step 1. Lay out the minimum valid document.**

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Maria Lopez | Portfolio</title>
    <link rel="stylesheet" href="assets/style.css">
  </head>
  <body>
    <h1>About Me</h1>
    <img src="headshot.jpg">
    <p>First-year data student at CAT 100.</p>
  </body>
</html>
```

**Step 2. Find the two problems.** The browser tab reads correctly because <title> sits in <head>, but the image fails accessibility: <img src="headshot.jpg"> has no alt text, so a screen reader announces only "image".

**Step 3. Fix the image and add one CSS rule.**

```html
<img src="headshot.jpg" alt="Maria Lopez, headshot">
```

```css
/* assets/style.css */
body { font-family: system-ui, sans-serif; max-width: 640px; margin: 2rem auto; }
h1 { color: #1f3a5f; }
```

**Step 4. Confirm the cascade.** If a later rule said h1 { color: #b00; } it would win over #1f3a5f at equal specificity, so keep only the rule you intend.

The page now sets the correct tab title, gives the image a real alt description, and applies a stylesheet whose single h1 rule is unambiguous. Every change is visible in the markup, not just in how the page looks.

Predict the cascade before you reveal it. Two rules target the same heading, so the resolution is deterministic, not random.

## Decision Rule

Before you call an HTML page finished, read the markup, not the preview, against three checks:

1. **Structure check:** Does every visible piece of content sit in a tag that matches its meaning (heading for headings, paragraph for prose, list for lists)? Never reach for a heading tag just to make text bigger; that is what CSS font-size is for.
2. **Accessibility check:** Does every informative `<img>` have descriptive `alt` text? Read each alt aloud and ask whether a visitor who cannot see the image learns what they need to.
3. **Cascade check:** For any element you styled, can you name which rule is winning and why? If two rules target it, the later one wins at equal specificity; if you did not intend that, delete or rename one.

If you cannot pass all three by reading the source, the page may look done but is not done.

Order the parts of a minimal valid HTML document from the outside in. Some pieces live in the head (unseen metadata) and some in the body (visible content), and the skeleton only validates when they nest in the right sequence.

## Common Misreadings

A frequent misreading is believing that "it looks right in my browser" means the markup is correct. Browsers are forgiving: they will render a page with a missing closing tag or no alt text without complaint. The errors surface only for screen-reader users, on slow connections, or when you add the next rule and the cascade behaves unexpectedly.

A second misreading is treating CSS specificity as random. It is fully deterministic. When a color refuses to change, the cause is almost always a more specific selector elsewhere winning the conflict, not a mysterious bug.

## Textbook Walkthrough

Apply the checks to a real fix. A student's page shows a headshot, but the alt attribute reads `alt="image1"`, the filename from her phone. The accessibility check fails: "image1" tells a screen-reader user nothing. She rewrites it as `alt="Maria Lopez, headshot"`, which names the person and the type of image. That is a content decision, not a style decision, so it belongs in the HTML.

Next she wants the page title navy. She adds `h1 { color: #1f3a5f; }`. Later, copying a snippet from a tutorial, she pastes `h1 { color: #b00; }` at the bottom of the same stylesheet. The heading turns red. Running the cascade check, she sees two rules of equal specificity targeting `h1`; the later red rule wins. She does not fight it with `!important` (a blunt tool that creates worse conflicts later); she simply deletes the stray rule so only the intended navy remains. The fix is to make the source say exactly one thing about the heading color.

## What Strong Reading Looks Like

A strong reader can predict what a browser will do before opening it. As you study the worked example, cover the result and ask: given this markup, what will a screen reader announce for the image? Given these two CSS rules, what color will the heading be? If your predictions match the browser, you are reading the code rather than guessing from the preview.

A strong reader of starter HTML and CSS can answer four questions about any page:

1. Which content belongs in the head (unseen metadata) and which in the body (visible content)?
2. Does each image's alt text describe its content or function, or does it just repeat the word image?
3. When two style rules conflict, which one wins, and is that the one you intended?
4. If you removed the stylesheet entirely, would the bare HTML still be readable and correctly structured?

## Stronger Artifact Standard

Your page is strong when the markup alone (with no CSS) is still a clean, ordered document: one main heading, real paragraphs, images with honest alt text, links that say where they go. CSS should improve a page that is already correct, never rescue a page that is structurally wrong. A reviewer who reads your source should be able to understand the page's meaning without seeing it rendered.

A strong submission notes one cascade decision you made on purpose: "I kept the navy rule and deleted the red one I had pasted, because two h1 color rules conflicted and only the intended one should remain."

## Transfer Case

Take the same skills to a different document type: a single landing page for a campus club instead of a personal About page. The HTML skeleton is identical (doctype, lang, head, body), and the cascade rules are unchanged. What shifts is the content and therefore the markup choices: the club page may need a list of meeting times (a real `<ul>`, not paragraphs with dashes) and a logo whose alt text states the club name. The principle that structure should match meaning and that conflicts resolve by specificity and order does not change; only the specific tags you reach for do. Being able to carry the rules to new content is the sign you learned the language and not just one page.
