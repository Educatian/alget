# Module 6 Website Studio

![Module 6 Website Studio textbook visual](/course-art/deep-exemplars/cat100-supplement/06-08-module-6-website-studio.png)

## Why This Section Matters

This is the capstone where the seven prior sections become one published site. Until now you practiced each skill in isolation: architecture, markup, repo setup, publishing, debugging, evidence, maintenance. The studio asks you to integrate them and prove the result works end to end. Integration is its own skill, because a site can pass each check individually and still fail as a whole, for example a perfectly accessible page that 404s on the live URL, or a clean file tree with a secret quietly sitting in history.

The work product here is a single, deliberate verification: assemble the publishable file tree, run one combined accessibility, privacy, and publishing checklist, attach an honest AI-use note, and confirm everything on the live URL the way a visitor would. The deliverable is not a mockup or a description; it is a working, inspectable, published site.

## Opening Case

A student believes she is done. Her About page is accessible, her repo is clean, her resume bullet is sharp, her CSS is tidy. She submits a folder of files. But she never enabled Pages on the right branch, so the site is not actually live; she never opened the published URL on a phone, so she did not notice that her project links 404 from the subpath (her repo is a project site served at /reponame/, where leading-slash absolute paths break); and although she deleted a stray token file, it still sits in commit history. Each individual skill from the module is present, yet the submission fails as a published artifact because nothing tied the pieces together and tested them as a system.

The studio exists to prevent exactly this. Passing every section separately is necessary but not sufficient; the capstone is about the integration and the single end-to-end proof.

## Core Concept

Integration in this studio means three things working together.

**One file tree that satisfies every prior section at once.** The tree must reflect the architecture decision (only pages that serve the purpose), the markup decision (valid HTML with alt text), the repo decision (a `.gitignore`, no secrets), and the publishing decision (lowercase `index.html`, relative asset paths). The tree is the place where all the module's choices become simultaneously visible.

**One combined checklist across three dimensions.** Rather than three separate passes, the studio runs accessibility, privacy, and publishing as a single review where each check names its evidence in the artifact. Accessibility: every informative image has descriptive alt, navigation uses real links. Privacy: no keys, address, or phone committed, with `.gitignore` in place. Publishing: Pages source set, lowercase entry file, relative paths. One distinction keeps the publishing row honest: a user site such as mlopez.github.io serves from the domain root (/), where an absolute path like /assets/style.css happens to work, while a project site serves from a /reponame/ subpath, where leading-slash absolute paths 404. Relative paths resolve correctly in both cases, which is why the checklist asks for them. The discipline is that each row points to something concrete in the site, not to a claim that it is fine.

**One end-to-end verification on the live URL.** The decisive test is a single visit to the published address in a private window on a phone. That one action exercises accessibility (the screen reader announces alt text), privacy (no secrets surface), and publishing (pages load, links resolve, layout holds) at the same time. A live test that passes is worth more than any number of local previews, because it is the environment your audience actually uses.

All three course anchors converge here. [NACE career readiness](https://www.naceweb.org/career-readiness/competencies/career-readiness-defined) treats shipping a working public artifact as the real outcome. [ISTE digital citizenship](https://iste.org/standards/students) covers the privacy and accessibility obligations of anything you publish. data-ink and visual evidence applies to your proof: the strongest evidence is the live site itself, demonstrated, not asserted.

## Worked Example

This studio integrates the whole module. Maria assembles the final file tree, runs the three-part checklist, and verifies on the live URL.

**Step 1. Confirm the publishable file tree.**

```text
mlopez.github.io/
  index.html        (Home, links to all pages)
  about.html        (bio + headshot)
  projects/
    index.html      (project cards)
    dashboard.html
  resume.pdf
  assets/
    style.css
  .gitignore        (token.txt, .DS_Store)
```

**Step 2. Run the accessibility, privacy, publishing checklist.**

| Check | Evidence in the artifact |
| --- | --- |
| Accessibility | Every `<img>` has descriptive alt; nav uses real `<a>` links |
| Privacy | No API keys, address, or phone committed; .gitignore in place |
| Publishing | Settings, Pages source set; lowercase index.html; relative asset paths |

**Step 3. Add the AI-use note.** "AI assisted with drafting starter HTML, debugging one unclosed tag, and rewording one resume bullet. I verified every change in the browser and own all factual claims." Naming the tool makes the note stronger: an LLM coding assistant such as GitHub Copilot, Claude, ChatGPT, or Cursor, with the version if you know it. Follow your course's GenAI disclosure policy in Blackboard for the exact format.

**Step 4. Verify end to end like a visitor.** Open https://mlopez.github.io in a private window on a phone: pages load, the headshot announces its alt text, all nav and project links resolve, and no secrets appear in the repo.

The submission is now a real published site, not a mockup. One end-to-end test on the live URL exercises accessibility, privacy, and publishing together, and the AI-use note keeps the work honest and auditable.

Order the capstone integration steps so the single live-URL test comes last and subsumes the rest. Assemble and check the pieces first, then prove the whole on the real address.

## Decision Rule

Before you call the studio complete, the submission must pass one integrated test, not three separate ones:

1. **Tree check:** Does the file tree simultaneously satisfy architecture, markup, repo hygiene, and publishing requirements? Any one missing breaks the whole.
2. **Live check:** Open the published URL in a private window on a phone. Do pages load, do all links resolve, does alt text announce, does the layout hold?
3. **History check:** Is the repo clean across its whole history, not just the latest snapshot? A secret in an old commit still fails privacy.

If the live check passes on the real URL, you have a published site. If you only verified locally, you have not finished the studio.

## Common Misreadings

The central misreading at this stage is "I passed every section, so the site is done." Sections passed in isolation can still combine into a broken whole: accessible markup served from a path that 404s, or a tidy current snapshot hiding a leaked key in history. Integration must be tested as integration.

A second misreading is submitting files instead of a live site. A folder of correct files is not a published artifact. The capstone is specifically about the deployed, verifiable result, which is why the live-URL test is non-negotiable.

## Textbook Walkthrough

Apply the rule to a clean capstone. Maria first confirms the publishable file tree: `index.html` at the root, an `about.html` with headshot and alt text, a `projects/` folder, `resume.pdf`, an `assets/style.css`, and a `.gitignore` excluding `token.txt` and `.DS_Store`. The tree alone shows architecture (only purposeful pages), markup (real pages, not placeholders), repo hygiene (the ignore file), and publishing readiness (lowercase index).

She then runs the combined checklist, naming evidence for each row: accessibility is satisfied because every `<img>` has descriptive alt and the nav uses real `<a>` links; privacy is satisfied because no keys, address, or phone are committed and `.gitignore` is in place; publishing is satisfied because the Pages source is set, the entry file is lowercase, and asset paths are relative (they work on her root-served user site and would keep working if the pages ever moved into a project repo served at /reponame/). She attaches the AI-use note covering the starter HTML draft, the one debugging fix, and the reworded resume bullet, naming the assistant she used and stating she verified every change and owns all factual claims. Finally she runs the single end-to-end test: opening the live URL in a private window on her phone, where the pages load, the headshot announces its alt text, every link resolves, and no secret appears. One visit exercised all three dimensions at once, which is the point of the studio.

## What Strong Reading Looks Like

A strong reader treats the live visit as the experiment that subsumes the others. As you study the worked example, for each checklist row ask what a visitor on the live URL would actually experience if that row failed (an unannounced image, a leaked key, a 404). If you can map every check to a concrete failure a real visitor would hit, you understand why the integrated live test is the decisive one.

A strong reader of the website studio can answer four questions:

1. How does a single file tree make every prior section's decision visible at once?
2. Why can a site pass each check separately and still fail as a whole?
3. What does one live-URL visit on a phone verify that a local preview cannot?
4. Why is a clean latest snapshot not the same as a clean history?

## Stronger Artifact Standard

Your capstone is strong when a reviewer can open your live URL, experience an accessible, working, secret-free site, and trace each quality to concrete evidence in the repo. The AI-use note should make your tool use transparent, and the verification should rest on the live site rather than on a claim that it worked locally.

A strong submission names the integration failure you caught: "Each section passed on its own, but my projects repo is a project site served at /reponame/, and its links 404ed on the live subpath until I switched to relative paths; I found it only by opening the published URL on my phone, not in the editor."

## Transfer Case

Carry the integration-and-verify discipline to any capstone deliverable, for example a data report that combines a cleaned spreadsheet, a chart, and a written summary. The components can each be correct while the whole fails: a chart built from an older version of the data, or a summary citing a number the spreadsheet no longer contains. The remedy is the same as in this studio: assemble the pieces into one artifact, run a single combined check that ties each claim to its source, and verify the finished thing in the form the audience will actually receive. Recognizing that "test the integrated result in its real environment" is the portable lesson, not "click the GitHub Pages button," is what shows you finished the module rather than just its last task.
