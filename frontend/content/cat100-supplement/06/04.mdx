# Publishing With GitHub Pages

![Publishing With GitHub Pages textbook visual](/course-art/deep-exemplars/cat100-supplement/06-04-publishing-with-github-pages.png)

## Why This Section Matters

Publishing is the moment your files stop being a local experiment and become a live URL anyone can open. GitHub Pages does this by taking a branch of your repo, running a build, and serving the result over HTTPS for free. The catch that trips up nearly every first-time publisher is that the live site is not the same environment as your editor preview: paths resolve differently, the build takes a minute, and a project site lives under a subpath. A page that works perfectly on your laptop can appear unstyled or broken the instant it is live.

This section teaches you to enable Pages, understand why local and live differ, and verify on the real URL the way a visitor would. The single most valuable habit here is testing the published address, not the preview, because that is where the truth lives.

## Opening Case

A student pushes his finished portfolio, enables Pages, and opens the live link. The text is all there but completely unstyled: black on white, default fonts, no layout. He is sure the stylesheet works because it looks perfect in his editor's preview. He spends an hour rewriting CSS that was never broken. The real cause is one character in the link tag: his stylesheet path starts with a slash, `/style.css`, which means "from the domain root." On a project site served from `username.github.io/portfolio/`, the domain root has no `style.css`, so the browser silently gets a 404 and renders the page with no styles.

The bug was invisible in the editor preview, which serves from the folder root, and visible only on the live subpath. This section is about closing that gap between what you see locally and what visitors actually get.

## Core Concept

Three facts about GitHub Pages explain almost every publishing surprise.

**Pages is a build-and-serve pipeline, not a live file mirror.** When you push, GitHub queues a build and then serves the output. There is a delay (often under a minute, sometimes longer), and a recent change is not live until the build finishes. "I pushed and nothing changed" is usually "the build has not completed and your browser is showing a cached copy."

**Absolute versus relative paths.** A path beginning with `/` is absolute: it starts from the domain root, `username.github.io/`. A path with no leading slash is relative: it starts from the current page's folder. On a user site served from the root, absolute paths happen to work. On a project site served from `/portfolio/`, an absolute `/style.css` points outside your project and fails, while a relative `assets/style.css` resolves correctly. This single distinction causes the unstyled-page case.

**The live URL is the source of truth.** Your editor preview, a local server, and the published site are three different environments. Caching, build timing, and the subpath all mean the only reliable test is opening the actual published address, ideally in a private window (to dodge cache) and on a phone (to catch layout problems).

These facts connect to the course anchors. NACE career readiness frames publishing as shipping: professionals are judged on what is live, not on what works locally. data-ink and visual evidence applies to verification itself; the strongest evidence that your fix worked is a screenshot or check of the live URL, not a claim that it looked fine in the editor.

## Worked Example

Maria pushed her files but the live page shows unstyled text. Follow the publishing checklist that finds and fixes the break.

**Step 1. Turn Pages on.** In the repo: Settings, Pages, Source, Deploy from a branch, Branch: main, Folder: / (root), Save. GitHub reports: Your site is live at https://mlopez.github.io/portfolio/.

**Step 2. Reproduce the bug on the live URL, not the editor.** Locally the page is styled. On the live project URL the CSS is missing. The difference is the subpath /portfolio/.

**Step 3. Inspect the link tag.**

```html
<!-- before: absolute path points at the domain root, 404s on a project site -->
<link rel="stylesheet" href="/style.css">

<!-- after: relative path resolves under /portfolio/ -->
<link rel="stylesheet" href="assets/style.css">
```

**Step 4. Verify like a visitor.** Commit, wait for the Pages build to finish, then hard-refresh and open the live URL in a private window on a phone. Styles now load.

The fix was one character of path logic, not a broken deploy. The lesson is that a project site serves from a subpath, so absolute paths that work locally break online. Verifying on the live URL, not the editor preview, is what exposed it.

Order the publishing-and-verify steps so you diagnose before you rewrite. Enabling Pages and waiting for the build come first, and confirming on the real URL comes last.

## Decision Rule

When the live page looks wrong, do not start editing. Diagnose with three checks in order:

1. **Build check:** Did the Pages build finish, and are you looking at a fresh copy? Wait for the build, then hard-refresh or use a private window so caching is not lying to you.
2. **Path check:** Are your asset links relative (`assets/style.css`) or absolute (`/style.css`)? On a project subpath, absolute paths fail. Match the path style to where the site is actually served.
3. **Environment check:** Did you verify on the live URL or only in the editor preview? If only the preview, you have not actually tested publishing.

Most "broken deploy" panics are really a caching delay or one absolute path. Diagnose before you rewrite.

## Common Misreadings

The biggest misreading is trusting the editor preview as proof the published site works. The preview and the live site are different environments; a path or build issue exists only on the live URL. Treating the preview as ground truth is how students rewrite working CSS for an hour.

A second misreading is assuming a push is instant. Pages builds take time, and browsers cache aggressively, so "nothing changed" frequently means "wait and hard-refresh," not "my code is wrong."

## Textbook Walkthrough

Apply the rule to the unstyled-page case. The student first runs the build check: the Pages dashboard shows the latest build succeeded, and a private-window reload still shows no styles, so caching and build timing are ruled out. He runs the path check and finds `<link rel="stylesheet" href="/style.css">`. Because his site is a project site at `/portfolio/`, that absolute path resolves to `username.github.io/style.css`, which does not exist. He changes it to the relative `assets/style.css`, which resolves under `/portfolio/`. He runs the environment check by opening the live URL, not the preview, in a private window on his phone; the styles now load.

The fix was one path, found by diagnosis rather than guesswork. The walkthrough shows the value of the ordered checks: ruling out build and cache first meant he did not waste time, and the path check pointed straight at the real cause.

## What Strong Reading Looks Like

A strong reader treats the live URL as the experiment and the editor as a hypothesis. As you study the worked example, ask at each step which environment is being tested and what a difference between them would imply. If the page works locally but not live, your attention should go immediately to paths, build state, and cache, in that order, rather than to the CSS itself.

A strong reader of GitHub Pages publishing can answer four questions:

1. Why can a page look perfect in the editor but unstyled on the live URL?
2. When does an absolute path work and when does it break?
3. What two browser habits (private window, hard refresh) rule out caching as the cause?
4. What is the single most reliable way to prove a fix actually shipped?

## Stronger Artifact Standard

Your published site is strong when you can point to evidence from the live URL, not the preview, that it works for a visitor: the styled page loading in a private window, links resolving, layout holding on a phone. Verification on the real address is the artifact, not just the code change.

A strong submission names the environment difference you resolved: "Locally my CSS loaded; live it 404ed because I used an absolute path on a project subpath. I switched to a relative path and confirmed the fix on the live URL in a private window."

## Transfer Case

Move the same publishing logic to a different host, say a Netlify or Cloudflare Pages deploy of the same site. The exact menu to enable the site differs, but the deep facts carry over: there is a build step with a delay, paths must match where the site is served, and the only trustworthy test is the live URL in a clean browser session. A student who learned to diagnose local-versus-live differences on GitHub Pages will diagnose the same class of bug on any static host, because the cause (environment mismatch) is platform-independent. Recognizing that the skill is "verify the deployed environment," not "click the GitHub Pages button," is the sign you understood publishing rather than memorizing one dashboard.
