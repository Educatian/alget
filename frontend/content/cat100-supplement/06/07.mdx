# Maintenance Plan

![Maintenance Plan textbook visual](/course-art/deep-exemplars/cat100-supplement/06-07-maintenance-plan.png)

## Why This Section Matters

A website is not finished when it goes live; it starts decaying the moment it does. Resume PDFs go stale, project links break when files are renamed, and a portfolio that proudly says "first-year student" two years later quietly tells visitors you stopped caring. A maintenance plan is the small, repeatable routine that keeps a published site honest over time. The hard part is not writing a plan but writing one you will actually follow: specific enough to act on, triggered by a real date, and matched to the kind of site you actually run.

This section also teaches a transferable judgment skill: filtering a generic AI-generated checklist down to what fits your situation. A static GitHub Pages site has no server to patch and no SSL certificate to renew, so a one-size-fits-all maintenance list includes tasks that are simply impossible for you. Learning to drop the irrelevant items and keep the real ones is the core move.

## Opening Case

A student finishes his portfolio and writes a maintenance note: "Keep the site updated sometime." A year later nothing has changed. The resume PDF is from freshman year, two project links 404 because he renamed the files, and the About page still says "incoming first-year." A recruiter who finds the site assumes it is abandoned. Wanting to do better, he asks an AI for a website maintenance checklist and gets a generic list: renew the SSL certificate monthly, patch server dependencies, refresh content quarterly, check links periodically. He starts trying to renew an SSL certificate that GitHub already manages for him and looking for a server that does not exist.

Two failures meet here: a plan too vague to follow, and a checklist not matched to a static site. This section fixes both.

## Core Concept

A usable maintenance plan has three properties.

**It is triggered, not aspirational.** "Sometime" never arrives. A plan needs a concrete trigger tied to the calendar: the first day of each quarter, the start of each semester, the day after every job application. A trigger turns intention into a recurring event you can actually notice.

**It is specific and verifiable.** "Keep it updated" cannot be checked off; "replace the oldest project card with my newest work" can. Each step should be a discrete action a future version of you can perform without interpreting what you meant, and a reviewer can confirm was done.

**It is matched to the platform.** Maintenance tasks depend on what kind of site you run. A static GitHub Pages site has no backend, so server patching and dependency updates do not apply, and Pages provides HTTPS automatically, so certificate renewal is GitHub's job, not yours. What does apply to a static portfolio is content freshness (resume, projects) and link integrity (renamed files break internal links). Filtering a generic list down to platform-relevant tasks is itself the skill.

The table shows that filtering applied to a typical AI checklist:

| AI checklist item | Keep for static GitHub Pages? | Reason |
| --- | --- | --- |
| Renew SSL certificate monthly | Drop | Pages provides HTTPS automatically |
| Patch server dependencies | Drop | No server exists to patch |
| Refresh content quarterly | Keep | Resume and projects go stale |
| Check links periodically | Keep | Renamed files break internal links |

This is ISTE digital citizenship in its quiet form: maintaining what you publish is part of publishing responsibly, and a neglected site misleads the people who rely on it. NACE career readiness frames the routine as professionalism; keeping a public artifact current is the kind of follow-through employers value.

## Worked Example

Maria's site is live. Now she writes a maintenance plan she can actually follow, and she filters a generic AI checklist down to what fits a static GitHub Pages site.

**Step 1. Start from the AI draft and judge each item.**

| AI checklist item | Keep for GitHub Pages? | Reason |
| --- | --- | --- |
| Renew SSL certificate monthly | Drop | Pages provides HTTPS automatically |
| Patch server dependencies | Drop | Static site; there is no server to patch |
| Refresh content quarterly | Keep | Resume and projects go stale |
| Check all links periodically | Keep | Renamed files break internal links |

**Step 2. Turn the kept items into a triggered, specific plan.**

```text
MAINTENANCE PLAN (my-portfolio)
Trigger: first day of each quarter (Jan 1, Apr 1, Jul 1, Oct 1)
1. Replace the oldest project card with my newest work.
2. Export the current resume to assets/resume.pdf.
3. Click every nav link and every project link; fix any 404.
4. Open the live URL on a phone to confirm layout still holds.
```

**Step 3. Record why a vague version was rejected.** The first draft said "keep the site updated sometime." That has no trigger and no task list, so it can never be verified or repeated. Naming the date and the four steps makes it actionable.

The plan now matches the platform (no server tasks), names a concrete cadence, and lists steps a future Maria can perform without guessing. Maintenance became a repeatable routine instead of a good intention.

## Decision Rule

Test any maintenance plan against three questions before you call it done:

1. **Trigger check:** Is there a concrete date or event that starts the routine? If the answer is "when I get around to it," the plan will not run.
2. **Specificity check:** Can each step be performed without reinterpreting it and confirmed as done? Replace verbs like "update" with named actions like "export resume to assets/resume.pdf."
3. **Platform check:** Does every task actually apply to a static GitHub Pages site? Drop server and certificate tasks; keep content and link tasks.

A plan that passes all three is a routine. A plan that fails the trigger check is a wish, and one that fails the platform check sends you chasing problems you do not have.

## Common Misreadings

The most common misreading is that more thorough means better. A long checklist copied from a generic source feels responsible but wastes effort on impossible tasks (patching a nonexistent server) and buries the two items that matter (content and links). Relevance beats length.

A second misreading is treating "I'll keep it updated" as a plan. Without a trigger and named steps, it is a hope. The discipline is to convert intention into a dated, checkable routine.

## Textbook Walkthrough

Apply the rule to the student's situation. He starts from the AI checklist and runs the platform check first. "Renew SSL certificate monthly" is dropped because Pages handles HTTPS automatically. "Patch server dependencies" is dropped because a static site has no server. "Refresh content quarterly" and "check links periodically" survive, because resumes go stale and renamed files break links on exactly this kind of site.

He then runs the specificity and trigger checks by rewriting the survivors into a dated routine: trigger on the first day of each quarter, then four named steps (replace the oldest project card, export the current resume to assets/resume.pdf, click every nav and project link and fix any 404, open the live URL on a phone to confirm layout). Compared with "keep the site updated sometime," every step is now actionable and verifiable, and the cadence is concrete. The plan matches the platform, names a trigger, and lists steps a future version of him can follow without guessing.

## What Strong Reading Looks Like

A strong reader can take any generic maintenance item and decide instantly whether it applies to a static site and how to make it specific. As you study the worked example, cover the "Keep?" column and judge each AI item yourself, then cover the routine and try to rewrite a vague task into a verifiable one. Matching the table and the routine means you can build a plan, not just copy one.

A strong reader of maintenance planning can answer four questions:

1. What trigger starts this plan, and is it concrete enough to notice?
2. Which generic checklist items are impossible on a static site, and why?
3. Could a stranger follow each step without asking what you meant?
4. How would you confirm, weeks later, that the routine actually ran?

## Stronger Artifact Standard

Your maintenance plan is strong when a future version of you, returning after months away, could execute it cold: a clear trigger, named steps, nothing that requires interpretation, and nothing that applies to a platform you do not run. The plan should read like a short procedure, not a paragraph of good intentions.

A strong submission names one item you deliberately dropped: "I removed 'renew SSL monthly' because GitHub Pages provides HTTPS automatically, so the task is not mine to do and including it would only waste time each quarter."

## Transfer Case

Move the same planning discipline to a different artifact: maintaining a shared team spreadsheet instead of a website. The platform changes, so the specific tasks change (archive last quarter's tab, re-verify the source data link, confirm formulas still reference the right ranges), but the three properties hold. The plan still needs a trigger (end of each month), still needs verifiable steps (not "tidy it up" but "delete rows older than one year"), and still must match the artifact (a spreadsheet has no SSL, but it has formula integrity). Carrying trigger, specificity, and platform-fit to a non-web artifact is the proof you learned to design a maintenance routine rather than memorize a website checklist.
