# Spreadsheet Structure and Clean Data

![Spreadsheet Structure and Clean Data textbook visual](/course-art/deep-exemplars/cat100-supplement/03-01-spreadsheet-structure-and-clean-data.png)

## Why This Section Matters

Every chart, pivot, and formula later in this module assumes the data underneath is clean. If the rows are not laid out the way Excel expects, nothing downstream behaves: a SUM skips numbers stored as text, a pivot splits `TX` and `texas` into two regions, and a chart inherits the mess. Clean structure is not housekeeping; it is the load-bearing step that decides whether the rest of your data story is trustworthy.

A spreadsheet built for analysis follows one quiet rule called tidy data: one variable per column, one observation (record) per row, and exactly one value in each cell. Downloaded exports almost never arrive that way. They carry banner titles, merged cells, blank spacer rows, two facts crammed into one column, and three spellings of the same category. This section teaches you to spot those defects and repair them in a sequence a reader can re-trace against the original file.

## Opening Case

You download a club's "Q3 Sales Report" and the first thing you see is a title in cell A1, an empty row 2, and a header row that does not start until row 3. The Region column reads `TX`, `texas`, and `Tx` in three different rows, and one name cell holds `Lopez, Maria`. You drop in `=SUM` to total the units and get a number that feels too low. Nothing is broken in an obvious way, yet the file cannot be analyzed as it stands.

That gap, between a file that looks finished and a table that is actually analyzable, is the real subject of this section. The fix is not cosmetic. Each repair changes what a formula or pivot will compute, so each repair is a decision you can defend.

## Core Concept

Clean data has a precise definition you can check against any sheet. A table is analysis-ready when it satisfies three structural conditions and one consistency condition:

| Rule | What it means | Common violation |
| --- | --- | --- |
| One header row | Row 1 holds column names only, with nothing above it | A banner title in A1 or a blank spacer row 2 |
| One value per cell | Each cell holds a single fact | `Lopez, Maria` (two facts) or `18 units` (number plus text) |
| One record per row | Each row is one observation | A subtotal row mixed in with raw rows |
| Consistent category labels | The same category is spelled one way | `TX`, `Tx`, and `texas` for one state |

The reason these rules matter is mechanical, not stylistic. Excel's aggregation tools (SUM, COUNT, pivot tables) treat each distinct text string as a distinct category and silently skip cells whose type is text when they expect a number. So `texas` and `TX` become two regions in a pivot, and a units value typed as `18 units` is read as text and excluded from a SUM. The visible symptom is a total that is lower than you expect with no error message to warn you. Cleaning the data is what makes the later count, sum, and chart say what you think they say.

Three tools do most of the repair work: **Text to Columns** (split one cell into two on a delimiter such as a comma), **Find and Replace** (collapse spelling variants into one canonical label), and deleting non-data rows (the banner and the blank). Knowing which tool fixes which defect is the core skill here.

## Worked Example

Suppose a downloaded export arrives looking like this, with a banner title, a blank row, mixed name format, and inconsistent regions:

```
   A              B        C
1  Q3 Sales Report
2
3  Name           Region   Units
4  Lopez, Maria   TX       18
5  Chen, David    texas     9
6  Park, Sun      Tx       12
```

Step 1. Delete rows 1 and 2 so the header row `Name | Region | Units` becomes row 1 with no banner or blank row above it.

Step 2. Split column A on the comma with Text to Columns so `Lopez, Maria` becomes `Lopez` in one column and `Maria` in the next. Now one value lives in one cell.

Step 3. Standardize the Region column. Replace `texas` and `Tx` with `TX` so all three rows read `TX`. A pivot will now count one region, not three.

Step 4. Confirm Units is numeric. `=SUM(units)` returns `39`. If any cell had been typed as `18 units`, that text cell would have been skipped and the total would read `21`, which is the visible symptom of the numbers-stored-as-text problem.

The clean table is now: three rows, one header, one value per cell, one spelling per region, and a SUM that matches the data. Each step is a decision a reader can re-trace against the raw export.

## Decision Rule

Clean structure before you compute anything. The order is deliberate: fix the layout, then split the cells, then standardize the labels, then confirm the numeric type, and only then sum, count, or chart. Running an analysis first and cleaning afterward means you never know which numbers were wrong.

Before you trust any total, run this three-point structural audit:

1. **Layout check:** Is row 1 a pure header with no banner or blank row above it, and is every row below it one record?
2. **Atomic check:** Does any cell hold two facts (a comma-joined name) or a number with a label (`18 units`)? If so, split it.
3. **Type and label check:** Are the values you will sum actually numeric (right-aligned by default), and is each category spelled exactly one way?

If `=SUM` of a column you believe is numeric returns a total lower than a hand count, you have failed the type check: at least one value is text and is being skipped.

## Common Misreadings

The most common error is treating a value typed as `18 units` or `$600` the same as a number. Excel left-aligns text and right-aligns numbers by default, so alignment is your fastest tell; a "number" hugging the left edge of its cell is text and will be dropped from sums.

A second misreading is thinking that deleting the visible banner is enough. If a blank spacer row remains between the title and the data, a pivot table will treat the first data row as a header or stop reading at the gap. Remove the blank row too, so the header sits in row 1 with data directly beneath it.

## Textbook Walkthrough

Apply the audit to a registrar export that lists course enrollments. The file opens with `Fall Enrollment Snapshot` in A1, a blank A2, and headers `Student, Course, Credits` starting in A3. The layout check fails twice, so delete rows 1 and 2 until `Student | Course | Credits` is row 1.

Scan for atomic violations. The Course column holds `CAT 100 - Intro`, two facts (a code and a title) in one cell. Use Text to Columns with the hyphen as the delimiter so the code and title live in separate columns; now you can pivot on the code alone. Then run the type check on Credits: a few cells read `3 cr`, which is text. Strip the `cr` so `=SUM(Credits)` counts every row instead of skipping the labeled ones.

Finally, standardize labels. The Course code appears as `CAT 100`, `CAT100`, and `cat 100`. Find and Replace each variant with `CAT 100`. Only now is the snapshot ready to summarize, and every step is one a reviewer can re-run against the original download.

## What Strong Reading Looks Like

A strong reader does not just notice that a sheet is messy; they predict the exact analytical failure each defect will cause. Train yourself to read a raw export and name the downstream consequence:

1. A blank spacer row will truncate a pivot or break a SUM range.
2. A comma-joined name cell cannot be sorted or filtered by last name.
3. Three spellings of one region will appear as three rows in a pivot, inflating the category count.
4. A number stored as text will silently lower every total it should be part of.

When you can move from "this looks untidy" to "this specific cell will drop \$600 from the total," you are reading the structure, not just the surface.

## Stronger Artifact Standard

A strong cleaned-data artifact ships with a short repair log, not just the tidy table. The log names each defect found in the raw export, the tool used to fix it, and the proof that the fix worked. A model line reads: "Region had `texas`, `Tx`, and `TX`; Find and Replace collapsed all three to `TX`; the pivot dropped from three region rows to one." The proof matters because it lets a reviewer confirm the repair without reopening the raw file.

The weakest version says only "I cleaned the data." The strongest version lets a reader reconstruct the original mess and verify that the SUM now matches a hand count of the rows. Aim for the version where the before state, the action, and the numeric proof are all visible.

## Transfer Case

The same audit transfers to a context with no banner and no blank rows: a survey export from a Google Form. Here the structural defects move into the cells. A "select all that apply" question stores `Pizza, Tacos, Sushi` in one cell, which violates the atomic rule and cannot be counted by option. A timestamp column mixes date and time, which you may need to split for a by-day pivot. The layout is fine, but the atomic and type checks still drive the work, so the skill is the audit itself rather than the specific banner-deleting steps from the worked example.
