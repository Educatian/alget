## Why This Section Matters

The capstone artifact review is the moment when everything you built across CAT 100 stops being homework and starts being a public record of what you can do. A hiring manager, a transfer advisor, or a scholarship reviewer will not read your weekly assignments; they will open one spreadsheet, one website, or one resume and decide in about thirty seconds whether to trust it. That decision is shaped by something you usually cannot see while you are building: whether your files quietly leak private information.

A privacy checklist is the discipline of inspecting your own artifacts the way an attacker or a careless search engine would. The most common failure in a student portfolio is not an ugly layout; it is an API key, a password, an email address, or a classmate's name committed into a public GitHub repository where it stays forever. This section teaches you to run a concrete, repeatable scan before review, so the artifact you publish is both useful and safe to share.

## Opening Case

Maya is about to share her GitHub Pages portfolio in the capstone showcase. The site looks finished: a clean header, three project cards, a contact form. What she cannot see from the rendered page is that her `app.js` still holds a weather API key she pasted while testing, and her `contact.html` carries a leftover comment with an SMTP password.

The rendered website hides both. A reviewer browsing the live page would never notice. But in a public GitHub repository, automated bots scrape new commits for exactly these strings within minutes; researchers who planted honeytoken AWS keys saw exploitation in about 30 minutes on average (Meli et al., 2019), and GitHub reported detecting 39 million leaked secrets in 2024, which is why push protection is now on by default. Maya's artifact is visually polished and simultaneously a security incident. The privacy checklist exists to catch the gap between "looks done" and "is safe to publish."

## Core Concept

A privacy checklist is a fixed set of inspections you run against the actual files you are about to publish, not against your memory of how careful you were. It rests on one hard fact about version control and the open web: once something is committed and pushed to a public repository, it is permanent. Deleting a secret in a later commit does not remove it; the value still lives in the repository history and may already be cached by scrapers. The only safe response to a leaked credential is to rotate it (generate a new one and invalidate the old).

The checklist covers three distinct surfaces, and confusing them is where students get hurt:

| Surface | What to look for | Why it matters |
| --- | --- | --- |
| Accounts and credentials | API keys, passwords, tokens, `.env` contents in tracked files | A live key can be abused to run up charges or send mail in your name |
| Data sharing | Real names, emails, student IDs, anything tied to a person who did not consent | FERPA-style privacy and basic respect; classmates did not agree to be published |
| AI tool boundaries | What you pasted into an AI tool, and what it generated that you cannot verify | Pasting private data into a chatbot shares it with a third party |

The reason a checklist beats good intentions is that secrets enter files by accident, during testing, when you are focused on making something work. You will not remember them later. A scan finds them; a memory does not. The output that earns review is not "I was careful," it is a reproducible command and its result.

> **Recent evidence (as of 2026).** Since March 11, 2024, GitHub enables secret scanning and push protection by default on new public repositories owned by personal accounts, so an obvious API-key push is often blocked before it ever lands; push protection blocked roughly 4.4 million secrets in 2024. But the guardrail recognizes only a limited set of known token types (200+ patterns from 180+ providers), can be bypassed or overridden, and does not scan a repository's existing history. The manual checklist, plus a dedicated scanner such as gitleaks (fast pre-commit/diff regex scanning) or trufflehog (full-history scanning that also verifies whether a found credential is still live), still matters.

## Worked Example: Auditing One Repo Against the Privacy Checklist

A student is about to submit a personal portfolio site hosted on GitHub Pages. Before the capstone review, they run the three-line privacy checklist against the repo.

**Step 1. Scan for committed secrets.** Open the project and search the tracked files.

```
$ git grep -n -i "key\|password\|token"
app.js:14:  const WEATHER_API_KEY = "a1f4c9e7b2d6";
contact.html:32:  <!-- TODO: SMTP password = summer2026! -->
```

Two hits. Both are real secrets sitting in tracked files.

**Step 2. Decide and act, row by row.**

| Item | Finding | Action |
| --- | --- | --- |
| `app.js:14` weather API key | Live key in a public repo | Move to `/config/keys.js`, add that path to `.gitignore`, rotate the key |
| `contact.html:32` SMTP password | Password in an HTML comment | Delete the comment, store the password in the server env, rotate it |
| Old commits | Key already pushed in commit `a1b2c3` | History is public, so treat both secrets as leaked and rotate regardless of deletion |

**Step 3. Record verifiable evidence.** The checklist line that passes review is not "checked privacy." It is:

> Removed weather key from `app.js:14` into `/config/keys.js` (now in `.gitignore`), deleted SMTP comment in `contact.html:32`, rotated both secrets on 2026-05-12, reran `git grep -i key` with zero hits in the working tree, and ran a history scan confirming no live credential remains in any commit; confirmed the page still loads.

That paragraph names the file, the line, the action, the date, and the re-check, so a reviewer can reproduce every step. Polish (a nicer layout, a hero image) is the last layer; it never substitutes for the secret audit.

> **The scan has a blind spot.** `git grep` searches only the current working tree. Delete a pushed secret, re-run the scan, and you will get zero hits while the secret still lives in commit `a1b2c3`, exactly the false reassurance this section warns against. To search history, run `git grep <pattern> $(git rev-list --all)`, or use a dedicated scanner: gitleaks (fast regex scanning of diffs and pre-commit hooks) or trufflehog (scans the full history and verifies whether a found credential is still live). A clean result means zero hits in the working tree *and* a history scan confirming no live credential remains; either way, rotation, not deletion, is still the real fix.

## Decision Rule

Treat any string that grants access or identifies a person as a leak until you have proven otherwise with a scan. Concretely, before you publish:

1. **Scan, do not recall.** Run `git grep -i` for `key`, `password`, `token`, `secret`, and `@` (to catch emails). Trust the output, not your memory. Remember that `git grep` checks only the working tree; pair it with a history scan (`git grep <pattern> $(git rev-list --all)`, or gitleaks/trufflehog) before you call the repo clean.
2. **Rotate anything that was ever pushed.** If a secret reached a public commit, deletion is not enough; invalidate the old credential and issue a new one.
3. **Quarantine third-party data.** Anything you pasted into an AI tool has left your machine; if it included private data, treat that data as shared and disclose it.

If a string survives all three checks, it is safe to publish. If you skip the scan, "it looks fine" is a guess, not a decision.

## Common Misreadings

The most damaging misreading is believing that deleting a secret fixes the leak. It does not: the value remains in the commit history of a public repository, retrievable by anyone who clones it. Deletion plus rotation is the fix; deletion alone is theater.

A second misreading is treating private data as only passwords. A classmate's full name on a sample invoice, a real email in a contact form's default value, or a teammate's student ID in a test dataset are all data you are publishing without consent. The checklist protects people, not just credentials.

## Textbook Walkthrough

Walk a real repository through the checklist in order. Begin with the credentials surface: open every file you wrote, not just the ones you remember editing, and run the grep scan. Treat each hit as guilty until cleared. The weather key in the worked example looks harmless because it is short and "just for testing," but a live key in a public repo is exactly what bots harvest.

Move next to the data surface. Look at sample data, form defaults, comments, and commit messages. A budget spreadsheet you built from a real club roster may carry member names; replace them with placeholders like `Member A` before publishing. This is where the artifact stops being only about you and starts being about the people whose information you handled.

Finally, audit the AI boundary. Reconstruct what you actually pasted into any AI tool while building. If you pasted a code block that contained the API key to ask for help debugging, that key is now known outside your machine and must be rotated, exactly as if you had published it. The walkthrough ends with the evidence paragraph: file, line, action, date, and re-check.

## What Strong Reading Looks Like

As you read, keep a running list with two columns: the exact string you found and the exact remediation you performed. A strong reader of this section does not summarize "I checked for secrets"; they can point to `app.js:14`, the action taken, the rotation date, and the clean re-scan.

A strong reader of the capstone privacy checklist can answer four questions:

1. Which exact files and lines did the scan flag?
2. For each flagged item, was the credential rotated, not just deleted?
3. What real-person data appears in sample data or form defaults, and how was it removed?
4. What did you paste into an AI tool, and does any of it now need rotation or disclosure?

## Stronger Artifact Standard

The artifact is strong when a reviewer can rerun your scan and get zero hits, and when every remediation is dated and verifiable. The standard is not "I believe it is clean," it is a reproducible `git grep` command that returns nothing plus a short log of what was removed and rotated.

A useful closing note for the artifact would read: "Scanned the repo for credentials and personal data on 2026-05-12; moved one API key out of tracked files and rotated it, removed one password comment and rotated the mail credential, replaced two real member names in the sample budget with placeholders. Re-scan returns zero hits." That sentence proves the decision instead of asserting it.

## Transfer Case

Move the same artifact into a stricter setting: a public job application where the repository link goes to a recruiter, or a team project where a partner committed the secrets. The scan does not change, but the stakes and the responsibility do. With a recruiter, a single leaked key signals carelessness about exactly the kind of access an employer would trust you with. With a partner, you must coordinate rotation because the leaked credential may be theirs. Use the change in setting to test whether you treat the checklist as a habit you can run anywhere, or only a one-time CAT 100 task.
