# Final Submission Checklist

![Final Submission Checklist textbook visual](/course-art/deep-exemplars/cat100-supplement/08-07-final-submission-checklist.png)

## Why This Section Matters

More submissions lose points to logistics than to weak content. A deck submitted in the wrong format, a portfolio link that returns a 404 to anyone not signed into your account, a file named `final.pdf` that the grader cannot tell apart from forty others: each of these is fully avoidable and each can sink an otherwise strong artifact. The final submission checklist is the last gate, and its whole purpose is to replace the feeling that the work is done with proof that it is deliverable.

The deeper habit here is verification from the recipient's position. You know your link works because it works for you, signed in, on your machine. The grader is none of those things. A checklist forces you to open the exported file yourself, click the link in an incognito window, and read the assignment requirements literally. It is the difference between "I think I submitted correctly" and "I confirmed each requirement with a test."

## Learning Targets

- Translate each literal assignment requirement into a testable checklist row with a pass condition.
- Verify each row from the recipient's position, such as loading links in a signed-out window and opening the exported file you actually submitted.
- Document a bounded AI/software support move with accepted and rejected suggestions.
- Use feedback, support requests, and revision notes to improve the artifact before sharing it.

## Opening Case

Alex finishes a capstone with three deliverables and uploads them. The assignment said, "Submit slides as a PDF and include a public link to your site." Alex uploaded the PowerPoint file, not a PDF, and pasted a GitHub Pages link that happens to load only because Alex is signed into the account that owns the repository.

To Alex, everything looks submitted and working. To the grader, the slides may render with shifted fonts in a different PowerPoint version, and the site link returns a 404 because the grader is not Alex. The work is strong; the submission is broken. The checklist exists to catch exactly this gap between "works for me" and "works for the person receiving it."

## Core Concept

A submission checklist is a list of concrete, testable requirements, where each item is verified by an action you actually perform, not by recollection. The items fall into a few categories that recur across almost every assignment:

| Category | Item | The test that verifies it |
| --- | --- | --- |
| Format | Correct file type (PDF, not PPTX) | Export, then open the exported file and confirm nothing shifted |
| Access | Link is public | Open it in an incognito or signed-out window and confirm no 404 |
| Identification | Filename follows the convention | Read the requirement, rename to match (`lastname_course_v3.pdf`) |
| Safety | No private data or credentials | For a repo artifact, rerun the `git grep` credential scan; for a document or spreadsheet, open the file and scan for embedded keys, passwords, tokens, or personal data |
| Correctness | No broken values | Open the file and confirm totals compute, with no `#REF!` |

The unifying principle is testing from the recipient's environment. Exporting to PDF is not enough; you open the PDF to confirm a chart did not move. Pasting a link is not enough; you load it while signed out, which is the single most common catch, because GitHub Pages, Google Drive, and many tools quietly grant you access they do not grant a stranger. Each checklist row is a hypothesis ("the link is public") paired with the experiment that confirms it ("loaded it incognito, no 404").

The same recipient-position logic bounds AI help. As of 2026, a chat assistant such as ChatGPT or Claude can draft the checklist rows for you, but it cannot reliably open your exported PDF or load your link the way the grader will: file handling is gated by format and plan, and even an assistant that can fetch a URL does so through its own service, not through a signed-out, no-account browser session. The verification tests stay yours to run.

## Worked Example: Running the Final Submission Checklist

A student is ready to submit a capstone with three deliverables: a slide deck, a portfolio link, and a budget spreadsheet. The assignment says, "Submit slides as a PDF and include a public link to your site." They run each checklist item and record the result.

| Checklist item | Action and result | Status |
| --- | --- | --- |
| Correct export format | Exported `presentation.pptx` to PDF; opened the PDF and confirmed fonts and chart did not shift | Pass |
| Link is public | Opened the GitHub Pages link in an incognito window while signed out; page loaded, no 404 | Pass |
| Filename convention | Renamed `final.pdf` to `moon_cat100_capstone_v3.pdf` so it is identifiable | Pass |
| No private data | Reran `git grep -i "key\|password"` on the repo (zero hits); opened the PDF deck and the budget spreadsheet and scanned them for embedded keys, tokens, and personal data (none found) | Pass |
| Spreadsheet totals | Confirmed Total cell B14 reads `=SUM(B2:B13)` = 8,420 with no `#REF!` | Pass |

The checklist is not cosmetic. Each row is a concrete test the student actually performed, including opening the exported file and the link from a signed-out browser. The submission goes out only after every item shows a verifiable pass, not after the work merely "feels done."

## Decision Rule

Submit only after every requirement has passed a test you ran from the recipient's position. Before you click submit:

1. **Read the requirement literally.** "Slides as a PDF" means a PDF, not the source file. Match the exact format and naming the assignment states.
2. **Open what you exported.** A PDF that lost a chart is worse than the original; confirm the file by opening it, not by trusting the export button.
3. **Test access while signed out.** Load every link in an incognito window. If it 404s there, it 404s for the grader.

If any item cannot be tested to a pass, the artifact is not ready to submit, however finished it feels.

## Common Misreadings

The first misreading is trusting that a link works because it works for you. Signed-in access is invisible privilege; the incognito test is the only honest check. Skipping it is the most common reason strong portfolios receive a zero for the link.

The second misreading is treating the checklist as bureaucratic busywork. Each row prevents a specific, real failure: wrong format, broken access, an unidentifiable filename, a leaked credential, a broken total. The checklist is not ceremony; it is the set of mistakes that actually cost students points, written down so you stop repeating them.

## Textbook Walkthrough

Begin by reading the assignment instructions and converting each requirement into a testable row. "Submit slides as a PDF" becomes two rows: export to PDF, and open the PDF to confirm fidelity. "Include a public link" becomes one row with an explicit incognito test. Turning prose requirements into tests is the move that prevents "I thought it said" mistakes.

Work the rows with real actions. Export the deck, then open the resulting PDF and look at the chart and fonts, because conversion routinely shifts them. Copy the site link, open a private window, sign out, and load it; a 404 here is the failure you most want to catch before the grader does. Rename the file to the stated convention so it is identifiable among many. Rerun the credential scan against whatever artifact actually carries text or data, not only the repo: `git grep` covers tracked files in a git repository and does nothing for a standalone PDF or spreadsheet, so open those files and scan for embedded API keys, passwords, tokens, or personal data (a leftover key in a worksheet cell or in the speaker notes is the classic miss). Then open the spreadsheet to confirm the total computes.

Mark each row pass only after its test passes, and submit only when the whole table is green. The walkthrough output is a checklist table where every status is backed by an action you can describe, not a feeling.

## What Strong Reading Looks Like

As you read, write the test, not just the item, for each requirement of an assignment you actually have. A strong reader does not list "link is public"; they write "open it incognito, expect no 404," because the test is what makes the item verifiable.

A strong reader of the final submission checklist can answer four questions:

1. What does the assignment require, stated literally, and is each requirement a row?
2. For each row, what action verified it, performed from the recipient's environment?
3. Which link or file did you test while signed out, and what did you see?
4. Did anything fail a test, and was submission held until it passed?

## Stronger Artifact Standard

The submission is strong when every requirement maps to a row, every row records the action that verified it, and access items were tested signed out. The standard is a checklist where each status is justified by a test, not by the sense that the work is finished.

A useful closing note would read: "I converted each assignment requirement into a testable row. I exported the deck to PDF and opened it to confirm the chart did not shift, loaded the site link in an incognito window and saw no 404, renamed the file to `moon_cat100_capstone_v3.pdf`, reran the credential scan with zero hits, and confirmed the spreadsheet total computes. I submitted only after every row passed its test."

## Transfer Case

Apply the same checklist discipline to a job application, where the recipient is a recruiter and the requirements live in the posting. "Attach your resume as a PDF" and "include a link to your portfolio" become the same testable rows, but the cost of a failed access test is now a missed opportunity rather than lost points. Loading your own portfolio link from a friend's signed-out browser before you send the application is the test of whether you carry submission verification into high-stakes settings, not just into the course where you first learned it.
