## Why This Section Matters

The hardest part of finishing a course is naming what you actually learned in language a future employer or professor understands. "I learned Excel" is nearly useless: it names a brand, not a capability, and it does not say what you can do or whether it survives outside a 40-row classroom dataset. A transfer map fixes this by converting each tool you touched into a portable capability, a proof that you did it, a real destination task where it applies, and an honest note about what changes when the context grows.

This matters because transfer is rarely a copy. The pivot table that ran cleanly over 512 class rows can silently go stale over 40,000 rows at a part-time job if its source range stays fixed while the data keeps growing. Knowing the click sequence is not the same as owning the skill. The transfer map is where you prove you understand a skill well enough to adapt it, which is exactly what makes it worth listing on a resume.

## Opening Case

Jordan is updating a resume after CAT 100 and writes a transfer line that reads, in full, "Excel - my future career." A peer reviewer asks two questions Jordan cannot answer: "What can you do in Excel?" and "Where would you use it?" The line names a tool and a vague hope, with no capability and no destination.

The problem is not that Jordan lacks skills; it is that the line does not transfer. It cannot move into a job description because it never said what task it performs. The transfer map turns that dead line into something a reader can act on: a named capability, a file that proves it, a concrete job task, and the adaptation the new context demands.

## Core Concept

A digital skills transfer map is a table with one row per skill and four columns that force you from a tool name toward a defensible claim of competence:

| Column | Question it answers | Failure if missing |
| --- | --- | --- |
| Capability | What can you actually do, in verb form? | You list a brand ("Excel"), not an ability |
| Proof artifact | Where is the file that shows you did it? | The claim is unverifiable |
| Destination task | What real task outside class uses this? | The skill has nowhere to go |
| Adaptation note | What changes when the context shifts? | You reveal you only memorized clicks |

The intellectual core is the difference between near transfer and far transfer, a distinction that follows Barnett and Ceci's (2002) taxonomy of the dimensions along which a learned skill must travel to a new context. Near transfer is reusing a skill in a context almost identical to where you learned it. Far transfer is applying it where the data, scale, or stakes differ, and it requires understanding why the procedure works, not just the keystrokes. The adaptation column is where far transfer shows: a student who writes "the formula needs an absolute reference once the data grows past a few thousand rows" understands the mechanism; a student who writes "use Excel" does not.

This is also why a proof artifact is non-negotiable. A capability claim without a linked file is a wish. The map ties every claim to a real Unit file a reviewer can open, which is the same evidence standard you carry into the resume and portfolio.

## Worked Example: Building One Row of a Transfer Map

A student is mapping a CAT 100 skill to a part-time retail job. The weak first draft is a single word.

**Before (a tool name, not a skill).**

| Skill | Transfers to |
| --- | --- |
| Excel | My future career |

A reviewer learns nothing: no capability, no destination task, no proof.

**After (capability, proof, destination, adaptation).**

| Skill (capability) | Proof artifact | Destination task | What changes in the new context |
| --- | --- | --- | --- |
| Summarize data with a pivot table | Unit 5 file pivots 512 order rows into a Region x Month grid | Build the weekly sales recap at the store | Source grows from 512 to ~4,000 rows; a pivot built on the fixed range `A1:F512` silently ignores the new rows, so base the pivot on an Excel Table (or a named dynamic range) and Refresh after each import |

The capability replaces the brand name. The proof points to a real file. The destination names a concrete job task. The last column shows the transfer is an adaptation, not a copy: the pivot that ran over 512 class rows silently excludes appended rows once the source range stops matching the data, so it must sit on an Excel Table and be refreshed. That adaptation note is the evidence that the student understands the skill rather than just the click sequence.

## Decision Rule

Promote a tool to a transferable skill only when you can fill all four columns honestly. For each row:

1. **Name the verb, not the brand.** "Summarize data with a pivot table" beats "Excel." If you cannot state a verb, you have not isolated a capability.
2. **Link a real file.** Point to the specific Unit artifact that demonstrates the capability. No file, no claim.
3. **Stress-test the transfer.** Ask what breaks when the data is bigger, messier, or higher-stakes. If nothing changes, you are describing near transfer only; name the adaptation that far transfer would require.

If any column stays empty, the skill is not yet ready to put in front of an employer.

## Common Misreadings

The first misreading is treating the destination as "my future career" or "any job." A destination is a specific task: the weekly sales recap, the budget reconciliation, the inventory count. Vague destinations signal that you have not pictured the skill in use.

The second misreading is assuming a skill transfers unchanged. The most revealing column is the adaptation note. A student who claims a 40-row pivot transfers untouched to a 40,000-row dataset has not understood that a pivot built on a fixed source range silently excludes appended rows; it must be based on an Excel Table or refreshed against the grown range. Naming what changes is the proof of genuine, far transfer.

## Textbook Walkthrough

Begin with one skill you genuinely used, and write the capability as a verb phrase. Resist the brand name; "make a website" is weak, "publish a multi-page static site with valid HTML headings" is a capability. The sharper the verb, the more a reader can match it to a task.

Next, link the proof. Open your course files and find the exact artifact that demonstrates the capability, then reference it by unit and content, like "Unit 5 pivots 512 order rows." This grounds the claim in something inspectable and keeps you honest about what you actually built.

Then name a real destination and stress-test it. Pick a concrete task in a job, internship, or another course, and ask what differs there: more rows, dirtier data, a deadline, a real customer whose name appears in the data. Write the adaptation that difference forces, such as anchoring a lookup range or sampling before charting. That final note is what separates a transfer map from a tool inventory.

## What Strong Reading Looks Like

As you read, draft one transfer-map row for a skill you have not seen modeled here, all the way through the adaptation column. A strong reader does not restate the pivot-table example; they can map a different skill, such as version control or HTML, and name what changes when it scales.

A strong reader of the digital skills transfer map can answer four questions:

1. For each skill, what is the capability stated as a verb, not a brand?
2. Which specific file proves the capability?
3. What concrete destination task uses it, and is the task real rather than "my career"?
4. What changes about the procedure when the data or stakes grow, and why?

## Stronger Artifact Standard

The map is strong when every row links a verb-form capability to a real file, a concrete destination, and a specific adaptation that demonstrates far transfer. The standard is not length; a three-row map with honest adaptation notes beats a ten-row list of tool names.

A useful closing note would read: "I mapped the pivot-table skill to the store's weekly sales recap and noted that the source grows from 512 to about 4,000 rows, which forces the pivot onto an Excel Table source, refreshed after each import, so it does not silently exclude the new rows. I left off a row for a tool I only watched a demo of, because I have no proof artifact and cannot defend the transfer."

## Transfer Case

Apply the map itself to a non-spreadsheet skill, such as the HTML you wrote for your portfolio. The capability is "publish a multi-page static site"; the proof is your GitHub Pages repo; the destination might be maintaining a small business's landing page. The adaptation note now concerns something different: a real site needs a mobile-friendly layout and accessible alt text that a single class page could ignore. Reaching a correct adaptation note for a skill the worked example never covered is the test of whether you can build transfer maps independently rather than copy one.

## Adaptive Support

ALGET uses your annotations and artifact trace to choose support:

- If your note is a **question**, ask for a concise explanation tied to **[NACE career readiness](https://www.naceweb.org/career-readiness/competencies/career-readiness-defined)**.

- If your note is an **insight**, transfer the same decision rule to a new audience or setting.
- If your note makes a **connection**, show where the connection changes the artifact.

For the bounded AI/software support move itself, ground it in a current tool: as of 2026, Copilot in Excel suggests formulas and builds pivot tables from natural language, and it may offer a relative-range formula paste that should be modified to an anchored range before accepting. Documenting that modify-or-reject decision is exactly the adaptation note the map asks for.
