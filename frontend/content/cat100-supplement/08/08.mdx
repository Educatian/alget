# Future Learning Plan

![Future Learning Plan textbook visual](/course-art/deep-exemplars/cat100-supplement/08-08-future-learning-plan.png)

## Why This Section Matters

"Get better at coding and learn more about data" is the kind of goal that feels good to write and is impossible to act on. It has no finish line, no proof, and no sequence, so a month later you cannot tell whether you made progress. The skill this final section builds is turning vague intentions into a learning plan you can actually check: measurable goals, each tied to a concrete deliverable, scheduled with dates, and ordered so that prerequisites come first.

This matters because the course is ending and no one will assign you the next step. A plan that names a specific artifact ("a budget file using `SUMIFS` and `VLOOKUP` across 200 rows, posted as a link") is something you, or an advisor three months from now, can verify happened. A plan that says "improve at Excel" cannot be checked by anyone, including you. Learning to write goals with built-in proof is what lets self-directed learning continue after the course stops directing it.

## Opening Case

Robin finishes CAT 100 and writes a future plan in one line: "Get better at coding and learn more about data." It feels ambitious and motivated. Two months later, Robin cannot answer a simple question: did it happen? There was no target to hit, no artifact to point to, and no order to follow, so "better" stayed undefined.

The intention was real; the plan was unusable. A goal with no measure cannot succeed or fail, which means it cannot guide a single afternoon of effort. The future learning plan turns Robin's wish into rows that each name a goal, the deliverable that proves it, a date, and the prerequisite that must come first, so progress becomes something you can check rather than feel.

## Core Concept

A future learning plan is a table where each goal carries four parts that together make it verifiable and sequenced:

- **Measurable goal.** A capability stated so completion is unambiguous. "Master spreadsheet formulas" is too soft; "build a budget file using `SUMIFS` and `VLOOKUP` across 200 rows" has a clear done state.
- **Proof artifact.** The deliverable that demonstrates the goal, such as a posted link or a screenshot. The proof is what makes the goal checkable by someone other than you.
- **Target date.** A deadline that turns "someday" into a commitment you can fall behind on and notice.
- **Prerequisite.** What must be learned first, so the plan respects dependencies instead of attempting everything at once.

The intellectual core is two ideas from goal-setting and skill-building. The first is the difference between an outcome you can measure and a vibe you cannot: a goal that produces an inspectable artifact can be confirmed, while "get better" cannot. The second is sequencing by prerequisite. You cannot meaningfully write a database query before you can summarize data in a spreadsheet, so the plan orders the database goal after the spreadsheet goal rather than starting both at once. A plan that ignores prerequisites collapses under its own ambition; a sequenced plan moves one verifiable step at a time.

## Worked Example: From a Vague Wish to a Verifiable Learning Plan

A student finishing CAT 100 first writes a vague plan.

**Before (no measure, no date, no proof).**

> Get better at coding and learn more about data.

There is no finish line, so progress can never be checked.

**After (measurable goals, sequenced, each with a proof).**

| Goal | Measurable proof | Target date | Prerequisite |
| --- | --- | --- | --- |
| Master spreadsheet formulas | A budget file using `SUMIFS` and `VLOOKUP` across 200 rows, posted as a link | June 15 | Finish CAT 100 Excel unit |
| Publish a portfolio site | 3 pages live on GitHub Pages with valid HTML headings and a working nav | August 1 | Finish CAT 100 HTML unit |
| Try a database query | One `SELECT ... WHERE` query that filters the budget data, with a screenshot | September 1 | Spreadsheet goal complete first |

Each row names a goal, a concrete deliverable that proves it, a date, and the prerequisite that must come first. The database goal is sequenced after spreadsheets rather than attempted all at once. A future advisor, or the student in three months, can check each milestone against its proof instead of guessing whether progress happened.

## Decision Rule

Write only goals that produce a deliverable you could show someone, in an order their prerequisites allow. For each goal:

1. **Demand a proof artifact.** If you cannot name the file, link, or screenshot that would prove completion, the goal is too vague to keep.
2. **Set a date.** A goal without a deadline never becomes urgent; assign one you can be measured against.
3. **Order by prerequisite.** Place each goal after whatever it depends on, so you build one verifiable step at a time instead of attempting everything at once.

If a goal has no measurable proof, it is a wish; rewrite it until it produces something checkable.

## Common Misreadings

The first misreading is mistaking ambition for a plan. "Learn data science" is a direction, not a goal; it has no done state and no proof. The fix is to name the smallest deliverable that would show real progress, like one working `SELECT ... WHERE` query, and start there.

The second misreading is ignoring prerequisites and scheduling everything for next week. Stacking a database goal in the same window as the spreadsheet goal it depends on guarantees both stall. Sequencing is not pessimism; it is what makes each step achievable, because the earlier skill is the foundation the later one stands on.

## Textbook Walkthrough

Start by taking a vague intention and asking, "What would I be able to show if I succeeded?" That question converts "get better at spreadsheets" into "a budget file using `SUMIFS` and `VLOOKUP` across 200 rows, posted as a link." The deliverable is now the goal, and it is checkable.

Next, attach a date and a prerequisite to each goal. The date forces commitment; the prerequisite reveals order. The portfolio-site goal depends on finishing the HTML unit, and the database goal depends on the spreadsheet goal being done first, because querying data assumes you can already structure and summarize it. Lay the goals out so each one sits after what it needs.

Finally, sanity-check the sequence by reading it top to bottom: could you actually complete row two before row three begins? If a later goal secretly depends on an earlier one you scheduled after it, reorder. The walkthrough output is a goal table where every row has a proof, a date, and a prerequisite, and the order respects dependencies.

## What Strong Reading Looks Like

As you read, draft one goal of your own all the way to its proof artifact and prerequisite. A strong reader does not just admire the example table; they can take a real ambition and pin a checkable deliverable and a correct prerequisite to it.

A strong reader of the future learning plan can answer four questions:

1. For each goal, what specific deliverable would prove it is done?
2. What date is attached, and is it concrete enough to fall behind on?
3. What must be learned first, and does the order respect that prerequisite?
4. Where a goal is still vague, what is the smallest provable version of it?

## Stronger Artifact Standard

The plan is strong when every goal names a measurable proof artifact, carries a date, and sits in an order its prerequisites justify. The standard is not a long list of aspirations; a three-goal plan where each goal is checkable and correctly sequenced beats a sprawling wish list with no proofs.

A useful closing note would read: "I rewrote 'get better at coding and data' into three goals, each with a deliverable I can post: a 200-row `SUMIFS` and `VLOOKUP` budget file by June 15, a three-page GitHub Pages site by August 1, and one `SELECT ... WHERE` query with a screenshot by September 1. I sequenced the database goal after the spreadsheet goal because querying data assumes I can already structure and summarize it."

## Transfer Case

Apply the plan to a non-technical goal, such as preparing for an internship search. The structure holds: "get a good internship" becomes measurable goals like "complete three tailored applications by July 1," each with a proof (the submitted application) and a prerequisite (a finished resume and portfolio, which themselves come from earlier sections of this chapter). Writing a sequenced, provable plan for a goal that has no formula or code at all is the test of whether you have internalized goal-setting as a reusable method rather than a spreadsheet-specific exercise.
