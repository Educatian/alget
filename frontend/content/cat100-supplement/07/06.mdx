# Collaboration Norms

![Collaboration Norms textbook visual](/course-art/deep-exemplars/cat100-supplement/07-06-collaboration-norms.png)

## Why This Section Matters

Group work fails far more often from missing norms than from missing effort. Four motivated students sharing one document will still collide if everyone edits the same paragraph at once, if the link is open to the world, if changes overwrite each other with no record, and if the only deadline is the real one at 11:59 PM. These are not personality problems; they are the predictable result of an unmanaged shared file. This section teaches the small set of norms that make a shared document safe to work in: least-access sharing, clear section ownership, suggesting mode, and an internal deadline ahead of the real one.

These norms are the difference between a group project that comes together calmly the day before and one that produces a last-minute scramble where someone's work silently disappears. They are also directly transferable to every workplace that uses shared documents.

## Learning Targets

- Set least-access sharing so only the people who need to edit can edit, and everyone else can view.
- Assign section ownership so no two people work on the same part at the same time.
- Use suggesting mode and comments so edits are visible and reversible, never silent overwrites.
- Set an internal deadline ahead of the real one to leave time for review.

## Opening Case

A four-person team shares one document set to "anyone with the link can edit." All four open the introduction at once on the night it is due. Two of them type over each other; the document keeps only the last save, so one person's paragraph vanishes with no trace. The final section is pasted in at 11:55 PM for an 11:59 PM deadline, leaving zero time to read the whole thing for coherence. Nothing here was caused by laziness; it was caused by the absence of four simple rules.

The fix is to agree on access, ownership, edit mode, and timing before anyone starts writing, so the document structure itself prevents the collisions.

## Core Concept

Collaboration norms manage four risks that shared documents create.

**Access risk** is who can change the file. The principle is least access: grant edit rights only to the actual contributors and leave everyone else on view-only. "Anyone with the link can edit" invites accidental or malicious changes from outside the group.

**Collision risk** is two people editing the same content at once. The fix is **section ownership**: each contributor owns a distinct part (intro, methods, results, conclusion), so simultaneous edits never land on the same text. Ownership turns a free-for-all into parallel, non-overlapping work.

**Overwrite risk** is one edit silently erasing another. **Suggesting mode** (proposed changes the owner accepts or rejects) plus comments makes every change visible and reversible, so nothing disappears without a record. This is the collaborative analogue of the version history you would keep for your own files.

**Timing risk** is having no margin to review. An **internal deadline** set 24 hours before the real one reserves time for the team to read the assembled whole, catch contradictions between sections, and fix them before submission.

The unifying idea is that good collaboration is designed, not hoped for: you set up the document so the common failures cannot happen, rather than asking everyone to be careful.

## Worked Example

Here is a real group document moved from chaos to working norms.

**Before (one shared file, no rules):**

```
Sharing:  Anyone with link can EDIT
Owners:   none; all four edit the intro at once
Timing:   last section pasted at 11:55 PM for an 11:59 PM due time
Edits:    teammates overwrite each other's text with no record
```

A stranger could edit it, two people collided on the intro, and there was no time to review.

**After (named access, owners, suggestions, internal deadline):**

```
Sharing:  4 named teammates as EDITORS; everyone else VIEW only
Owners:   Intro = Ana, Methods = Ben, Results = Cy, Conclusion = Dee
Timing:   internal deadline Thursday 11:59 PM (24h before the real one)
Edits:    use Suggesting mode + comments so changes are visible and reversible
```

Four norms did the work:

1. **Least-access sharing**: named editors only, not public edit.
2. **Section owners** so no two people retype the same paragraph.
3. **Suggesting mode and comments** so edits never silently overwrite a teammate.
4. **An internal deadline 24 hours early** so the team can review before submitting.

## Decision Rule

Before a group starts working in a shared file, decide four things: who can edit (least access), who owns which section, how edits will be made visible (suggesting mode), and when the internal deadline falls. Settle these before the writing, not during the crisis.

A well-run shared document passes four checks:

1. **Access check:** Can only the actual contributors edit, with everyone else on view-only?
2. **Ownership check:** Does each section have one clear owner, so no two people edit the same part?
3. **Visibility check:** Are changes made through suggesting mode and comments, so nothing is silently overwritten?
4. **Timing check:** Is there an internal deadline ahead of the real one to leave room for review?

If any check fails, the document is set up to produce the exact collisions group projects are famous for.

## Common Misreadings

The most common misreading is "we trust each other, so we do not need rules." Trust does not prevent two people from opening the same paragraph at once; ownership and edit mode do. The norms protect good teammates from honest collisions, not just from bad actors.

A second misreading is treating the assignment deadline as the team deadline. With no internal deadline, the document is finished at the moment it is due, with no time to read it as a whole.

## Textbook Walkthrough

Apply the norms to a slide deck instead of a written report, where the same risks appear in a different shape. Access: invite the four presenters as editors, set the link to view-only for the rest of the class who will see it later. Ownership: assign slides by topic so two people never restyle the same slide and overwrite each other's layout.

Visibility is trickier in slides, where suggesting mode may not exist, so the norm adapts to "edit your own slides only, and leave a comment before changing someone else's." Timing: set the internal deadline to the night before the presentation so the team can do a full run-through and fix the slide where two sections repeat the same statistic. The walkthrough shows the four norms holding across document types, with the visibility norm adapting to the tool's features.

## What Strong Reading Looks Like

A strong reader looks at a shared document and can predict where it will break before any work happens. An open edit link, no section owners, and only the real deadline are red flags regardless of how good the team is.

A strong reader of a collaborative document can answer four questions:

1. Who can edit this, and is anyone with access who should not have it?
2. Who owns each section, and where could two people collide on the same content?
3. If a teammate's text were overwritten tonight, could it be recovered, and would anyone notice?
4. Is there time reserved to read the assembled whole before it is due?

## Stronger Artifact Standard

The artifact is the document's collaboration setup: its sharing settings, an ownership map, the edit mode, and the internal deadline. It is strong when a reader can see that the four risks are each addressed before any content is written.

A useful note sounds like this: "I changed the sharing from public-edit to four named editors and assigned each of us a section, then set the document to suggesting mode. I rejected keeping a single shared intro that everyone edits, because that is exactly where our last project lost a paragraph to an overwrite."

## Transfer Case

Move the norms from a class group project to a workplace shared drive. Least access, ownership, visibility, and an internal deadline all transfer, but access control becomes stricter and more consequential: at work, the wrong person editing a client file can have legal or financial consequences, so view/edit permissions are governed by role and policy, not just convenience. The four norms hold; what adapts is that access decisions move from a casual group choice to a policy-bound one.
