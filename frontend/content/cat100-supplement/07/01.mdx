# File Organization for Coursework

![File Organization for Coursework textbook visual](/course-art/deep-exemplars/cat100-supplement/07-01-file-organization-for-coursework.png)

## Why This Section Matters

By the end of a single semester a typical student touches several hundred files: drafts, datasets, screenshots, downloaded readings, rubrics, and exports from group tools. The cost of disorder is not abstract. It shows up as a submitted draft that turns out to be `final2` instead of `FINAL_real`, a missing rubric the night before grading, or a deleted-by-accident essay with no second copy. File organization is the unglamorous foundation that every later skill in this chapter (calendars, templates, automation) sits on top of, because automation amplifies whatever structure you already have. If your files are chaotic, a rename rule run across the whole folder amplifies the chaos.

This section teaches a concrete, repeatable filing system you can set up in fifteen minutes and reuse every term. The test of the system is simple: a stranger (or future-you in week 14) can open one folder and find the newest version of any assignment without asking a single question.

## Learning Targets

- Build a course/module/task folder tree so all files for one assignment travel together.
- Apply a `date_course_task_version` naming pattern that makes the newest file obvious at a glance.
- Keep a second synced copy so a single device failure never destroys the only version of your work.
- Justify each filing decision by the question it answers for a future reader: which file, which version, where.

## Opening Case

A student finishes a lab report at 11:50 PM, opens the upload page, and faces four candidate files: `lab.docx`, `lab_final.docx`, `lab_final2.docx`, and `FINAL_real.docx`. The modified dates all read "today" because the student saved, duplicated, and re-exported all four during the same late-night session, so they cluster to the same day. There is no way to tell which is the version with the corrected calculations short of opening all four and reading them. That two-minute panic is the exact failure a naming convention prevents.

The deeper point is that file names are a communication channel. A good name tells a reader the date, the course, the task, and the version without opening the file. A bad name forces a guess, and guesses under deadline pressure produce wrong submissions.

## Core Concept

File organization is the practice of encoding three pieces of information into structure and names so that retrieval is fast and unambiguous: **what** the file is, **which version** it is, and **where** it belongs. Two mechanisms carry the load.

The first is the **folder hierarchy**, which answers "where does this belong." A flat Desktop with 80 items forces a linear scan; a tree lets you navigate by elimination. The reliable pattern for school is three levels: course, then module or week, then task. Everything for one assignment lives in one leaf folder, so it can be backed up, shared, or zipped as a unit.

The second is the **file name**, which answers "what" and "which version." Computers sort names alphabetically, so if you lead with an ISO date (`2026-05-28`), files sort into chronological order automatically. A name built as `date_course_task_version` then encodes everything a reader needs:

| Part | Example | What it answers |
| --- | --- | --- |
| ISO date | `2026-05-28` | When; also forces chronological sort |
| Course | `cat100` | Which class, so search finds it |
| Task | `essay` | What the file is |
| Version | `v3` | Which is newest, with no FINAL_real guessing |

These two mechanisms work because they front-load the decision. You name and file the moment you create, not later, so retrieval never requires reconstruction from memory.

## Worked Example

Here is a real before/after for one student's CAT 100 files.

**Before (flat Desktop, undescriptive names):**

```
Desktop/
  final.docx
  final2.docx
  FINAL_real.docx
  IMG_4471.jpg
  syllabus.pdf
  Downloads/
    document(1).docx
```

You cannot tell which `final` is newest, which class the syllabus belongs to, or where the essay image goes.

**After (course / module / task tree with dated names):**

```
Documents/
  CAT100/
    Module07-Productivity/
      file-organization/
        2026-05-28_cat100_essay_v3.docx
        2026-05-28_cat100_essay_rubric.pdf
        2026-05-26_cat100_essay_diagram.jpg
```

Three concrete changes did the work:

1. **Folder tree by course then module then task** so one assignment's files travel together.
2. **Name pattern `date_course_task_version`** so `_v3` is obviously newer than `_v2`, no `FINAL_real` guessing.
3. **A second synced copy** in a cloud drive such as OneDrive (5 GB free), Google Drive (15 GB free), or iCloud Drive (5 GB free) so a dead USB stick cannot erase the only version. University-provided storage (institutional OneDrive or Google Workspace for Education) is often the safest second copy, because it has effectively large quotas and survives a lost personal device.

The improvement is not nicer wording. It is a structure another person, or future-you, can navigate without asking.

## Decision Rule

When you create or save any file, make three decisions before you click Save, in this order: where it belongs (folder), what it is plus its version (name), and how it is protected (backup).

A well-filed assignment should pass three quick tests:

1. **Location test:** Does this file live in its course/module/task leaf folder, not loose on the Desktop or in Downloads?
2. **Name test:** Does the name lead with an ISO date and say course, task, and version, so the newest copy is obvious without opening it?
3. **Backup test:** Is there a second synced copy (OneDrive, Google Drive, iCloud Drive, or your university's institutional storage) somewhere a single dead drive cannot erase? Free-tier quotas change frequently, so verify the current offering rather than trusting a remembered number.

If any test fails, the file is findable today only because you remember where it is, and that memory will not survive to week 14.

## Common Misreadings

The most common error is filing later. "I will organize at the end of the term" never happens, and by then the modified dates are scrambled and the context is gone. File at creation, when you still know what the file is.

A second error is over-nesting: ten folder levels deep is as hard to navigate as a flat pile. Three levels (course, module, task) is the sweet spot for a semester.

## Textbook Walkthrough

Apply the system to a concrete week. You start CAT 100 Module 7 and download three things: the assignment prompt, the rubric, and a dataset. Before doing anything else, create `Documents/CAT100/Module07-Productivity/` and drop all three inside, renamed: `2026-05-25_cat100_module7_prompt.pdf`, `2026-05-25_cat100_module7_rubric.pdf`, `2026-05-25_cat100_module7_data.xlsx`. Now every artifact for this module has a home.

As you draft, each save increments the version: `_v1`, `_v2`, `_v3`. You never overwrite the prompt or rubric, so the source-of-truth files stay clean. When you finish, the leaf folder holds the full story of the assignment in date order, and you upload the highest version number with zero ambiguity.

The walkthrough shows the payoff: the decision cost is a few seconds at creation, and the return is that retrieval, backup, and submission all become trivial.

## What Strong Reading Looks Like

A strong reader treats their own file system as something to audit, not just live in. Open your busiest course folder right now and ask: could a classmate find my latest draft in under thirty seconds? If the answer is no, the structure has failed even though every file is technically present.

A strong reader of file organization can answer four questions about any folder:

1. Which file is the newest version of this assignment, judged from names alone?
2. Where would a brand-new file for this task go, without thinking?
3. If this drive died right now, where is the second copy?
4. What naming or folder rule would prevent the last mistake I made?

## Stronger Artifact Standard

The artifact here is the folder structure itself, plus a short note explaining your naming convention. It is strong when a reader can reconstruct your filing logic from one screenshot: the tree shows course/module/task, the names show date/course/task/version, and the note states where the backup lives.

A useful note sounds like this: "I switched from a flat Desktop to a `CAT100/Module07/file-organization/` tree and renamed files as `date_course_task_version`. I rejected adding a separate `old_versions` folder because version numbers in the name already mark the newest file, and an extra folder would just hide history I might need."

## Transfer Case

Move the same system from school to an internship. The course/module/task tree becomes client/project/deliverable; the `date_course_task_version` name still applies; the OneDrive backup becomes the company's shared drive with its access rules. What changes is the backup constraint: at work, a personal cloud copy of company files may violate policy, so the "second copy" lives only where the employer allows. Recognizing that the structure transfers but the backup rule must adapt is the sign you understand the system rather than just one folder layout.
