## Why This Section Matters

This capstone section asks you to publish your workflow as a live web page, which means the abstract ideas from the rest of the chapter now have to survive contact with a real server. A page that looks fine on your laptop can return a 404, show a broken image, or fail to render a list once it is on the web, because publishing exposes three concrete requirements that local files hide: the homepage must be named exactly `index.html`, image paths must be relative (not pointing at your hard drive), and publishing must be turned on in the host's settings. This section teaches those mechanics using GitHub Pages.

The skill matters because "it works on my machine" is not the same as "it works for everyone." A published artifact is the strongest evidence of digital fluency precisely because a stranger's browser, with none of your local context, has to render it correctly.

## Learning Targets

- Name the homepage `index.html` so the site resolves at its root instead of returning a 404.
- Use relative image paths so images load for every visitor, not just on your computer.
- Enable publishing in the host's settings, since pushing files alone does not make a site live.
- Close every HTML tag so the browser renders the content as intended.

## Opening Case

A student finishes a workflow write-up, pushes the files to GitHub, and visits the site URL, only to see a 404. The HTML is perfect, but the file is named `home.html`, and a web server looks for `index.html` at the root by default (GitHub Pages documents that it looks for `index.html`, `index.md`, or `README.md` as the entry file; the same convention is Apache's `DirectoryIndex index.html` default). They rename it, and the page appears, but the chart is a broken-image icon because the `<img>` tag points at `C:/Users/student/Desktop/chart.png`, a path that exists only on their laptop. No visitor's browser can reach the student's Desktop.

These are not coding mistakes in the usual sense; the markup is valid. They are publishing mistakes: the page assumed a local context that does not exist on the web.

## Core Concept

Publishing a static site rests on three rules that local files let you ignore.

**The homepage name.** A web server, asked for a site's root, looks for a file named `index.html`. Any other name (`home.html`, `main.html`) leaves the root with nothing to serve, producing a 404. This is a convention, not a choice; the file must be named `index.html`.

**Relative versus absolute paths.** An absolute path like `C:/Users/you/chart.png` points to a specific location on your machine that no visitor can reach. A **relative path** like `./images/chart.png` points to a location relative to the HTML file itself, so it works wherever the site is hosted. The table makes the distinction concrete:

| Path style | Example | Works for visitors? |
| --- | --- | --- |
| Absolute local | `C:/Users/you/chart.png` | No, points to your hard drive |
| Absolute web | `https://site.com/img/chart.png` | Yes, but brittle if the site moves |
| Relative | `./images/chart.png` | Yes, travels with the files |

**Publishing must be enabled.** Pushing files to a repository stores them; it does not serve them. GitHub Pages requires you to set the source in Settings (branch and folder) before anything goes live; "Deploy from a branch" is the simplest source, while "GitHub Actions" is the modern alternative for sites that need a custom build. The files existing is necessary but not sufficient.

Underneath all three is one principle: a published page cannot rely on anything that lives only on your computer, including the file's local name, its disk paths, or your assumption that "saved" means "served." Plus, well-formed HTML (every tag closed) is what lets the browser render structure like lists at all.

## Worked Example

Here is a real workflow write-up published as a GitHub Pages site.

**The repo (note the homepage name and relative image path):**

```
my-workflow-site/
  index.html          <- must be index.html to serve at the site root
  images/
    audit-chart.png
```

**index.html:**

```html
<!DOCTYPE html>
<html>
  <head><title>My CAT 100 Workflow</title></head>
  <body>
    <h1>Weekly Workflow Audit</h1>
    <ul>
      <li>Log time per step</li>
      <li>Find the slowest frequent step</li>
      <li>Fix it, then measure again</li>
    </ul>
    <img src="./images/audit-chart.png" alt="Before and after times">
  </body>
</html>
```

**Publish:** in Settings > Pages, set Source = branch `main`, folder `/ (root)`. After a push, the site can take up to about 10 minutes to build and propagate, so a brief wait before checking the live URL is normal.

Three concrete decisions made it load:

1. **Homepage named `index.html`** so the site root resolves instead of returning 404.
2. **Relative image path `./images/audit-chart.png`** (not a `C:/Users/...` local path) so it works for every visitor.
3. **Pages source set in Settings**, because pushing files alone does not enable publishing, and every `<li>` and `<ul>` is closed so the list renders.

## Decision Rule

Before declaring a site published, ask three things in order: is the homepage named `index.html`, do all asset paths point to locations a stranger's browser can reach (relative, not local), and is publishing actually turned on in the host's settings.

A live site passes three checks:

1. **Root check:** Is the homepage named `index.html`, so the site root resolves instead of 404?
2. **Path check:** Do all images and assets use relative paths that load for any visitor?
3. **Publish check:** Is the Pages source enabled in Settings, so the pushed files are actually served?

If any check fails, the files exist but the site does not work for anyone but you.

## Common Misreadings

The most common misreading is "I pushed the files, so the site is live." Pushing stores the files; enabling Pages in Settings is what serves them. The two are separate steps.

A second misreading is testing only by opening `index.html` from your hard drive, where local absolute image paths happen to work. Always test the published URL in a fresh browser, because that is the only context that reveals a broken path or a wrong filename.

## Textbook Walkthrough

Apply the rules to add a second page, a resume, to the same site. You create `resume.html` alongside `index.html` and link to it from the homepage with `<a href="./resume.html">Resume</a>`, a relative link so it works on the live site. The new page embeds a headshot with `<img src="./images/headshot.jpg">`, again relative.

You push, then visit the live URL and click the link. If the resume 404s, the likely cause is a filename typo (`resume.htm` versus `resume.html`) or a missing push; if the headshot is broken, the path is wrong or the image was not committed. The walkthrough shows the same three rules governing every page you add: each must reach the others through relative links, each asset must use a relative path, and the whole thing only works once Pages is enabled and the files are actually pushed. Testing on the live URL, not the local file, is what catches the failures.

## What Strong Reading Looks Like

A strong reader never trusts a page until it has been opened from its public URL in a browser that has no access to their computer. "It works locally" is treated as untested, because local opening hides exactly the publishing errors that matter.

A strong reader of a published site can answer four questions:

1. Is the homepage named `index.html`, and does the root URL load it without a 404?
2. Does every image and link use a path a stranger's browser can resolve?
3. Is Pages actually enabled, and have the latest files been pushed?
4. Does the page render correctly in a fresh browser, not just when opened from disk?

## Stronger Artifact Standard

The artifact is the live site plus its repository structure. It is strong when a reader can open the public URL on a device that has never touched your files and see the page render fully, images and all, with a short note explaining the three publishing decisions.

A useful note sounds like this: "I renamed `home.html` to `index.html` so the root URL resolves, switched the chart from a `C:/Users/...` path to `./images/audit-chart.png` so it loads for visitors, and enabled Pages in Settings. I rejected linking the image from my Google Drive because a private-drive link would break for anyone not signed in as me."

## Transfer Case

Move from GitHub Pages to a different host, say a university web space or Netlify. The three rules transfer: a default homepage filename (often still `index.html`), relative asset paths, and an explicit publish or deploy step. What adapts is the publishing mechanism: one host reads from a Git branch, another from an uploaded folder, another from a deploy command. Recognizing that the `index.html` and relative-path rules are universal while the "turn on publishing" step is host-specific is what lets you ship a site anywhere, not just on the one platform you learned.
