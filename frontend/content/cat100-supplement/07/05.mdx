## Why This Section Matters

Automation is a force multiplier, and a force multiplier multiplies mistakes as readily as it multiplies good work. A rename rule, a bulk delete, a mail filter, or a find-and-replace applied to 200 items will execute a flawed pattern 200 times in a second, with no pause to let you notice. The thing that makes automation safe is not better luck; it is a habit of testing on a small sample first and keeping an undo path for actions the tool cannot reverse. This section teaches that habit: dry run, backup, then scale.

The stakes are concrete. A wrong rename pattern can corrupt every file name in a folder; a bad bulk delete can empty a drive past the point a recycle bin can recover. The safety check costs a minute; the missing safety check can cost a semester of work.

## Learning Targets

- Run any bulk operation on a small sample (a dry run) before applying it to everything.
- Create a backup or undo path before any action the tool cannot reverse.
- Confirm the sample result is correct before scaling, so the full run is verification, not a gamble.
- Distinguish reversible actions (safe to try) from irreversible ones (must be backed up first).

## Opening Case

A student wants to add a date prefix to 200 coursework files and writes a rename rule. The pattern has a subtle flaw: it prepends the date to a name that already starts with the date, but the student does not see this, because they run it on all 200 files at once. In one click, every file becomes `2026-05-28_2026-05-28_essay.docx`, and the rename tool offers no single-step undo. The error was small; the blast radius was the entire folder.

The fix is structural, not careful: test the rule on three copies first, confirm the output, then run it on the full set with a backup already in place.

## Core Concept

Automation safety rests on two ideas: limiting the blast radius and preserving reversibility.

**Blast radius** is how many items a single action affects. The danger of automation is that the blast radius equals the whole set, so one flawed rule damages everything at once. A **dry run** shrinks the blast radius to a tiny sample: copy three files into a test folder, run the rule there, and inspect the result. If the pattern is wrong, only three throwaway copies are affected, and you learn it for free.

**Reversibility** is whether you can get back to the prior state. Some actions are reversible (moving a file, which you can move back). Many automated actions are not: a permanent delete, an overwrite, or a rename with no built-in undo. For any irreversible action, you make a **backup** first, which manufactures an undo path the tool itself does not provide.

The procedure that follows from these ideas is fixed:

1. Copy a small sample into a test location.
2. Run the operation on the sample only.
3. Inspect the sample output against what you expected.
4. Back up the full set (the undo path).
5. Run on the full set, treating it as verification, not a first try.

The common error is collapsing this to a single step (run on everything and hope), which works until the day it does not, and that day is unrecoverable.

## Worked Example

Here is a real bulk action made safe with a dry run and an undo path.

**The task:** add a date prefix to 200 coursework files with a rename rule.

**Unsafe (run on everything at once):**

```
Rule:  rename *  ->  2026-05-28_*
Run on:  CAT100/ (all 200 files)
Result:  pattern was wrong; 200 files now read 2026-05-28_2026-05-28_essay.docx
```

One bad pattern just corrupted every file.

**Safe (dry run on copies, then full run with a backup):**

```
1. Copy 3 files into CAT100/_test/        (sample)
2. Run rule on _test/ only
   essay.docx        -> 2026-05-28_essay.docx     OK
   lab.docx          -> 2026-05-28_lab.docx        OK
3. Backup CAT100/ to OneDrive              (undo path)
4. Run rule on the full folder
```

Three safety checks did the work:

1. **Dry run on a small sample** caught the pattern before it touched all 200 files.
2. **A backup copy** in OneDrive gave an undo path for an action the tool cannot reverse.
3. **Confirm the result on the sample** before scaling, so the full run is verification, not a gamble.

## Decision Rule

Before running any operation on more than a handful of items, ask: can I test this on a small sample first, and if it goes wrong, can I undo it? If the answer to either is no, do not run it yet; create the test or the backup first.

A safe bulk operation passes three checks:

1. **Dry-run check:** Was the operation tested on a small sample and the output inspected before scaling?
2. **Reversibility check:** Is there a backup or undo path for any action the tool cannot itself reverse?
3. **Confirm-before-scale check:** Did the sample produce exactly the expected result before the full run?

If you cannot point to the test sample and the backup, the full run is a gamble, not a safe operation.

## Common Misreadings

The most common misreading is "I read the rule carefully, so it is fine." Careful reading does not catch subtle pattern errors; a dry run does. Inspection of actual output beats inspection of the rule.

A second misreading is assuming the recycle bin or an app's undo button is a sufficient safety net. Many bulk tools bypass the recycle bin or offer no undo at all, which is exactly why you make your own backup before running.

**In real tools (2026).** Each safeguard has a concrete home in current tools. For bulk renames, Windows PowerToys PowerRename shows a live preview of every new name before you commit (a built-in dry run) and can undo a completed rename; macOS Finder's batch Rename previews the result as well. For undo paths, OneDrive and Google Drive both keep version history (around 30 days of file restores on personal accounts). For email rules, Outlook and Gmail filters let you review what a rule matched and adjust it. These interfaces change, so the live tool, not a remembered screenshot, is the source of truth.

## Textbook Walkthrough

Apply this to a bulk delete, the most dangerous common operation. You want to clear out old downloads: delete every file in `Downloads/` older than 90 days. The risk is that an important PDF you saved months ago also matches "older than 90 days." Run the dry run first by sorting the folder by date and listing what the rule would catch, without deleting; scan that list and you spot the syllabus you meant to keep.

Now adjust the rule (exclude PDFs, or move-to-archive instead of delete), back up `Downloads/` to the cloud as the undo path, and only then run the deletion. The walkthrough shows that the dry run is not a formality: it surfaces the false matches (files that fit the rule but should not be touched) that a careful reading of the rule would miss, and the backup covers the case where you miss one anyway.

## What Strong Reading Looks Like

A strong reader treats every automated action as guilty until proven safe, asking what the worst case is before running it. They mentally separate "this is reversible" from "this is permanent" and apply heavier safeguards to the permanent ones.

A strong reader of an automated operation can answer four questions:

1. How many items will this affect, and what is the worst thing that happens if the rule is wrong?
2. Did I test it on a sample and inspect the actual output, not just the rule?
3. Is this action reversible, and if not, where is the backup?
4. Which items match the rule but should not be touched, and how did I catch them?

## Stronger Artifact Standard

The artifact is a record of a bulk operation done safely: the rule, the dry-run sample and its output, the backup location, and the full-run result. It is strong when a reader can see that the operation was tested and reversible before it ran at scale.

A useful note sounds like this: "I tested the rename rule on three copies first and caught a doubled-prefix bug; I fixed it, backed up the folder to OneDrive, then ran the full rename. I rejected running directly on the live folder even though it was faster, because the tool has no undo and a wrong pattern would have hit all 200 files."

## Transfer Case

**When the actor is an AI agent.** The same three checks apply when an AI assistant or agent proposes a bulk action (delete, move, send, overwrite), plus one more gate: require a dry-run preview of exactly what it would do before it acts, never grant an agent irreversible permissions without a current backup, and log the proposal in your accepted/modified/rejected note. A rejected bulk-delete suggestion, with the reason, is exactly the kind of entry that proves the judgment stayed with you.

Move the safety habit from file renaming to a spreadsheet find-and-replace. Dry run, backup, and confirm-before-scale all transfer, but the test method changes: instead of copying files, you duplicate the sheet (or save a copy of the workbook) and run the replace there first, watching for unintended matches like replacing "1" inside "10" or "100." The procedure is identical; what adapts is how you build the sample (a copied sheet rather than copied files) and what false matches to watch for.
