# Evidence Collection

![Evidence Collection textbook visual](/course-art/deep-exemplars/cat100-supplement/04-07-evidence-collection.png)

## Why This Section Matters

A folder full of files named `Untitled.docx` and `final final v2.docx` forces a reviewer to open everything and guess what each file proves. That guessing is where credit gets lost: a reviewer who cannot find the evidence for a claim treats the claim as unsupported. This section teaches you to assemble evidence as a named set of files plus a manifest that maps each file to the exact claim it backs, so anyone can open one file and immediately see what it demonstrates.

The discipline here is file management as argument. Each claim you want credit for should have exactly one file behind it, and each file should support exactly one claim. A claim with no file is unsupported; a file with no claim is clutter. The manifest makes both gaps visible, which is what turns a pile of work into a reviewable case.

## Opening Case

A student finishes Module 4 and turns in a folder: `Untitled.docx`, `Screenshot 2026-05-18.png`, `final final v2.docx`, `notes.txt`. Every file might contain good work, but the reviewer cannot tell what any of it proves without opening all four and reading them. The screenshot proves nothing on its own. Two of the documents have nearly identical names, so the reviewer does not even know which is current.

The same work, organized, becomes a case: `01_persona.txt`, `02_factcheck_table.xlsx`, `03_parent_email_before_after.docx`, `04_decision_log.xlsx`, each name stating its content, plus a manifest saying what claim each file backs. Now the reviewer opens the table named `02_factcheck` and confirms in seconds that three AI claims were verified. The work did not change; the way it was made findable did.

## Core Concept

Evidence collection has two artifacts working together: named files and a manifest that maps each file to a claim.

| Move | Bad version | Good version |
|------|-------------|--------------|
| File naming | `Untitled.docx`, `v2 final.docx` | `01_persona.txt`, name states the content |
| Claim mapping | reviewer infers what each file is for | manifest row: file to the exact claim it proves |
| Coverage | some claims have no file | every claim has exactly one file behind it |
| Pruning | screenshots and stray notes pad the folder | files that prove nothing are cut |

The key idea is a one-to-one mapping between claims and files. Coverage means every claim you want credit for has a file; pruning means every file earns its place by backing a claim. A numbered prefix (`01_`, `02_`) gives the set a reading order, so the reviewer can follow your case from start to finish rather than opening files at random.

A manifest is just a small table, often kept as a `README.txt` or a sheet, with two columns: the file name and the claim it proves. It is the index to your evidence. Without it, the reviewer reconstructs your argument by guessing; with it, they verify it by reading.

## Worked Example

Evidence collection is concrete file management: you build a manifest that maps each saved file to the exact claim it proves. A freshman assembles a folder and a manifest table so a reviewer can open any file and see what it supports. Follow the steps.

Step 1. Here is the messy first folder a student turns in:

```text
module4/
  Untitled.docx
  Screenshot 2026-05-18.png
  final final v2.docx
  notes.txt
```

Nothing names what it proves, so a reviewer has to open every file and guess.

Step 2. Rename the files so the name states the content, then build a manifest mapping file to claim:

| Renamed file | Claim it proves |
|--------------|-----------------|
| `01_persona.txt` | I wrote a four-field teacher persona |
| `02_factcheck_table.xlsx` | I verified 3 AI claims and rejected the fabricated 90% statistic |
| `03_parent_email_before_after.docx` | I revised a vague email into a concrete, dated one |
| `04_decision_log.xlsx` | I overrode the AI twice and accepted once, with reasons |

Step 3. Check coverage. Each claim you want credit for now has exactly one named file behind it. A claim with no file is unsupported; a file with no claim is clutter and gets cut.

Step 4. Log the one rejected item. You had a fifth file, `Screenshot 2026-05-18.png`, but it proved nothing on its own, so you cut it rather than pad the folder. The renamed files plus the manifest are the evidence: a reviewer can open any row and confirm the claim without asking you.

## Decision Rule

Map every claim to one named file and cut every file that maps to no claim. An evidence set is reviewable only when the manifest lets someone confirm each claim by opening a single file.

Run these three checks before you submit:

1. **Coverage check:** Does every claim you want credit for have exactly one file behind it?
2. **Naming check:** Does each file name state its content, so a reviewer knows what it is before opening it?
3. **Pruning check:** Does every file in the folder back a claim, or are there screenshots and stray notes proving nothing?

If a file does not appear in your manifest, it is clutter. If a claim has no file, it is unsupported. Fix both before you call the set complete.

## Common Misreadings

The first misreading is that more files mean stronger evidence. A folder of twelve files where four are duplicates and three are unlabeled screenshots is weaker than four named files that each prove a claim. Padding lowers the signal a reviewer can find.

The second misreading is that a screenshot is automatically evidence. A screenshot proves something only if it is named and mapped to a claim ("`05_published_page.png`, proves the page is live at the URL"). An unlabeled `Screenshot 2026-05-18.png` proves nothing because the reviewer cannot tell what they are looking at or why.

## Textbook Walkthrough

Apply the manifest method when a claim turns out to have no file. You list the claims you want credit for and find one says "I revised my persona after testing it," but no file shows the before and after. The coverage check fails for that claim. You have two honest options: create the missing evidence by saving both `persona_v1.txt` and `persona_v2.txt`, or drop the claim because you cannot support it.

Suppose you saved only the final persona and overwrote the draft. Then the claim "I revised it" is unsupported, and the right move is to drop it rather than assert it. The walkthrough shows the manifest doing real work: it does not just organize evidence you have, it exposes claims you cannot back, so you stop yourself from asserting something a reviewer would not be able to confirm. That is the integrity check built into the coverage step.

## What Strong Reading Looks Like

As you read, keep a two-column note: **claim** on the left, **the file that proves it** on the right. A strong reader does not say "the folder is organized"; they say "the claim about verifying AI advice is backed by `02_factcheck_table.xlsx`, which I could open and confirm." The named file is what makes the claim checkable.

A strong reader of Evidence Collection can answer four questions:

1. Does every claim in the manifest map to exactly one file?
2. Does every file in the folder appear in the manifest, or is something padding it?
3. Which claim, if any, has no file behind it and should be dropped or supported?
4. Could a reviewer confirm each claim by opening a single named file, without asking you?

## Stronger Artifact Standard

The artifact is strong when a reviewer can read the manifest and confirm each claim by opening one named file, with no orphan files and no unsupported claims. Keep the manifest as a `README.txt` or sheet at the top of the folder so it is the first thing a reviewer sees.

A useful closing note for the artifact would read: "Each of my four claims maps to one named file, and the manifest lets a reviewer open any row and confirm it. I cut `Screenshot 2026-05-18.png` because it proved nothing on its own and would have padded the folder without adding a verifiable claim." That states the one-to-one mapping and defends one pruning decision.

## Transfer Case

Move the manifest from a course folder to a job portfolio on GitHub Pages. The same logic governs: each portfolio item should map to a claim a hiring reviewer cares about ("this repo shows I can build a working web page"), and items that back no claim get cut. But the audience shifts the standard for what counts as a claim. A reviewer for credit cares that you completed the module; a hiring reviewer cares that you can do the skill again. So the manifest entries reframe from "I did the assignment" to "this artifact demonstrates a transferable skill." The mapping discipline transfers; the claims you choose to support change with who is reading.
