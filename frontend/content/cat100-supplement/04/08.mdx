## Why This Section Matters

The studio is where your Module 4 work stops being files on your laptop and becomes a real web page anyone can open by URL. Publishing to GitHub Pages means writing plain HTML, pushing it to a repository, and letting GitHub serve it as a live site. The skill that matters is not making it pretty; it is making it correct, so the page has a real title, real headings, and links that actually reach your evidence files. A page that "looks fine" in the browser but has no `<title>` and a dead link fails the moment a reviewer tries to use it.

This matters because a public page is the most exposed artifact in the course. There is no instructor standing next to it to explain what you meant. The markup has to carry the meaning on its own: the structure tags tell the browser and any assistive technology what each piece is, and the working link is what lets the evidence behind the page be reached. Getting the HTML right is what makes the publication trustworthy.

## Opening Case

A student's first `index.html` is three lines: an `<html>` tag, the bare text "my ai project," and an empty `<a>link</a>`. It loads without error, so the student assumes it is done. But the browser tab shows the file path instead of a name, because there is no `<title>`. The heading is not a heading, just loose text, so a screen reader announces nothing structural. The link goes nowhere, because the `<a>` has no `href`.

The page that looks finished is actually broken in every way that counts. A correct version adds a `<title>` in the head, marks the heading with `<h1>`, and gives the link a real `href` pointing to an evidence file. After pushing to GitHub Pages, the student opens the live URL and confirms the title shows in the tab, the heading renders large, and the link downloads the real file.

## Core Concept

A publishable page is checked against a small set of structural requirements, each tied to a specific HTML element.

| Requirement | Element | Why it matters |
|-------------|---------|----------------|
| Page title | `<title>` inside `<head>` | shows in the browser tab, search results, and bookmarks |
| Document type | `<!DOCTYPE html>` | tells the browser to use standard rendering |
| Real heading | `<h1>` | gives the page a structural top level for readers and assistive tech |
| Working link | `<a href="file">` | actually reaches the evidence; an empty `href` is a dead end |

The distinction the studio enforces is structure versus appearance. A heading is not "big text"; it is an `<h1>` element that means "this is the main heading," which the browser then happens to render large. Using a real `<h1>` instead of bare bold text is what lets a screen reader, a search engine, and a future editor understand the page. This is the WCAG idea of semantic markup: the tag carries the meaning, not the visual size.

GitHub Pages serves whatever is in the published branch, so "publishing" is just pushing your `index.html` and opening the live URL. The verification step is non-negotiable: you load the actual URL, not the local file, because a link that works on your disk can break once the site is served from a different root.

## Worked Example

The Module 4 studio is where you publish the work as a real web page on GitHub Pages, so the dialogue artifact and its evidence are public and linkable. A freshman writes plain HTML, then checks it against a publish checklist. Follow the steps.

Step 1. A student's first `index.html` looks like this:

```html
<html>
my ai project
<a>link</a>
</html>
```

It loads, but it has no title, the heading is not a heading, and the link points nowhere.

Step 2. Run the four-item publish checklist and mark each PASS or FAIL:

| Item | Requirement | Draft above |
|------|-------------|-------------|
| Page title | `<title>` in the head | FAIL (no head, no title) |
| Real heading | content uses `<h1>` | FAIL (bare text) |
| Working link | `<a href="...">` points to a file | FAIL (empty href) |
| One artifact shown | the dialogue or table is embedded | FAIL (nothing shown) |

Step 3. Rewrite the markup so every item passes:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <title>CAT 100 Module 4: AI Dialogue Studio</title>
  </head>
  <body>
    <h1>My Teacher-AI Dialogue Project</h1>
    <p>This page links my four Module 4 artifacts.</p>
    <a href="02_factcheck_table.xlsx">Fact-check table (3 claims verified)</a>
  </body>
</html>
```

Step 4. Verify the publish. After pushing to the `gh-pages` branch, you open the live URL and confirm the title shows in the browser tab, the heading renders large, and the link downloads the real file. You also rejected the AI's suggestion to add a flashy background color, because the publish checklist values a working link over decoration. The before/after markup plus the passing checklist is the evidence: a reader can view source and see exactly what you fixed.

Publish for correctness first and appearance last, and verify on the live URL, not the local file. A page is ready only when the title, heading, and links pass on the served site.

Run these three checks after you push:

1. **Tab check:** Does the browser tab show your `<title>` text rather than a file path?
2. **Structure check:** Is the main heading a real `<h1>`, so it carries meaning and not just size?
3. **Link check:** Does each link, clicked on the live URL, actually reach the evidence file it names?

If a link works locally but 404s on the live site, the path is wrong relative to the served root. Fix the `href`, not the local copy.

## Common Misreadings

The first misreading is "if it renders, it is correct." A page with no `<title>` and bare text headings renders fine to a sighted user with a fast eye, but it fails for search engines, bookmarks, and screen readers. Rendering is the floor, not the standard.

The second misreading is reaching for styling before structure. Students often ask the AI for colors and fonts while the link is still dead. Decoration on a broken page is wasted effort; the checklist puts a working link above a background color on purpose, because a reachable artifact is the point of publishing.

## Textbook Walkthrough

Apply the publish checklist to a link that breaks only on the live site. Locally, your page links to `02_factcheck_table.xlsx` and it opens, because the file sits next to `index.html` on your disk. You push to GitHub Pages, open the live URL, click the link, and get a 404. The structure and title pass; the link check fails. The cause is almost always a path mismatch: the file was not committed, or it lives in a subfolder the `href` does not name.

You fix it by committing the file to the same folder the page expects, or by correcting the `href` to the real served path, then push again and re-test on the live URL. The walkthrough makes the verification step concrete: the only test that counts is clicking the link on the served site, because the served root differs from your laptop's folder. A page that passes locally and fails live has not actually been published in a usable state.

## What Strong Reading Looks Like

As you read, keep a two-column note: **requirement** on the left, **the element that satisfies it** on the right. A strong reader does not say "the page looks done"; they say "the heading passes because it uses `<h1>`, not because the text is large." Pointing to the element is what proves the requirement is met.

A strong reader of Module 4 Dialogue Studio can answer four questions:

1. Which element provides the page title, and does it show in the tab?
2. Is the main heading a real `<h1>`, or just styled text pretending to be one?
3. Does each link reach its file when clicked on the live URL, not the local copy?
4. What did you fix for correctness before touching appearance?

## Stronger Artifact Standard

The artifact is strong when a reviewer can open the live URL, see the title in the tab, and click a link that reaches a real evidence file, then view source and see correct structural markup. Keep the before and after HTML so the reviewer can see which tags you added and why.

A useful closing note for the artifact would read: "I added a `<title>` and an `<h1>` because the first version had neither, so the tab showed a file path and screen readers found no heading. I rejected the AI's suggestion to add a flashy background color because the checklist values a working link over decoration, and the link was still the part that mattered." That ties each fix to a failed requirement and defends one rejected suggestion.

## Transfer Case

Move the publishing skill from a course project page to a personal resume site, which CAT 100 also asks you to build. The same correctness checklist governs: a `<title>` so the tab and search results name you, real `<h1>` and `<h2>` headings so the structure is readable by assistive tech and recruiters' tools, and working links to your projects rather than dead ones. But the stakes raise the bar on verification, because a broken link on a resume site is seen by an employer, not a grader. The structure tags and the live-URL test transfer directly; what changes is that the audience now includes people who will not give you a second chance to fix a 404.
