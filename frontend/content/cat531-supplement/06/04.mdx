# Classroom Implementation Plan

![Classroom Implementation Plan textbook visual](/course-art/deep-exemplars/cat531-supplement/06-04-classroom-implementation-plan.png)

## Why This Section Matters

The gap between a good idea and a working classroom is paved with everything the idea forgot: the consent form that never went home, the day the wifi dropped, the student whose device was dead, the success metric no one defined until it was too late to measure. An implementation plan is the document that closes that gap by anticipating failure before it happens. Deciding to adopt a tool is a judgment; making it survive a real week of teaching is engineering, and the two require different work.

A defensible plan does not describe the happy path where everything works. It sequences the prerequisites in the right order, names who owns each step, specifies a fallback for every dependency that can fail, defines success in terms you could actually measure, and states the condition under which you would stop. The Design Tension Studio map records the value decision; the implementation plan is where that decision either holds up or quietly collapses under operational reality.

## Opening Case

A teacher plans to launch an AI math-practice tool: "Week 1, students log in and complete the adaptive module during class." It reads clean until a mentor asks three questions. When does parental consent clear, given the tool collects student responses? What happens the day the wifi fails mid-session? What counts as success, and how will you know if a subgroup is falling behind rather than catching up? The original plan answers none of these, which means it is not a plan; it is a hope with a calendar attached.

The fix is not more enthusiasm but more anticipation. Every dependency the plan relies on (consent, connectivity, devices, a working definition of success) is a place the plan can break, and a real implementation plan treats each one as a failure mode to design around in advance.

## Core Concept

A classroom implementation plan is an operational design with five load-bearing components:

- **Gated prerequisites.** Some steps must clear before others can legally or pedagogically begin. Consent must be on file before student data is collected; a plan that schedules the activity in week 2 and consent in week 3 has inverted a gate and exposed the teacher.
- **Named ownership.** Every step has a person responsible. "The tech will be ready" is not a plan; "the co-teacher confirms the device cart by Monday 8am" is.
- **Fallbacks for each dependency.** For every thing that can fail (network, device, login), the plan names what students do instead, so a failure becomes a detour rather than a lost period.
- **Evaluable success.** "All students complete the module" measures compliance, not learning. "Median student gains one proficiency level and no subgroup falls further behind by the unit test" measures the thing you actually care about.
- **A stop condition.** A plan that cannot fail cannot be evaluated. State in advance the signal (for example, a widening subgroup gap at the week-3 check) that would make you pause or revert.

The course anchors keep the plan honest. [TPACK](https://en.wikipedia.org/wiki/Technological_pedagogical_content_knowledge) checks that the activity serves the learning target rather than just keeping students busy on a tool; critical edtech studies forces the fallback design by asking who the happy-path plan would strand; datafication forces the consent gate by asking what student data flows and when. A plan missing a gate, an owner, a fallback, a metric, or a stop condition is not yet enactable, however polished it looks.

### Worked Example: An Annotated Rollout Decision

Follow a teacher turning a tool idea into an enactable classroom implementation plan for an AI math-practice tool.

1. **Before (happy path).** Draft plan: "Week 1, students log in and complete the adaptive module during class." A mentor annotates: "What about consent, devices, and the day the wifi drops?"
2. **Sequence the gates.** Reorder: parental-consent forms go out and clear in week 1; the tool is introduced in week 2, after consent is on file. The earlier draft had consent in week 3, after the activity that needed it.
3. **Plan the failure modes.** Add: if the tool is down, students use the printed practice set; if a student has no device, they pair on a class Chromebook. Owner named for each: teacher confirms wifi, co-teacher manages the device cart.
4. **Define evaluable success (after).** Replace "all students complete the module" with "median student gains one proficiency level and no subgroup falls further behind by the unit test."
5. **Stop condition.** If the subgroup gap widens at the week-3 check, pause the tool and revert to small-group instruction.

The before assumes everything works; the after names gates, owners, fallbacks, and a stop condition, so a colleague could run it.

## Decision Rule

Plan for the failure before you plan for the feature. For every dependency the activity relies on, write the fallback first; only a plan that survives its own broken parts is enactable. If you cannot state what students do when the tool is down, you do not yet have a plan you can run on a real Tuesday.

Check any plan against three questions:

1. **Sequence check:** Is every prerequisite (especially consent and access) gated to clear before the step that needs it?
2. **Fallback check:** Does every dependency that can fail have a named alternative and a named owner?
3. **Evaluation check:** Is success defined as a measurable learning outcome, and is there a stated stop condition?

If any answer is missing, the plan describes a hope, not an implementation.

## Common Misreadings

The most common error is the happy-path plan: a clean sequence that assumes consent, connectivity, devices, and engagement all arrive on schedule. Such plans look complete and fail on contact with the first dropped connection. A related error is defining success as completion ("everyone finished the module"), which a class can satisfy while learning nothing and while a subgroup quietly falls behind.

The subtlest misreading is omitting a stop condition. A teacher who has not decided in advance what would make them halt will, under sunk-cost pressure, keep running a tool that is widening a gap because stopping feels like admitting failure. Naming the stop condition before launch is what makes the decision to halt a professional judgment rather than a defeat.

## Textbook Walkthrough

Take a plan to use an AI discussion-summarizer in a history seminar. The happy-path draft: "Students discuss in small groups; the tool summarizes each group's key points for the whole-class debrief." Now engineer it. Gate the consent: the tool ingests student speech, so consent and a no-retention setting must clear before any recording. Name owners: the teacher verifies the no-retention setting; a student facilitator in each group confirms recording started.

Build the fallbacks: if the summarizer fails, each group's recorder reads three bullet points aloud, so the debrief proceeds without the tool. Define success not as "summaries were generated" but as "the whole-class debrief surfaced at least one cross-group connection students had not made in their own groups," which is the actual pedagogical purpose. Set the stop condition: if the summaries flatten distinct group arguments into the same generic points (a known failure of summarizers), drop the tool and have groups report directly. The walkthrough turns an appealing idea into something a substitute teacher could run, including on the day the tool misbehaves.

## What Strong Reading Looks Like

As you read a plan, hunt for its hidden assumptions: every "students will log in," "the tool will be ready," "all students complete" conceals a dependency that can fail. Write each assumption in the margin and ask what the plan does when it breaks. The unanswered ones are the plan's real weaknesses. By the end of CAT 531 06.04 you should be able to read any rollout plan and immediately name its weakest dependency and its missing fallback.

A strong reader of an implementation plan can answer four questions:

1. What must be true before each step, and is that prerequisite gated correctly?
2. For each dependency, what is the named fallback and who owns it?
3. How is success measured, and would the metric catch a widening subgroup gap?
4. What signal would make the teacher stop, and was it set before launch?

## Stronger Artifact Standard

A plan is strong when a colleague who has never seen your classroom could run it, including on the day a dependency fails, because the gates, owners, fallbacks, metric, and stop condition are all explicit. Formatting is the last layer; the load-bearing layers are the failure-mode design and the evaluable success criterion. If a step lacks a fallback, mark it and ask BigAL to compare a happy-path step with a failure-aware version rather than to "tighten the timeline."

A useful closing line would read: "I added the printed fallback and the pairing rule because the original plan assumed every student had a working device on every day, and the equity decision in my tension map is meaningless if the rollout quietly strands the students it was meant to protect."

## Transfer Case

Move the plan from a one-teacher classroom to a whole-grade rollout coordinated across five teachers. The pedagogical activity may be identical, but the implementation changes shape: ownership now requires a named coordinator rather than "the teacher," consent must be tracked across five rosters, and the stop condition needs a shared trigger so one teacher does not keep running a tool the data says to pause. If you understood implementation as failure-mode engineering, you scale the gates, owners, and fallbacks to the new coordination problem. If you only memorized your single-classroom timeline, the plan will break at exactly the seams between teachers that the original never had to consider.
