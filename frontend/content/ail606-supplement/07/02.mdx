# Evidence-Centered Design for Prototypes

![Evidence-Centered Design for Prototypes textbook visual](/course-art/deep-exemplars/ail606-supplement/07-02-evidence-centered-design-for-prototypes.png)

## Why This Section Matters

A prototype screen can look finished while quietly failing the one job that justifies it: producing evidence that a learner can do what you claim. Evidence-Centered Design (ECD), articulated by Mislevy and colleagues, gives you a discipline for closing the gap between what you assert and what your screens can actually show. Instead of building tasks and then guessing what they measure, ECD makes you reason backward from the claim to the evidence to the task. For a learning designer, the README traceability matrix is where that backward chain becomes inspectable: every screen must trace to an observable, and every observable must trace to a knowledge claim.

This section matters because misalignment is invisible until someone audits it. A drag-the-label task feels like it measures interpretation; on inspection it may only measure whether the learner can read labels. ECD is the tool that surfaces that mismatch before a reviewer, or a real learner, does.

## Learning Targets

- State the three ECD layers used here: claim (what the learner knows or can do), evidence (the observable that would reveal it), task (the screen that elicits the observable).
- Audit a traceability matrix row for the two classic failures: an unobservable evidence cell and a task that cannot elicit the named observable.
- Rewrite an internal-state evidence cell ("feels confident") as a scorable behavior.
- Reject task features that produce data unrelated to the claim.

## Opening Case

A teammate shows you a slick prototype: a drag-the-label screen where learners drag terms onto a residual plot. The matrix row reads: claim, "learner can interpret a residual plot"; evidence, "learner feels confident about the plot"; task, "drag-the-label screen." Every cell is filled, so it looks complete. But the evidence is a feeling no screen can observe, and even if it could, dragging a label onto a plot demonstrates label placement, not interpretation. The screen is polished and the row is wrong. ECD exists to catch exactly this.

## Core Concept

Evidence-Centered Design treats assessment, and by extension any prototype that claims to teach or measure, as an argument with three linked layers:

| Layer | Question it answers | Failure mode |
| --- | --- | --- |
| Claim (student model) | What knowledge or skill are we asserting? | Vague or unmeasurable target |
| Evidence (evidence model) | What observable behavior would reveal that knowledge? | Internal state instead of an action |
| Task (task model) | What situation forces the learner to produce the observable? | Task elicits a different behavior than the one named |

The argument is only valid when the layers connect in both directions: the task must elicit the observable, and the observable must license the claim. A clean screen with a broken link is worse than an ugly screen with an intact one, because the clean screen invites false confidence.

The course anchors sharpen each layer. **Mayer's principles** inform the task layer: a task that buries the observable behavior under extraneous decoration raises load and contaminates the evidence. **Cognitive load theory** warns that a struggling learner may fail a task for load reasons unrelated to the claim, so a high-load task produces ambiguous evidence. **UDL learner variability** pushes you to ask whether the task elicits the observable for all intended learners or only for those who happen to match the interface's assumptions; a single task may under-represent the claim for some.

## Worked Example

Watch one matrix row move from misaligned to defensible.

**Before (one matrix row, as first drafted):**

| Claim | Evidence | Task screen |
| --- | --- | --- |
| Learner can interpret a residual plot | Learner feels confident about the plot | Drag-the-label screen |

1. The evidence cell holds a feeling, which no screen can observe or score.
2. The task elicits label placement, not interpretation, so it cannot supply evidence for this claim even in principle.
3. Both backward links are broken: task does not yield the observable, observable does not license the claim.

**After (same claim, realigned row):**

| Claim | Evidence | Task screen |
| --- | --- | --- |
| Learner can interpret a residual plot | Learner selects the correct diagnosis (e.g., "non-constant variance") for three plotted patterns | Diagnosis-selection screen showing three residual plots |

Now the chain holds: the diagnosis-selection task forces the learner to produce a scorable choice, the choice is an observable, and a correct diagnosis on varied patterns licenses the interpretation claim. A reviewer can audit the row without my narration.

One rejected suggestion: adding a "How confident are you?" prompt to the screen. I declined because confidence is not evidence of interpretation; it would add a data column the claim does not need and could tempt a later analyst to treat self-report as competence.

## Decision Rule

Build every row backward, claim first, then evidence, then task, and accept the row only when both links survive an audit:

1. **Observable check:** Is the evidence cell a behavior you could score from a screen recording, with no mind-reading? If it names a feeling or an internal state, rewrite it.
2. **Elicitation check:** Does the task actually force the learner to produce that observable, or could a learner pass the task by some unrelated route? If the latter, the task is invalid for the claim.
3. **Relevance check:** Does any data the task collects fail to support the claim? Drop or quarantine it so it cannot masquerade as evidence.

A row that fails any check is not "almost done"; it is producing the wrong evidence, which is worse than producing none.

## Common Misreadings

The most common misreading equates a more attractive task with a more valid one. Visual polish does not repair a broken elicitation link; a beautiful drag task still cannot measure interpretation. A second misreading treats "the learner completed the task" as evidence for the claim, when completion can be reached by guessing, by interface familiarity, or by a route that bypasses the target skill. ECD asks not whether the task was finished but whether finishing it required the claimed competence.

## Textbook Walkthrough

Apply ECD to a writing prototype. The claim is "learner can write a testable hypothesis." A first draft task is a multiple-choice screen asking which of four hypotheses is best. Audit it: the observable in that task is recognition, not production, so it cannot license a *writing* claim; a learner could recognize a good hypothesis without being able to write one. The fix is a task-layer change, not a polish change: replace recognition with construction. The revised task gives a scenario and asks the learner to type a hypothesis, with the observable defined as "the typed statement names a manipulation, a measure, and a comparison." Now the task elicits production, the observable is scorable against a rubric, and the chain to the claim is intact. The matrix made the recognition/production mismatch visible before any learner saw the screen.

## What Strong Reading Looks Like

Read each row as an argument and try to break it. In the left column write the claim; in the right column write the single way a learner could satisfy the task *without* having the claimed skill. If you can find such a route, the row is invalid and the task layer needs work. A strong reader of an ECD matrix does not check whether cells are filled; they check whether the easiest path through the task happens to require the competence the claim asserts. When no shortcut exists, the evidence is trustworthy.

## Stronger Artifact Standard

The traceability matrix is strong when every row survives the elicitation audit and when the README states, for at least one row, the alternative route a learner could have taken and how the task design forecloses it. Polish (typography, color, layout) belongs only after the three links hold. If a link is missing, annotate the cell and request a targeted comparison of a valid versus invalid task for that claim, rather than a general explanation of ECD.

## Transfer Case

Carry ECD into a setting where you inherit someone else's prototype and cannot rebuild the tasks. The matrix still earns its place: by reverse-engineering each screen into the claim-evidence-task layers, you can label which existing screens produce trustworthy evidence and which are decorative. That triage lets you spend a limited revision budget on the rows whose links are broken, rather than uniformly polishing screens that already work. The discipline transfers because it is about the logic of the evidence argument, not about who built the screens.
