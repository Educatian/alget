## Why This Section Matters

Learner reflections are abundant and tempting to use as evidence, but in their raw form most are unusable: "I liked the lesson and learned a lot" names no feature, no behavior, and no consequence a designer could act on. Treating reflection as data means subjecting it to the same discipline you would apply to any qualitative source: select an analytic excerpt, apply a defined code, and tie the code to a design decision, while staying honest that self-report measures perception, not measured learning. The move converts a vague compliment into a finding that can drive a specific revision.

This matters because reflection is often the only "outcome" data a small design study has, and how you treat it determines whether it is evidence or decoration. A coded, excerpt-grounded reflection can justify a screen change; an uncoded global impression can justify nothing, no matter how positive it sounds.

## Learning Targets

- Distinguish a global impression (uncodeable) from an analytic excerpt that names a feature and a learner action.
- Apply a defined code to an excerpt and link the code to a specific design decision.
- Keep the inference modest: treat reflection as evidence of perceived experience, not as a measured learning gain, and pair it with a planned check.
- Reject coding that reads competence into a reaction.

## Opening Case

A learner writes: "I really liked the lesson and felt like I learned a lot. Great experience." It is warm, and it is worthless as design evidence. There is no feature to revise, no behavior to observe, and no way to confirm the perceived learning actually occurred. Treated as a finding, this text would let a designer claim success while changing nothing. The work of this section is to refuse that shortcut: to look for the part of any reflection (if any) that names a concrete feature and a concrete action, code it, and let only that drive a decision.

## Core Concept

Reflection becomes data through three disciplined moves, each guarding against a different error:

- **Excerpt selection:** choose the span of text that names a design feature and a learner action, and set aside global praise or blame. The unit of analysis is the codeable claim, not the whole paragraph.
- **Code application:** assign a defined code whose meaning is stated in advance, so that the same code would be applied the same way by another reader. A code like "redundancy-noticed (narration duplicates on-screen text)" has a clear inclusion rule; a code like "positive" does not.
- **Decision linkage:** connect the coded excerpt to one design change you can recheck. A code that changes nothing is a category, not evidence.

Throughout, the inference stays bounded: a reflection is self-report about *perceived* experience. It can tell you a learner noticed redundancy and changed how they read; it cannot tell you their recall improved. Honest practice pairs the reflection-based decision with a planned objective check.

The course anchors give the codes their meaning. **Cognitive load theory** supplies a vocabulary of mechanisms (a learner who "stopped reading and just listened" is describing the redundancy effect, a recognized source of extraneous load), which lets you name *why* a feature mattered. **Mayer's redundancy principle** turns that observation into a defensible revision (remove duplicated on-screen text where narration carries the content). **UDL learner variability** cautions that one learner's coded experience is not the population's; a redundancy code from a strong reader may not generalize to a learner who relies on the on-screen text, so the revision is provisional and checked across learners.

## Worked Example

Trace one reflection from unusable description to a coded data point that drives a decision.

**Before (raw learner reflection, treated as a finding):**

> "I really liked the lesson and felt like I learned a lot. Great experience."

1. This is global praise with no feature, behavior, or consequence, so it cannot be coded or acted on.
2. There is no span of text that names a design element a revision could target.
3. "Felt like I learned a lot" is perceived learning, not a measured gain.

**After (coded excerpt with design decision):**

> Excerpt: "When the narration and the on-screen text repeated each other, I stopped reading and just listened, so I missed the labels."
> Code applied: Redundancy-noticed (narration duplicates on-screen text).
> Design decision: remove the duplicated on-screen text on that frame; recheck whether label recall improves.

The revised version turns reflection into data: a defined code grounded in a specific span, tied to a concrete change and a recheck. The inference stays modest.

One rejected move: writing "learners learned more." I declined because the reflection is self-report about perception, not a measured learning gain, so I paired the revision with a planned recall check instead of claiming an outcome the data cannot support.

## Decision Rule

Before any reflection counts as evidence, run it through three tests:

1. **Excerpt check:** Is there a span that names a feature and a learner action? If only global praise remains, the reflection yields no codeable data.
2. **Code check:** Does the assigned code have a stated inclusion rule another reader could apply the same way? Replace impressionistic labels with defined codes.
3. **Linkage-and-modesty check:** Does the code connect to one recheckable design decision, and does the claim stop at perceived experience unless an objective measure backs it?

A reflection that fails the excerpt check is not weak evidence; it is no evidence, and treating it as evidence manufactures false confidence.

## Common Misreadings

The first misreading equates positive sentiment with effective design: lots of happy reflections must mean the lesson works. Sentiment and learning routinely diverge, and a lesson can feel smooth while teaching little. The second misreading over-codes, reading competence into a reaction, for example coding "I felt confident" as "mastery achieved." Confidence is a feeling, not a demonstrated skill, and calibrating it requires a performance measure. Disciplined coding keeps the code as close to the learner's actual words and actions as possible and resists upgrading reactions into outcomes.

## Textbook Walkthrough

Apply the discipline to a batch of reflections on a simulation lesson. Most say versions of "it was fun" (set aside as global). One says: "I kept clicking Run before reading the prompt, then had to start over." That span names a feature (the Run control's prominence) and an action (clicking before reading), so it is codeable as "premature-action (control invites action before instruction is read)." The linked design decision is concrete: delay the Run control's activation until the prompt has been displayed, and recheck the premature-click rate. Note what we do *not* claim: that the change "improves learning." We claim it reduces a specific friction the learner described, and we schedule a behavioral recheck. The walkthrough shows the whole arc, from a pile of mostly uncodeable praise to a single coded excerpt that earns a revision.

## What Strong Reading Looks Like

Read each reflection with a highlighter and a discard pile. In the keep pile go only spans that name a feature and an action; everything else, however flattering, goes in the discard pile because it cannot be coded. A strong reader can articulate, for any code they apply, the rule that would tell another coder when the code does and does not fit, and can state the boundary of the inference ("this shows the learner *noticed* redundancy, not that recall improved"). The discipline is treating warmth as noise and codeable behavior as signal.

## Stronger Artifact Standard

The reflection artifact is strong when each cited reflection is reduced to a defined-code excerpt tied to a recheckable decision, and when the README states the inclusion rule for at least one code and the objective check that will test the perception. Global praise may be reported as context but never as evidence for a design change. Polish of the write-up is the last layer; the load-bearing layer is the excerpt-code-decision chain with an honest inference boundary.

## Transfer Case

Move reflection-as-data into a context with many reflections and a need for reliability, such as coding a full cohort's exit notes. The transfer is to make the codebook shareable: each code gets a definition, an inclusion rule, and an example, so a second coder can apply it and you can check agreement. Scaling forces the discipline you practiced on one excerpt to become explicit, because what stayed in your head with five reflections must be written down for fifty. The skill transfers because it was never about volume; it was about converting subjective text into codes another person could reproduce and act on.
