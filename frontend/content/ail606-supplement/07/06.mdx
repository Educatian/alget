# Publication-Ready Artifact Packaging

![Publication-Ready Artifact Packaging textbook visual](/course-art/deep-exemplars/ail606-supplement/07-06-publication-ready-artifact-packaging.png)

## Why This Section Matters

A design artifact that only its author can use is not finished; it is a private draft. Publication-ready packaging is the discipline of preparing an artifact so a competent stranger can identify the canonical version, understand its intent, reuse it legally, and reproduce its use, all without contacting you. This is the reproducibility standard that scholarly and open-source communities have converged on: a clear README, an unambiguous canonical file, recorded provenance for every reused asset, an explicit license, and a changelog. The folder of "FINAL" and "FINAL (1)" files is the anti-pattern this section exists to eliminate.

For a learning designer, packaging is where evidence of your reasoning either survives or evaporates. If the decision log, the asset sources, and the AI-assistance notes are not written down at packaging time, they are usually lost. Treating packaging as a design step, not a clerical afterthought, is what makes your work citable, auditable, and reusable.

## Learning Targets

- Identify the reuse test: could a competent stranger find the canonical artifact and reproduce its use from the package alone?
- Build a package with a README (intent and decision log), a single dated canonical file, per-asset provenance, an explicit license, and a changelog.
- Record asset provenance (source and license) rather than silently reusing images.
- Decide what to include and what to summarize (e.g., disclose AI assistance in the README rather than dumping a full chat log).

## Opening Case

A teammate says the storyboard is "done" and shows you the folder: `storyboard_final_v2_FINAL.pdf`, `storyboard_final_v2_FINAL (1).pdf`, an `images/` directory, and a `notes.txt`. The work may be excellent, but the package fails immediately: a stranger cannot tell which PDF is canonical, the reused images carry no license, and nothing states what the artifact is for or how to use it. "Done" here means the author can still open it; it does not mean anyone else can. This section turns that folder into a package that passes the reuse test.

## Core Concept

Publication-ready packaging is organized around one operational standard, the reuse test, supported by five components:

| Component | What it guarantees | Failure if missing |
| --- | --- | --- |
| README | Intent, decision log, how to view, AI-assist and verification note | Reuser cannot tell what the artifact is for |
| Canonical file (single, dated) | One unambiguous source of truth | "Which FINAL is the real one?" |
| Per-asset provenance | Source and license for every reused image or text | Legal and ethical reuse risk |
| LICENSE | Explicit terms for reuse | Reuser does not know what is permitted |
| CHANGELOG | Version history and what changed | No way to track or cite a specific version |

The components serve the reuse test: a competent stranger should be able to open the README, find the canonical file, confirm they may reuse the assets, and rebuild the work. Packaging also includes a judgment about *what not to include*: the goal is the provenance a reuser needs, not every artifact you produced. A full AI chat transcript, for instance, is noise; the README's statement of which sections the AI drafted and how you verified them is the signal.

The course anchors apply even at the packaging stage. **Mayer's principles** shape the README so it communicates efficiently (a coherent, signposted document, not a wall of text), because a README that overloads the reader defeats its purpose. **Cognitive load theory** argues for structure that lowers the reuser's extraneous effort: a manifest and clear naming reduce the search cost of finding the canonical file. **UDL learner variability** reminds you that "competent stranger" includes reusers with different tools and access needs, so the package should not assume your exact software environment.

## Worked Example

Trace one artifact package from "looks done" to genuinely reusable by an outsider.

**Before (package contents, first pass):**

```
storyboard_final_v2_FINAL.pdf
storyboard_final_v2_FINAL (1).pdf
images/
notes.txt
```

1. Two near-identical "final" files, with no manifest to say which is canonical.
2. Reused images in `images/` with no recorded source or license.
3. No statement of intent and no instructions for viewing or rebuilding.

**After (publication-ready package):**

```
README.md            # intent, decision log, how to view, AI-assist + verification note
storyboard.pdf       # canonical artifact (single, dated)
assets/              # each image with source + license recorded in README
LICENSE              # CC BY 4.0
CHANGELOG.md         # version history
```

The revised package passes the reuse test: the canonical artifact is unambiguous, every reused asset carries provenance, and the README lets a competent stranger rebuild the work.

One rejected inclusion: the full AI chat log. I left it out because a reuser does not need the transcript; instead the README states which sections the AI drafted and how I verified them, which is the provenance that actually supports reuse and accountability.

## Decision Rule

Package the artifact, then run the reuse test as a thought experiment with a stranger:

1. **Canonical check:** Could the stranger identify the single authoritative file without guessing? If two files compete for "final," fix the naming and the manifest.
2. **Provenance check:** Does every reused asset record a source and a license? If an image's origin is unknown, you cannot ship it.
3. **Rebuild check:** Do the README instructions let the stranger view or reproduce the artifact in their own environment, without your help?
4. **Inclusion check:** Does the package contain the provenance a reuser needs and exclude noise (raw logs, dead drafts) that obscures it?

A package that fails any check is not "almost done"; it is a private draft wearing a "final" label.

## Common Misreadings

One misreading equates a polished artifact with a publication-ready one. A beautiful PDF in an unlicensed, unlabeled folder still fails the reuse test, because polish is a property of the artifact and reusability is a property of the package around it. A second misreading treats "include everything" as transparency. Dumping every draft and every chat log does not aid a reuser; it buries the canonical file and the relevant provenance under noise. Good packaging is curation toward reuse, not exhaustive archival.

## Textbook Walkthrough

Apply the standard to a dataset-plus-dashboard artifact. The first pass is a folder with `data.csv`, `dashboard.html`, and `final_charts.xlsx`, no README. Walk the checks. Canonical: name the authoritative dashboard file and date it, and state in the README that `data.csv` is the source for `dashboard.html`. Provenance: record where `data.csv` came from, how it was collected, and any de-identification applied, plus the license under which it may be reused. Rebuild: write the steps to open the dashboard and regenerate the charts, naming the tool versions so a stranger on different software can adapt. Inclusion: drop the stale `final_charts.xlsx` if the dashboard supersedes it, or mark it explicitly as deprecated in the changelog. The result is a package a reviewer could cite by version and a peer could rebuild, which is the whole point.

## What Strong Reading Looks Like

Read your own package as a stranger who has never met you and cannot ask you anything. For each file, ask "would I know what this is and whether I may use it?" and for the folder as a whole, ask "could I find the one real version and rebuild it?" A strong reader notices the gaps that authors are blind to: the unlicensed image, the undated duplicate, the assumed software, the missing decision log. The discipline is to package for the reuser you will never meet, not for the author who already knows everything.

## Transfer Case

Move packaging into a regulated or archival context, such as depositing an artifact in an institutional repository that requires persistent identifiers and long-term access. The reuse test tightens: the canonical file now needs a stable identifier, the license must permit the repository's terms, and the README must remain intelligible years after the software that made the artifact is gone. The same five components carry over, but the "competent stranger" becomes a future reuser with none of your context and possibly none of your tools. Designing the package to survive that gap is the proof that you understand packaging as future-proofing reuse, not as tidying a folder.
