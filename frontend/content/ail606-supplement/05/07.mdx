# Prioritizing Iterations

![Prioritizing Iterations textbook visual](/course-art/deep-exemplars/ail606-supplement/05-07-prioritizing-iterations.png)

## Why This Section Matters

A test usually surfaces more problems than a team can fix before the next build, so the real skill is not finding issues but deciding which ones to fix first. Teams default to fixing what is easy (a typo, a color) because easy work feels like progress, while the issue actually blocking learners sits untouched because it is hard. This section is about ranking revisions by their effect on the learning goal rather than by their cost to fix, using severity (how badly an issue blocks the goal) and reach (how many learners hit it) instead of effort. Prioritization is where formative testing either pays off or is wasted, because the same evidence can drive a build that removes the worst barrier or one that polishes around it.

In AIL 606 the storyboard frame sequence with narration, signaling, and reader-action notes is revised across iterations, and the order of those revisions is itself a defensible decision. A prioritized backlog is an argument: it says these problems, in this order, because of this evidence.

## Learning Targets

- Rank issues by severity and reach against the learning goal, not by ease of fixing.
- Treat accessibility barriers as non-negotiable even when they do not block the median learner.
- Build a triage table that makes the ordering inspectable and arguable.
- Defend an iteration plan by tracing each item's position to its effect on the goal.

## Opening Case

A test of a tutorial storyboard turns up four issues. The team's instinct is to start with the welcome-screen typo and the button color, because both are five-minute fixes, and to "get to the rest later." Later never comes before the deadline, and the next build ships with the same blocking defect it had before: three of five participants could not find the Submit control and abandoned the task.

The plan optimized for motion, not impact. It cleared the trivial and left the barrier that actually stops people from reaching the learning goal. The team will demo a tidier interface and report progress, but the one number that matters (whether learners can complete the task) will not have moved, because the iteration spent its budget on the wrong end of the list.

## Core Concept

Prioritization runs on two axes that effort routinely overrides: severity and reach. Severity asks how much an issue blocks the goal; reach asks how many learners encounter it. Ranking by their combination, rather than by how cheap the fix is, is the entire move.

| Axis | Question | Why it ranks ahead of effort |
| --- | --- | --- |
| Severity | Does it block the learning goal? | A blocking defect wastes the whole session for that learner |
| Reach | How many learners hit it? | A widespread issue compounds across the audience |
| Effort | How hard to fix? | Real, but it sets order only among equally important items |

There is one principled exception to "rank by impact on the median learner," and it is an access barrier. A low-contrast control may not block the typical user, but for a learner with low vision it is a wall, and **UDL learner variability** treats that as non-negotiable: access is not a nice-to-have that competes on severity-times-reach, it is a floor below which the design cannot ship. So an accessibility issue can outrank a cosmetic one even when its raw reach looks modest, because the learners it excludes are excluded completely.

The learning-goal anchor keeps the ranking honest. **Mayer multimedia learning** reminds you that the goal is a learning performance, so an issue is severe to the degree it blocks that performance, not to the degree it annoys someone. And **cognitive load theory** explains why a "small" friction can rank high: a confusing control that adds extraneous load at a decision point can derail the learning task even if it never produces an outright failure, which is why hesitation data, not just abandonment data, feeds the severity judgment.

## Worked Example: Prioritizing Which Issues to Fix First

A test surfaces four issues. The team must decide what to revise before the next build.

**Before (fix by ease, not impact):**

> Plan: Start with the typo on the welcome screen and the button color, because they are quick. We'll get to the rest later.

Walk through a defensible prioritization, step by step:

1. **List each issue with severity and reach.** Severity = how much it blocks the goal; reach = how many participants hit it.

| Issue | Hit by | Blocks task? | Severity |
| --- | --- | --- | --- |
| Cannot find Submit; 3 abandoned | 3 of 5 | Yes | High |
| Quiz feedback misread as error | 2 of 5 | Partly | Medium |
| Button color low contrast | 4 of 5 | No | Low (but accessibility) |
| Welcome-screen typo | 1 of 5 | No | Trivial |

2. **Sort by severity x reach, not by effort.** The Submit issue blocks the core task for most users; it ranks first.
3. **Protect access as a non-negotiable.** Low contrast does not block the task but is a **UDL learner variability** access barrier, so it stays above the typo.
4. **Schedule the cheap-but-trivial last.**

**After (impact-ordered plan):**

> Next iteration, in order: (1) fix Submit findability (high severity, 3 of 5 blocked); (2) relabel quiz feedback (medium); (3) raise button contrast (accessibility); (4) typo, if time allows.

The after version is defensible because effort is spent where it removes the largest barrier to the learning goal, and access is not deprioritized. The before version optimized for what was easy, leaving the task-blocking defect unaddressed, the classic prioritization trap.

## Decision Rule

Order by severity times reach against the learning goal, hold accessibility as a floor, and let effort break ties only among items of equal importance. If the first item on your backlog is the cheapest rather than the most blocking, the list is sorted by comfort, not evidence.

Before locking the iteration plan into your storyboard frame sequence with narration, signaling, and reader-action notes, check three things:

1. **Impact check:** Is each item ranked by its effect on the learning goal, not by how easy it is?
2. **Access check:** Have accessibility barriers been protected as non-negotiable, regardless of raw reach?
3. **Traceability check:** Can you point to the evidence (severity and reach) behind each item's position?

If any check fails, the iteration will spend its budget on motion rather than on the barrier that matters.

## Common Misreadings

The most common error is letting effort masquerade as priority, so the backlog becomes a list of quick wins with the hard, important problem perpetually at the bottom. A second error is treating accessibility as a low-priority polish item because it does not block the median learner, which silently accepts excluding the learners it does block. A third is ranking by how loudly an issue was reported rather than by how much it blocks the goal, which lets one vivid complaint jump the queue ahead of a quiet, widespread barrier.

A backlog sorted by ease is a backlog that protects the team's comfort at the learner's expense.

## Textbook Walkthrough

Trace one backlog from instinct to a defensible order. A storyboard test surfaces a frame whose narration runs long (annoying, two participants mentioned it), a missing caption on a key diagram (blocks deaf learners entirely), and a slightly off-brand color (one stakeholder noticed). The effort instinct fixes the color first; the impact discipline does not. The missing caption is an access floor under **UDL learner variability**, so it leads even though only some learners hit it, because for them it is total exclusion, not mild friction.

The long narration ranks next, not because it was mentioned, but because **cognitive load theory** flags overlong audio as extraneous load competing with the diagram the frame is teaching, so it plausibly blocks the learning action for more than the two who complained. The off-brand color, blocking nothing, drops to last. Read back, the order is an argument anyone can check: caption (access floor), narration (load on the learning goal), color (cosmetic), and each position cites the evidence that earned it rather than the hour it takes to fix.

## What Strong Reading Looks Like

As you read an iteration plan, keep one column for each item's rank and one for the justification, then flag any item whose position is explained by effort rather than by severity, reach, or access. Those are the places the plan has quietly sorted itself by convenience, and they are where the next build will disappoint.

A strong reader of a prioritization can answer four questions:

1. Is each item ranked by its effect on the learning goal?
2. Were accessibility barriers held as a floor rather than traded against severity?
3. What evidence (how many, how blocking) sits behind each position?
4. Where did ease of fixing distort the order?

## Stronger Artifact Standard

The iteration plan is strong when a reviewer can read the ordering, ignore how hard each fix is, and still agree the sequence removes the largest barriers to learning first. Treat the ranking justification as the load-bearing element; an order without cited severity and reach is an assertion, not an argument. Use the annotation tools to flag any item promoted for being cheap, and ask BigAL to compare your ordering against the impact check rather than to estimate development time.

A useful closing line reads: "I moved Submit findability to the top and the typo to the bottom because findability blocked three of five from the learning goal while the typo blocked no one; I rejected the suggestion to do the quick fixes first, since that order would ship the same task-blocking defect again."

## Transfer Case

Move the same prioritization discipline to triaging a course's redesign across a semester, where the issues are not interface defects but failing assignments, confusing readings, and a clunky gradebook. The temptation to fix the gradebook first because it is bounded is the same effort trap; the failing assignment that blocks the learning goal for most students has to lead. The structure transfers (severity times reach against the goal, access as a floor), but the units change from clicks to learning outcomes. A reader who sequences the redesign by what is administratively easiest has repeated the mistake of fixing the typo before the Submit button.
