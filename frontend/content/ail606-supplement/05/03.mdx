## Why This Section Matters

The task you hand a participant decides what your test can possibly learn. Tell someone where to click and you will measure whether they can follow directions, which no real user ever does. Give them a goal and a believable reason to pursue it, and you measure whether the design lets them find their own way, which is the only thing usability evidence is about. This section is about writing task scenarios that put the design at risk instead of protecting it: situations realistic enough that the participant's behavior stands in for a real user's, and open enough that failure can actually happen.

In AIL 606 the moderated usability test script with observation-to-revision trace lives or dies on its tasks. Strong tasks generate the friction, hesitation, and wrong turns that become revision evidence. Weak tasks (leading, artificial, or solved in the prompt) manufacture a smooth session that proves nothing and quietly flatters the prototype.

## Learning Targets

- Write goal-based scenarios that state a desired end-state and a realistic context, never a click path.
- Detect and remove embedded solutions, vocabulary leaks, and other cues that hand the participant the answer.
- Define an observable, promptable-free success condition the moderator can score consistently.
- Calibrate task difficulty so the design can fail without the task being impossible.

## Opening Case

A designer wants to test whether instructors can build a course module from a template in a new authoring tool. The draft task reads: "Click the blue New Module button, choose From Template, name it, and Save." A participant follows it perfectly, and the team concludes the feature is usable.

It concluded nothing. The task named every control and its order, so the participant was transcribing instructions, not finding anything. The one thing the test was supposed to check (can an instructor locate and recognize the template path on their own?) was answered for them in the prompt. The session produced a ceiling effect by construction: success was guaranteed, so the data is empty.

## Core Concept

A usable task scenario has three properties, and most weak tasks violate at least one.

| Property | What it means | Violation |
| --- | --- | --- |
| Goal-based | States an end-state, not the steps | A click path the user just follows |
| Realistic | Gives a believable role, context, and motive | A bare command with no reason behind it |
| Scorable | Has an observable success condition | "See if they like it," which cannot be marked |

The deepest property is goal-based framing. A real user arrives with an intention ("add a module from a template") and must map that intention onto the interface's controls; that mapping is precisely the gulf of execution Norman (2013) describes in *The Design of Everyday Things*: the gap between what a user intends and the actions the interface makes available. The moment your task names the control, you have bridged the gulf for the participant and erased the measurement; a goal-based scenario preserves the bridging work Norman argues a design must support unaided. **[Mayer multimedia learning](https://doi.org/10.1017/CBO9781139164603)** adds a learning-side reason to care about goal framing: a transferable goal is what makes a task meaningful, because clicking a specific button is not a skill anyone needs to keep.

Realism guards against a subtler failure. A context-free command ("create a module") gives the participant no stakes, so they behave like a test-taker, not a worker. A scenario with a role and a deadline ("you launch next week and want to reuse a template") recruits the same motivation a real user feels, which surfaces real shortcuts and real frustration. And every scenario needs a scorable end-state, because **[cognitive load theory](https://en.wikipedia.org/wiki/Cognitive_load)** warns that a moderator who has to interpret "did that count?" in real time adds load to their own observation and lets bias fill the gap. A predefined success condition keeps the scoring clean.

Match each property of a usable task scenario to the specific way a weak task violates it. The match is the diagnostic you will use to read any task list.

## Worked Example: Rewriting a Task Scenario So It Does Not Leak the Answer

A designer is writing the task a participant will attempt in a usability session for a course-authoring prototype.

**Before (leading, instruction-style task):**

> Task: Click the blue "New Module" button in the top-right toolbar, then choose "From Template," then name your module and click Save.

Walk through why this task cannot test the design:

1. **Spot the embedded solution.** The task names the exact buttons and order, so the participant only follows directions; nothing about findability is tested.
2. **Recover the underlying goal.** What does a real author actually want? To create a module from a template, without being told where the control lives.
3. **Write a goal-based scenario with a realistic context.** Give a situation and a desired end-state, not a click path.
4. **Define an observable success condition** the moderator can score without prompting.

**After (goal-based scenario):**

> Scenario: You are an instructor with one week before your course launches. You want to add a new module built from an existing template so you do not start from scratch. Using this prototype, create that module. (Success: a template-based module is created and saved; moderator records the path taken and any wrong turns.)

The after version is defensible because it tests whether the participant can find and complete the goal, which is what usability evidence requires. The before version guaranteed success and produced no evidence, a hidden ceiling effect.

## Decision Rule

State the destination, never the route, and check that a participant who does not know your interface could still fail the task. If your task contains any interface noun the participant could not have known on their own, you have leaked the answer and must rewrite.

Before locking tasks into your moderated usability test script with observation-to-revision trace, run three checks:

1. **Leak check:** Does the task name any control, label, or step the participant would otherwise have to discover?
2. **Realism check:** Does the scenario give a role and a motive a real user would actually have?
3. **Scorability check:** Can the moderator mark success or failure without prompting or interpreting on the fly?

If any check fails, the task will either guarantee success or produce data no two observers would score the same way.

## Common Misreadings

The most common error is mistaking task wording for instructions, so the scenario teaches the participant to use the tool instead of testing whether the tool teaches itself. A subtler leak is vocabulary: if your interface labels a feature "Template Library" and your task says "open the template library," you have handed over the search term that findability was supposed to test. Use the user's words, not the interface's.

A good task should be answerable in many wrong ways before it is answered in the right one.

## Textbook Walkthrough

Trace one task from a leaky draft to a scorable scenario. A team testing a data-dashboard prototype drafts: "Use the Filter dropdown to show only last quarter." The interface word "Filter" is a leak, and "use the dropdown" is a route. Recover the goal: a manager wants to see only last quarter's numbers. The realistic scenario becomes, "Your director just asked how the team did last quarter; using this dashboard, show only that period's results." Notice it never names a control, so the participant must decide whether filtering, a date picker, or a saved view is the path, which is exactly the findability question.

Now set the success condition before the session, not during it: success is the dashboard displaying only last-quarter data, regardless of route. With that condition fixed, **[cognitive load theory](https://en.wikipedia.org/wiki/Cognitive_load)** is respected for the moderator too; they are not improvising judgments mid-session, so their attention stays on behavior. A walkthrough that gets all three (goal, realism, scorable end-state) right turns a session into evidence instead of a guided tour.

## What Strong Reading Looks Like

As you read a task list, keep one column for the goal the task intends and one for every cue that betrays the solution. The betrayal column is the diagnostic: any interface noun, ordinal step, or matching keyword that appears there is a task you must rewrite before the session runs.

A strong reader of a task scenario can answer four questions:

1. What goal does this task test, stated without reference to the interface?
2. Where, if anywhere, does the wording leak the path or the vocabulary?
3. What is the exact, pre-agreed success condition?
4. Could a real user plausibly fail this task, and would that failure be informative?

## Stronger Artifact Standard

The task set is strong when a reviewer who has never seen the prototype can read each scenario and still not know which buttons to press, yet know exactly what counts as success. Treat each scenario's nouns as load-bearing; a single interface term smuggled in collapses the findability test for that task. Use the annotation tools to highlight every leaked cue, and ask BigAL to compare your wording against the leak check rather than to make the scenario sound more polished.

A useful closing line reads: "I rewrote the task from a click path into a goal-based scenario because the original named every control and tested only direction-following; I rejected the suggestion to add a hint after thirty seconds, since the prototype's whole point is whether the path is findable unaided."

## Transfer Case

Move the same task-writing discipline to an assessment-design context, where the scenario is the test item itself. The leak problem reappears as the giveaway stem: a question whose wording reveals its own answer measures reading, not knowledge, just as a leaky task measures compliance, not usability. The structure transfers (state the goal, hide the route, fix the scoring), but the stakes shift, because a leaked item inflates scores instead of inflating a usability claim. A reader who treats the two as unrelated has missed that both fail the same way: the prompt does the work the participant was supposed to do.
