# Comparative Software Audit

![Comparative Software Audit textbook visual](/course-art/deep-exemplars/ail606-supplement/02-07-comparative-software-audit.png)

## Why This Section Matters

Choosing a learning tool is one of the highest-leverage decisions a designer makes, because it sets the affordances and constraints every later design must live inside. Yet the most common way to choose is the least defensible: praise each candidate on whatever it happens to do best ("this one is cheap, that one has the most templates, the other is newest") and pick the one with the nicest-sounding strength. This section teaches the disciplined alternative, a comparative audit that scores every candidate on the same criteria so the comparison is actually a comparison.

The two structural ideas are shared criteria and gates. **Shared criteria** mean every tool is judged on the same dimensions, so a verdict reflects fit to your task rather than which feature each vendor chose to highlight. A **gate** is a non-negotiable requirement (often accessibility, security, or budget) that a tool must satisfy to remain eligible at all; a gate is pass-or-fail, not a weighted score that a strength elsewhere can offset. Confusing a gate with a weight is the error that lets a tool with a fatal flaw win on points.

## Opening Case

A team must pick an authoring tool for a cohort that includes screen-reader users, on a fixed budget. The first draft of the audit reads: "Tool A is cheap, Tool B has the most templates, Tool C is the newest, so let us go with Tool B for its template library." It sounds reasonable and it is indefensible, because no two tools were judged on the same dimension. The recommendation rests on a feature count, and the feature that would actually disqualify Tool B, its lack of screen-reader support, was never even in the comparison.

The case exposes why an unsound comparison can feel complete. Each tool was described accurately; the failure was structural, not factual. Without shared criteria there is no common ground to stand a verdict on, and without a gate the accessibility requirement that should have settled the decision was invisible. The audit must record the criteria and the gate so a reviewer can see that the comparison was fair before trusting its conclusion.

## Core Concept

A defensible comparative audit is built in a fixed order, and the order is what makes it fair. First, define the task precisely, including the learners and the constraints ("let novice designers build a branching scenario with screen-reader support, on a fixed budget"), because the task determines which criteria matter. Second, derive the criteria from the task, not from the tools, so the dimensions exist before any candidate is scored. Third, separate criteria into **weighted dimensions**, where more is better and a strength can offset a weakness, and **gates**, where failure is disqualifying regardless of other scores. Fourth, score every tool on every criterion using the same scale. Fifth, apply the gates before reading the totals, so a tool that fails a gate is removed even if it leads on points.

The decisive concept is the gate-versus-weight distinction. Accessibility for a cohort with screen-reader users is a gate: a tool that cannot serve those learners cannot be chosen, and no number of templates can buy back that failure. Treating accessibility as a mere weight (say, one criterion among five) is the technical mistake that lets a high template score rescue an inaccessible tool. Gates encode requirements that are categorical, not tradeable.

The course anchors decide which criteria deserve gate status:

- **UDL learner variability** is usually what elevates accessibility from a weight to a gate, because a tool that excludes a class of learners has failed the task, not merely scored low.
- **Cognitive load theory** informs the "novice learnability" criterion, since a tool that demands heavy interface learning taxes designers before they reach the design work.
- **Mayer's principles** inform criteria about how the tool lets you build (signaling, contiguity, control), connecting the audit back to what the tool must afford for good multimedia design.

## Worked Example: Building a Comparative Audit Matrix

Here is a before-and-after of an audit comparing three authoring tools for a task defined as "let novice designers build a branching scenario with screen-reader support, on a fixed budget."

**Before (unsound comparison)**

The draft praised each tool on a different axis: "Tool A is cheap, Tool B has the most templates, Tool C is the newest." It then picked Tool B for its template count. No two tools were judged on the same dimension.

**The decision point.** The audit was rebuilt around five shared criteria, scored 0 to 2 for every tool, with accessibility marked as a non-negotiable gate.

| Criterion (gate marked *) | Tool A | Tool B | Tool C |
| --- | --- | --- | --- |
| Branching authoring | 2 | 2 | 1 |
| Screen-reader support * | 2 | 0 | 2 |
| Novice learnability | 2 | 1 | 1 |
| Cost within budget | 2 | 2 | 0 |
| Export to LMS | 1 | 2 | 2 |
| Total | 9 | 7 | 6 |

**After (defensible recommendation)**

Tool B had the most templates but scored 0 on the accessibility gate, which disqualifies it for a cohort that includes screen-reader users. Tool A wins on both total score and the gate.

Audit note (decision level): "I scored all three tools on one shared criteria set rather than praising each on its own strength. Accessibility is a gate, not a weight, so Tool B's template lead cannot rescue a 0 there. The recommendation holds for novice designers on this budget with screen-reader users; if that context changed, Tool B could re-enter."

The audit is defensible because the verdict rests on common criteria, an explicit gate, and a named context, not on a feature count or a per-tool compliment.

## Decision Rule

Derive the criteria from the task before you look at any tool, and apply gates before you read totals. A comparison is only fair if every candidate met the same bar, and only valid if a fatal flaw cannot be outscored.

Before you trust an audit's recommendation, check it against these questions:

1. **Shared criteria:** Was every tool scored on the same dimensions, or was each praised on its own strength?
2. **Task-derived:** Do the criteria come from the task and its learners, or from the tools' marketing?
3. **Gate handling:** Which criteria are gates (pass/fail), and were they applied before totals so no strength could buy back a gate failure?
4. **Named context:** Does the recommendation state the learners, budget, and constraints under which it holds, so a reader knows when it would change?

An audit that passes is a defensible recommendation. One that compares feature counts across mismatched axes is a preference with a table around it.

## Common Misreadings

The first misreading treats the highest total as the winner without checking the gates. In the worked example Tool B scores well on templates but zero on the accessibility gate, so its total is irrelevant; a tool that fails a gate is out before totals are read. A scoring table without enforced gates can recommend a tool that cannot legally or ethically be used.

The second misreading collapses "newest" or "most features" into "best." Recency and feature count are properties of the tool, not measures of fit to your task. A two-year-old tool that affords screen-reader-friendly branching beats a brand-new one that does not, for a cohort that needs branching with screen readers. Always score fit to the named task, and let the criteria, not the vendor's framing, decide what counts.

## Textbook Walkthrough

Read the worked example's matrix as a machine for producing a defensible verdict. Every tool is scored 0 to 2 on the same five criteria, so the columns are comparable; this alone fixes the original draft's fatal flaw. Then notice the asterisk on "screen-reader support," which marks it as a gate. Tool B posts a strong total on templates and export, but its 0 on the gated criterion removes it from contention before the totals matter. The matrix lets you see, at a glance, that template strength cannot rescue an accessibility failure, because the gate is enforced separately from the sum.

Watch how the recommendation is then stated with its boundary conditions. Tool A wins "for novice designers on this budget with screen-reader users," and the audit explicitly notes that "if that context changed, Tool B could re-enter." That clause is not hedging; it is the mark of a rigorous audit, because it tells a future reader exactly which assumption would overturn the verdict. A recommendation without its conditions cannot be reused safely.

## What Strong Reading Looks Like

As you read, look at any "best tools" comparison you can find online and test it for shared criteria and gates. Most fail: they praise each product on a different strength and never declare a non-negotiable requirement. Spotting that failure trains the judgment to build audits that do not commit it, and it makes you a harder person to sell a tool to.

A strong reader of comparative audits can answer four questions about any tool recommendation:

1. Were all candidates scored on the same task-derived criteria?
2. Which requirements are gates, and were they enforced before totals?
3. Under exactly which learners, budget, and constraints does the verdict hold?
4. What single change in context would make a different tool win?

## Stronger Artifact Standard

A strong artifact for this section is an audit matrix with task-derived criteria, at least one explicit gate, identical scoring across all candidates, and a recommendation that names its context. The strongest versions add the re-entry condition: the specific change that would let a currently disqualified tool win, which proves the verdict is reasoned rather than a fixed preference.

When you use BigAL on an audit, ask it to attack your criteria, not to rank the tools. A useful prompt is: "Here is my task and my five criteria, one marked as a gate. Which criterion am I missing for this cohort, and is anything I weighted actually a gate?" Getting the criteria and gates right is where audits succeed or fail, so that is where the tool's scrutiny is most valuable.

## Transfer Case

Take the same three tools and change the task: the cohort no longer includes screen-reader users, but the deliverable must integrate with a strict student-data-privacy regime. The audit's machinery is unchanged, but two things move. The accessibility gate relaxes from a gate to a weight, which is exactly the "re-entry condition" the original audit named, so Tool B's template lead now counts. Meanwhile a new gate appears, data-privacy compliance, and whichever tool fails it is removed regardless of its template count. The same comparison, re-run with a different gate, can crown a different winner. If you can predict that Tool B re-enters when accessibility stops being a gate, but is removed again if it fails the privacy gate, you understand that an audit's verdict is a function of its task and gates, not a fixed ranking of tools.
