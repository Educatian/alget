# Course Readiness Checklist

![Course Readiness Checklist textbook visual](/course-art/deep-exemplars/ail606-supplement/08-08-course-readiness-checklist.png)

## Why This Section Matters

A course readiness checklist answers a deceptively simple question: is this course ready for students. The trap is that most readiness checklists answer a different question, is the course set up, and the two are not the same. "Syllabus posted, modules visible, links work" verifies that the instructor finished their setup. It says nothing about whether a student, walking the actual path through the course, has the scaffolds they need to complete the capstone they will be graded on.

This matters because setup-complete and student-ready fail in opposite ways. A course can pass every setup box and still strand learners: a capstone panel with no prior practice, a link that opens but points to last term's content, a policy that exists but is never connected to the assignment that depends on it. Readiness as a design property is about tracing the student's path, not the instructor's task list, and the checklist is the instrument that forces that shift in viewpoint.

## Opening Case

A coordinator runs the pre-launch checklist the night before a course opens: syllabus posted, modules visible, gradebook configured, links working. All four boxes check; the course looks ready. A deeper pass against what students will actually be asked to do tells a different story. The Module 8 capstone evidence board requires a "limitations" panel, but no earlier activity ever asked students to state a limitation, so the panel has no scaffold. Two module links open fine but point to last term's dropbox. The AI-use policy sits in the syllabus but is never referenced in the assignment that requires disclosure, so students will not connect them.

The case exposes the gap between a course that is set up and a course a student can complete. Every surface box was true; every path-level scaffold was missing. As you read, practice the reframe the checklist demands: stop asking "did I finish setting up" and start asking "can a student finish the work with the supports they were given."

## Core Concept

A genuine course readiness checklist audits path completability: whether a student traversing the course in order arrives at each graded task with the scaffolds that task requires. This reframes readiness from a setup inventory to a quality-assurance audit, the same shift quality-assurance frameworks make when they distinguish "the artifact exists" from "the artifact functions for its user."

Two design ideas make the audit substantive:

- **Trace each capstone demand back to a building activity.** The capstone evidence board has three panels (evidence, limitations, transfer claims). Scaffolding theory says a complex performance should be built from distributed sub-skills, not introduced whole at the end. So each panel needs a prior activity that practiced it. A limitations panel with no earlier limitation-naming activity front-loads a new demand at the worst moment, when the learner is already integrating everything else.
- **Verify links and policies at point of use, not point of existence.** A link that opens is not a link that points to the right place; a policy in the syllabus is inert if the assignment that depends on it never references it. Readiness checks function in context, not mere presence.

The unifying principle is that readiness is judged from the student's path, not the instructor's setup. "Links work" is a setup fact; "a student can complete the capstone with the scaffolds they were given" is a readiness fact, and only the second predicts whether the course will succeed.

| Surface (setup) check | What it misses | Path (readiness) check |
| --- | --- | --- |
| Links work | Link points to stale content | Link resolves to this term's resource |
| Capstone assignment posted | No prior practice for a panel | Each panel traces to a building activity |
| AI policy in syllabus | Never referenced at point of use | Assignment links to the policy it depends on |

## Worked Example

Walk through one concrete readiness review of a course before it opens, using a checklist tied to the capstone defense evidence board students will build.

**Before (the it-looks-done checklist).** The original checklist had four boxes: "Syllabus posted, Modules visible, Gradebook set up, Links work." All four were checked, so the course looked ready. A deeper readiness pass against actual student tasks found three gaps the surface checklist could not catch. (a) The capstone evidence board was due in Module 8 but no earlier activity ever asked students to state a limitation, so the "limitations" panel had no scaffold. (b) Two module links opened but pointed to last term's dropbox. (c) The AI-use policy was in the syllabus but not referenced anywhere in the assignment that required disclosure, so students would not connect them.

1. **Check readiness against the student's path, not the instructor's setup.** "Links work" is a setup fact; "a student can complete the capstone with the scaffolds they were given" is a readiness fact. The surface checklist verified the former and missed the latter.
2. **Trace each capstone panel back to a building activity.** The evidence board has three panels (evidence, limitations, transfer). Each panel needs a prior activity that practiced it. The limitations panel had none, so a Module 6 reflection prompt is added that asks for one named limitation. By **cognitive load theory**, distributing the sub-skills across the term keeps the capstone from front-loading three new demands at once.
3. **Close the link and policy gaps.** The two stale links are repointed to the current term, and the assignment text now links directly to the AI-use clause it depends on.

**After (the checklist as a readiness audit).** The checklist now verifies path-level readiness: 3 of 3 capstone panels traced to a building activity (was 2 of 3), 0 stale links (was 2), and the AI policy referenced at point of use. The change is auditable: a reviewer can compare the four-box surface list to the panel-to-activity trace and see which readiness gap each addition closed.

## Decision Rule

Check readiness by walking the student's path, not the instructor's setup list. Every checklist item should test whether a learner can do something, not whether the instructor has posted something. A box that verifies presence rather than function is a setup box wearing a readiness label.

Run each readiness item through three questions:

1. **Path check:** Does this item test something a student does, or only something the instructor finished? "Modules visible" is setup; "a student reaching Module 8 has practiced each capstone panel" is readiness.
2. **Scaffold-trace check:** For every graded demand, is there an earlier activity that built the sub-skill it requires? If a capstone panel has no prior practice, the course is set up but not ready.
3. **Point-of-use check:** Does each link resolve to the current resource, and is each governing policy referenced where it actually applies? Existence is not function.

A checklist that passes setup questions but fails these is the one that lets a course look ready and strand students anyway.

## Common Misreadings

The most common misread is that a fully checked setup list means the course is ready. Setup completeness is necessary but not sufficient; a course can be flawlessly assembled and still strand learners, because assembly verifies the instructor's task, not the student's path. A green checklist proves the building exists, not that anyone can get through it.

A second misread is that the capstone is a single deliverable to be assigned, not a set of sub-skills to be built. Treating it as one big task posted in Module 8 ignores that its panels (evidence, limitations, transfer) each require practice. A readiness audit that does not trace those sub-skills backward will declare the course ready while the hardest panel has no scaffold anywhere before it.

## Textbook Walkthrough

Convert a surface checklist into a readiness audit. Begin by replacing the question. The old list asks "is the course set up?" and answers yes. Ask instead "can a student complete the capstone with the supports they were given?" and the gaps appear.

Trace each capstone panel backward. The evidence panel has a Module 4 activity behind it; good. The transfer panel has a Module 7 activity; good. The limitations panel has nothing, so a Module 6 reflection that requires naming one limitation is added, distributing that sub-skill so the capstone does not introduce three new demands at once.

Then audit links and policies at point of use. The two module links open but resolve to last term's dropbox, so they are repointed to the current term. The AI-use policy exists but the disclosure assignment never references it, so the assignment text now links directly to the clause it depends on. The walkthrough is complete when the audit reports path-level facts (three of three panels traced to a building activity, zero stale links, policy referenced where used) rather than setup facts, which is the difference between a course that looks ready and one that is.

## What Strong Reading Looks Like

A strong reader of this section reads every checklist item and asks whether it tests the student's path or the instructor's setup. That single distinction separates a readiness audit from a setup inventory, and it is the habit that catches stranded capstones before students hit them.

Read any readiness checklist against these four questions:

1. Which items verify that a student can do something, and which only verify that the instructor posted something?
2. For each graded demand, is there an earlier activity that built the sub-skill, or does the capstone introduce it cold?
3. Does each link and policy function at its point of use, or merely exist somewhere in the course?
4. If you walked the course as a student, where is the first place you would be stuck with no scaffold?

## Stronger Artifact Standard

A strong readiness artifact reports path-level results: the count of capstone panels traced to a building activity (before and after), the number of stale links found and fixed, and the policies now referenced at point of use. A reviewer should be able to see that the audit moved a course from setup-complete to student-ready and to name the specific gap each addition closed.

A strong rationale sounds like this: "I added a Module 6 limitation-naming activity because the capstone's limitations panel had no prior scaffold, which would have front-loaded a new sub-skill at the worst moment. I rejected the suggestion to count the syllabus AI policy as satisfying the disclosure requirement, because a policy that exists but is never referenced at point of use does not function for the student."

## Transfer Case

Move the readiness checklist from a single course to a program-wide audit of twenty courses before a term. The path-completability principle holds, but a new constraint dominates: you cannot personally walk twenty student paths in the time available. The faithful transfer is to convert the per-course path-trace into a sampled, criterion-based audit, perhaps tracing capstone scaffolds and point-of-use links in a stratified sample and flagging patterns for course owners, rather than checking every box in every course. Reusing the single-course, walk-every-path method at program scale would be either impossibly slow or, more likely, quietly degraded back into a surface setup checklist, recreating exactly the failure the audit was meant to prevent.
