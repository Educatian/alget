# README and Repository Disclosure

![README and Repository Disclosure textbook visual](/course-art/deep-exemplars/ail606-supplement/04-07-readme-and-repository-disclosure.png)

## Why This Section Matters

"AI was used in this project" is a sentence that satisfies no one. It names no tool, no location, and no human edit, so a reviewer cannot check it, and an instructor cannot tell whether the work demonstrates the author's judgment or the model's defaults. A disclosure earns trust only when it is auditable: tied to the artifact, specific about who did what, and verifiable against the evidence (the commit history) that the repository already keeps. AIL 606 treats the README as the place where two obligations meet, honest disclosure of AI use and a traceability matrix linking each principle to each screen change, both of them checkable by anyone who clones the repo.

This section teaches you to write disclosures and traceability that a reviewer can verify against the commit log rather than take on faith. You should leave able to convert a vague integrity claim into evidence, and able to colocate the disclosure with the artifact so the claim and the proof live in the same place.

## Learning Targets

- Write AI-use disclosures that name the tool, the location, and the author's follow-up edit.
- Tie each disclosure claim to verifiable evidence (a commit) in the repository.
- Build a theory-to-screen traceability matrix that a reviewer can audit.
- Colocate disclosure and artifact so integrity is evidenced, not merely asserted.

## Opening Case

A reviewer clones two AIL 606 prototypes. The first README says "AI was used in this project. The design follows good learning principles." There is nothing to check: no tool named, no screen tied to a principle, no link to the history. The second README lists "Codex generated the flashcard component (commit a3f9c1); I rewrote the scoring to normalize case (commit b7d2e4)," followed by a table mapping each screen to its controlling principle. The reviewer opens the diff for commit b7d2e4 and confirms the scoring change with their own eyes. One README asserts integrity; the other lets the reviewer verify it.

The case shows the gap between claiming and evidencing. The first author may be perfectly honest, but honesty that cannot be checked carries no weight in a review.

## Core Concept

Disclosure is the documented, auditable account of how AI tools contributed to an artifact and what the human author did with the output. Three properties make a disclosure auditable. Specificity: it names the tool, the exact location (which component, which figure), and the author's follow-up edit, so a reader knows what was generated versus authored. Linkage: each claim points to a commit, so the assertion can be checked against the diff the version-control system already records. Colocation: the disclosure lives with the artifact in the repository, not in a separate document, so the claim and its evidence cannot drift apart.

Traceability in the README serves the parallel function for design: a matrix mapping each screen change to the controlling principle that justified it. This is the public, auditable form of the principle-to-feature work, written so a cloner can read down the table and then open the corresponding screen to check the mapping. Together, disclosure and traceability turn the repository into a self-verifying record: the README states the claims, the commit history and the screens supply the proof.

| Vague claim | Auditable disclosure |
| --- | --- |
| "AI was used" | "Codex generated the flashcard component (commit a3f9c1)" |
| "I edited it" | "I rewrote the scoring to normalize case (commit b7d2e4) after testing Paris and paris" |
| "Good learning principles" | A table mapping each screen to its controlling principle |

The reason version control is central is that a commit is tamper-evident evidence with an author and a timestamp. Pointing a disclosure at a commit converts an honor-system statement into something a reviewer can independently confirm, which is the entire difference between claiming integrity and evidencing it.

An auditable disclosure is written from the commit history backward, in a definite order. Arrange the steps so specificity, linkage, and colocation all fall out of the process.

## Worked Example

Work through one annotated before/after revision of a README's AI-use disclosure and traceability section.

**Before (README excerpt):**

```markdown
## About
This is my AIL 606 prototype. AI was used in this project.
The design follows good learning principles.
```

**Annotations a reviewer would leave:**

1. "AI was used" names no tool, no location, and no author edit, so it cannot be verified or audited.
2. "Good learning principles" asserts quality without tracing any principle to any screen change.
3. The disclosure lives only in prose with no link to the commit history, so a cloner cannot check it.

**After (revised README excerpt):**

```markdown
## AI Use Disclosure
- Codex generated the flashcard component (commit a3f9c1). I rewrote the
  scoring to normalize case (commit b7d2e4) after testing "Paris" and "paris".
- ChatGPT drafted alt text for Figures 1 to 3; I revised each to match the
  diagram content (commit c1a8f0).

## Theory-to-Screen Traceability
| Screen | Principle | Change |
| --- | --- | --- |
| Practice 1 | Signaling | Highlight synced to the prompt term |
| Quiz | Feedback timing | Per-item feedback for formative items |
```

**Why the after version is stronger:** every AI claim names the tool, the commit, and the author's follow-up edit, so a reviewer cloning the repo can check each one against the diff. The traceability table ties each screen change to a specific principle. The disclosure and the artifact now live together and are auditable, which is the difference between claiming integrity and evidencing it.

## Decision Rule

Write every disclosure so a stranger with the repo could verify it. For each claim:

1. **Specificity check:** Does it name the tool, the location, and the author's edit?
2. **Linkage check:** Does it point to a commit a reviewer can open and confirm?
3. **Colocation check:** Does the disclosure live with the artifact, and does the traceability table map each screen to its principle?

If a claim cannot be checked against the commit history, it is an assertion, not a disclosure.

## Common Misreadings

The first error is the catch-all sentence ("AI was used"), which feels like disclosure but discloses nothing checkable. The second is asserting quality ("follows good principles") without a traceability table that ties principles to actual screens. The third is keeping the disclosure in a separate file from the artifact, so the claim and the evidence can drift apart and neither can be trusted.

Disclosure is verifiable evidence colocated with the work, not a polite acknowledgment that a tool was somewhere involved.

## Textbook Walkthrough

Write the disclosure from the commit history backward. Open the log, find each commit where AI output entered or was revised, and write a line that names the tool, the location, and what you changed, ending with the commit hash. Sourcing the disclosure from the actual history guarantees specificity and linkage at once.

Then build the traceability table as the public face of your principle-to-feature work. Each row maps a screen to the one principle that controls its key change, written so a reader can open that screen and check the claim. The table is the bridge between your internal design reasoning and an external reviewer's ability to audit it.

Finally, colocate everything in the README and confirm the links resolve. A disclosure that points to a commit that does not exist, or a table that names a screen that is not in the repo, is worse than none, because it claims verifiability it cannot deliver. Clone your own repo fresh and check every link as a reviewer would.

## What Strong Reading Looks Like

As you read, keep a two-column note: **claim** on the left, **evidence** on the right. The claim is a disclosure or traceability statement; the evidence is the commit or screen a reviewer would open to confirm it. By the end of AIL 606 04.07, your notes should let a stranger audit the repository without asking you anything.

A strong reader of a README disclosure can answer four questions:

1. Which tool did what, where, and what did the author change afterward?
2. Which commit would a reviewer open to verify each claim?
3. Does the traceability table map each screen to a checkable principle?
4. Do the disclosure and the artifact live together so the evidence cannot drift?

## Stronger Artifact Standard

The artifact is strong when every AI claim is specific, linked to a commit, and colocated with the work, and when the traceability table lets a reviewer audit each principle-to-screen mapping. Treat a catch-all sentence as a non-disclosure. Where a claim lacks a commit link, mark it with the annotation tools and ask BigAL to compare a vague disclosure with an auditable one rather than for a generic statement about academic integrity.

A useful final paragraph for the artifact would sound like this: "I rewrote the disclosure to name each tool, location, and my follow-up edit with its commit hash, and added a screen-to-principle table. I rejected the suggestion to summarize all AI use in one sentence, because a reviewer could not verify a single specific claim from it."

## Transfer Case

Move the same disclosure obligation from a course prototype to a published open-source educational tool with outside contributors. The properties hold, but the stakes and audience grow: disclosure now serves not just an instructor but every downstream user and contributor, the traceability table becomes part of the project's documentation, and the commit linkage must survive across many authors. Transfer means scaling the same auditable structure to a multi-author repository, not abandoning it because the project got bigger. If you understand disclosure as evidence, a larger audience raises the bar for verifiability rather than lowering it.
