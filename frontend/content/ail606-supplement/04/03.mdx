# Wireframes That Show Learning Logic

![Wireframes That Show Learning Logic textbook visual](/course-art/deep-exemplars/ail606-supplement/04-03-wireframes-that-show-learning-logic.png)

## Why This Section Matters

A wireframe is usually treated as a layout document: boxes for where the text, image, and buttons go. In instructional design, that framing is a trap, because a layout can be perfectly arranged and still teach nothing or teach the wrong thing. A wireframe that shows learning logic annotates each region with the learner action it supports and its place in the instructional sequence, so a reviewer critiques the teaching decision rather than the aesthetics. AIL 606 asks for wireframes that expose intent: this region assesses recall, this control logs a help request, this feedback is delayed to keep performance unaided.

This section teaches you to annotate a wireframe so its instructional logic is visible before any visual design exists. You should leave able to tell when a layout decision quietly contradicts the screen's pedagogical purpose, as when a hint button undermines a screen meant to observe unaided performance.

## Learning Targets

- Annotate each wireframe region with the learner action it supports and its sequence position.
- Detect contradictions between a screen's purpose and its interaction affordances.
- Encode instructional intent through layout choices (button placement, feedback timing).
- Critique a wireframe as a teaching decision, not as a visual arrangement.

## Opening Case

A designer presents a clean wireframe for a mastery-check screen: four answer options, a Hint button beside every item, and feedback after submission. It looks tidy. But the purpose of a mastery check is to observe what the learner can do unaided, and a hint button next to every item invites prompting that contaminates exactly the evidence the screen exists to collect. The layout is fine; the learning logic is self-contradictory. No amount of visual polish fixes a screen whose affordances fight its purpose.

The case shows that the most dangerous wireframe is the one that looks done. Tidiness hides the contradiction; only annotating each region with its instructional job surfaces it.

## Core Concept

A wireframe shows learning logic when every region carries two labels: the learner action it supports and where that action sits in the instructional sequence (acquire, practice with support, perform unaided, receive feedback). Layout is not neutral; placement and effort encode pedagogy. A help control placed prominently beside each item lowers the cost of seeking help, which is right for guided practice and wrong for a final check. The same control, moved to a single effortful button at the bottom that logs the request, raises the cost of help and preserves an unaided measure.

The governing idea is the alignment of affordance with intent. An affordance is what an interface invites the learner to do; intent is what the screen is pedagogically for. When the two align, the screen collects the evidence it promises. When they conflict, the screen produces misleading data: a "mastery" score inflated by hints, or a "practice" screen so bare that struggling learners get no support. Feedback timing is the other lever: immediate per-item feedback supports formative practice, while end-of-set feedback protects summative measurement by keeping each response independent.

- **Acquire:** present and signal; affordances should reduce search and load.
- **Practice with support:** make help cheap and visible; immediate feedback.
- **Perform unaided:** make help costly and logged; delay feedback to the end.
- **Reflect or feedback:** make the learner's own reasoning visible before revealing the answer.

The reason this matters for evidence is that a wireframe is the earliest point at which a teaching mistake is cheap to fix. Catching a hint-on-a-final-check contradiction in the wireframe costs a sentence; catching it after the prototype is built costs a rebuild.

Before you can label a region with its phase, you have to hold the instructional sequence in order. Arrange the four phases from first encounter to evidence of mastery.

## Worked Example

Work through one annotated before/after revision of a practice-screen wireframe, the kind you would walk a reviewer through.

**Before (wireframe of a mastery-check screen):**

```
+------------------------------------------+
|  [Question text]                         |
|  ( ) Option A   ( ) Option B             |
|  ( ) Option C   ( ) Option D             |
|  [ Hint ] beside each item               |
|  [ Submit ]   feedback after all items   |
+------------------------------------------+
```

**Annotations a reviewer would leave:**

1. No region is labeled with the learner action it supports, so this reads as a layout, not learning logic.
2. A per-item Hint button on a mastery check invites prompting, which contradicts the screen's purpose of observing unaided performance.
3. Feedback batched to the end fits a final check, but the per-item hints fight that intent.

**After (revised wireframe with logic annotations):**

```
+------------------------------------------+
|  [Question text]   <- assess recall of   |
|                       Concept 4.2        |
|  ( ) A  ( ) B  ( ) C  ( ) D              |
|  [ Need help? ] one button, bottom,      |
|     logs a hint request before scoring   |
|  [ Submit ]  -> end-of-set feedback,     |
|     so performance stays unaided         |
+------------------------------------------+
```

**Why the after version is stronger:** each region now names the learner action and its place in the sequence (recall assessment, then optional help, then end-of-set feedback). Moving hints to one effortful bottom button encodes the assessment intent rather than decorating the screen. The reviewer can now critique the teaching decision, not just the look. The change is a clearer learning argument, not a prettier screen.

## Decision Rule

Annotate intent before you arrange boxes, then check that affordances serve it. Run three tests on every wireframe:

1. **Action-label check:** Does each region state the learner action it supports?
2. **Sequence check:** Is each region tagged with its phase (acquire, practice, perform, feedback)?
3. **Affordance-intent check:** Does every control's prominence and feedback timing match the screen's purpose, or does any of them contradict it?

If a control invites behavior the screen's purpose forbids, the wireframe is misaligned regardless of how clean it looks.

## Common Misreadings

The usual error is reviewing a wireframe for aesthetics (spacing, alignment, balance) and declaring it done, while the instructional logic was never stated and so was never checked. A second error is assuming that adding helpful affordances (hints, tips, examples) is always good; on an unaided check, help is contamination, not kindness.

A wireframe is an argument about teaching, so review it for whether its affordances collect the evidence the screen promises.

## Textbook Walkthrough

Begin by writing the screen's purpose in one sentence before drawing anything: "this screen measures unaided recall of Concept 4.2." That sentence is the standard every later decision answers to. Skipping it is how contradictions sneak in.

Now label each region with a learner action and a phase tag. The act of labeling forces the contradiction to the surface; a Hint button next to a region labeled "perform unaided" is obviously wrong once both labels exist side by side. This is why annotation, not arrangement, is the real work of an instructional wireframe.

Finally, tune the affordances to the purpose. Decide button prominence by the cost of the behavior you want: cheap and visible for help you encourage, costly and logged for help you want to discourage and measure. Set feedback timing by whether the screen is formative (immediate) or summative (delayed). When every affordance traces back to the one-sentence purpose, the wireframe shows learning logic.

## What Strong Reading Looks Like

As you read, keep a two-column note: **claim** on the left, **evidence** on the right. The claim is the learner action you think a region supports; the evidence is the annotation and affordance choice that make the action observable. By the end of AIL 606 04.03, your notes should let a reviewer judge whether each affordance serves the screen's stated purpose.

A strong reader of an instructional wireframe can answer four questions:

1. What is this screen's one-sentence pedagogical purpose?
2. Which affordance, if any, contradicts that purpose?
3. Why is the feedback timing right for this phase?
4. How would the layout change if the screen moved from practice to a final check?

## Stronger Artifact Standard

The artifact is strong when a reviewer can read each region's learner action, its sequence phase, and a clear reason every affordance matches the screen's purpose. Treat visual styling as the last layer. Where an affordance and an intent conflict, mark it with the annotation tools and ask BigAL to compare a practice-screen wireframe with a final-check wireframe rather than for generic layout tips.

A useful final paragraph for the artifact would sound like this: "I moved the per-item hints to one logged bottom button and delayed feedback to the end, because the screen measures unaided recall. I rejected the suggestion to add an example beside each item, since it would have contaminated the measure this screen exists to collect."

## Transfer Case

Move the same wireframe from a summative mastery check to a first-attempt guided-practice screen on the same concept. Now the contradiction reverses: the costly, logged help button is wrong, because guided practice wants help to be cheap and immediate, and end-of-set feedback should become per-item. Transfer means re-deriving the affordances from the new phase, not reusing the layout. If you understand learning logic, changing the phase visibly changes where the help lives and when feedback fires.
