# AI-Assisted Authoring With Codex

![AI-Assisted Authoring With Codex textbook visual](/course-art/deep-exemplars/ail606-supplement/04-06-ai-assisted-authoring-with-codex.png)

## Why This Section Matters

A code-generating assistant like Codex will happily build whatever you ask for, which is exactly the danger: if you ask it to "make a good flashcard app," it makes the instructional decisions for you, and they will be generic decisions optimized for plausibility, not for your learners. The skill in AI-assisted authoring is not prompting; it is keeping the instructional decisions and delegating only the implementation. AIL 606 frames this as a division of labor: the designer owns what the interaction should be and why, and Codex owns turning that specification into working code, with every accepted and rejected suggestion documented.

This section teaches you to specify the pedagogy precisely enough that the AI implements your design rather than substituting its own. You should leave able to rewrite a vague "make me an app" prompt into an instructional specification, and able to recognize when generated code encodes a teaching mistake (rewarding wrong answers, fusing content with logic) that you must reject.

## Learning Targets

- Specify the instructional interaction precisely enough that the tool implements your design, not its defaults.
- Keep design decisions (sequence, feedback, separation of content) with the human author.
- Audit generated code for encoded pedagogy errors, not just for whether it runs.
- Document each accepted and rejected suggestion with the instructional reason.

## Opening Case

A student prompts Codex with "Make me a good flashcard app for my module." The tool returns working code: all card data crammed into one global string with answers inline, and a confetti animation that fires on every click, including wrong answers. The code runs and looks done. But the prompt delegated the design ("a good app"), so the tool supplied its own defaults: a data structure no non-coder teammate can edit, answers exposed in the markup, and a reward that celebrates errors. Each of these is a teaching decision the student never consciously made.

The case shows that the most consequential moment in AI-assisted authoring is the prompt. A prompt that hands over the instructional decision gets generic pedagogy back; a prompt that specifies the interaction gets implementation back.

## Core Concept

The governing principle is the division of cognitive labor: the human author holds the instructional decisions, and the generative tool holds the implementation. An instructional decision answers a teaching question, such as when feedback appears, whether the answer is hidden until the learner commits, how content is separated from logic so non-coders can edit it, and which behaviors are rewarded. An implementation detail answers a construction question, such as which loop or data structure realizes that decision. When you let the tool make instructional decisions, you inherit its defaults, which are tuned for a generic average and often violate basic pedagogy (rewarding any click, exposing answers).

A precise specification is the instrument that enforces the division. Compare "make a good flashcard app" with "read cards from a separate JSON array, flip on click, reveal the answer only after a flip, show brief feedback, and play no celebratory animation on incorrect responses." The second prompt has already made every instructional decision; Codex is left only with implementation. The separation of content from logic deserves special note, because it is both an architecture choice and a pedagogy choice: when content lives in a separate file, a non-coding subject expert can revise the cards, and answers are not leaked into the markup.

| Owned by the human author (decisions) | Owned by the tool (implementation) |
| --- | --- |
| When feedback appears, and for which responses | The function that renders the feedback |
| Whether the answer is hidden until a flip | The state variable tracking flip status |
| That content lives separate from logic | The import statement and file format |
| Which behaviors earn a reward | The animation library call |

The reason auditing matters as much as prompting is that even a good prompt can produce code that quietly encodes a mistake. "Runs without errors" is a construction test; "rewards only correct answers, hides answers until commit, keeps content editable" is the pedagogy test, and only the human can run it.

## Worked Example

Work through one annotated before/after revision of a Codex-assisted authoring decision for a flashcard widget.

**Before (prompt and what Codex returned):**

Prompt: "Make me a good flashcard app for my module."

```js
let cards = "Q1:A1;Q2:A2;Q3:A3"; // all data in one global string, answers inline in markup
function showConfetti() { /* fires on every click, even wrong answers */ }
```

**Annotations a reviewer would leave:**

1. The prompt handed the design decision ("a good flashcard app") to Codex instead of specifying the interaction.
2. Content and logic are fused in one global string, so a non-coder on the team cannot edit cards and the answers are exposed in the markup.
3. Confetti fires on every click, including wrong answers, which rewards errors and adds extraneous load.

**After (revised prompt and accepted code):**

Prompt: "Generate a flashcard component that reads cards from a separate JSON array, flips on click, reveals the answer only after a flip, and shows brief feedback; no celebratory animation on incorrect responses. I will write the card content."

```js
import cards from "./cards.json"; // content separated from logic, editable by non-coders
// feedback text comes from the card object; positive animation gated to correct answers only
```

**Why the after version is stronger:** the designer kept the instructional decisions (separation of content and logic, answer hidden until flip, animation only on correct) and used Codex to implement them. Each accepted or rejected suggestion is documented with its reason, so a reviewer can audit why the confetti-on-every-click behavior was dropped. The change is a defensible authoring decision, not just code that runs.

## Decision Rule

Decide the pedagogy before you prompt, then audit the output as pedagogy. For each AI-assisted authoring step:

1. **Specification check:** Does the prompt state every instructional decision (feedback timing, answer reveal, content separation, reward conditions) so only implementation is left to the tool?
2. **Encoded-pedagogy check:** Does the generated code encode any teaching mistake (rewarding errors, exposing answers, fusing content with logic)?
3. **Documentation check:** Is each accepted and rejected suggestion recorded with its instructional reason?

If the prompt left an instructional decision open, the tool made it for you, and you now own a decision you never examined.

## Common Misreadings

The first error is treating prompting as the skill, when the real skill is deciding the pedagogy before prompting. The second is accepting code because it runs; running is necessary but says nothing about whether the interaction teaches. The third is treating AI assistance as authorship that needs no disclosure, when in fact every generated piece needs an audit and a record of what you kept and changed.

The author's job is to own the instructional decisions and verify the implementation, not to outsource judgment to whatever the tool returns.

## Textbook Walkthrough

Write the specification before opening the tool. List every instructional decision the component embodies: feedback timing, answer reveal, content-logic separation, reward conditions. This list is your prompt and also your audit checklist, which is why writing it first does double duty.

Then prompt with the specification, not the goal. "Implement this interaction" gets you implementation; "make something good" gets you the tool's defaults. The more decisions your prompt fixes, the less room the tool has to substitute its own pedagogy.

Finally, audit against the same list and record the result. Run the pedagogy test (does it reward only correct answers, hide answers until commit, keep content editable), not just the build. For each suggestion the tool offered, note whether you accepted or rejected it and why, because that record is what makes your authoring auditable and feeds directly into the disclosure artifact.

## What Strong Reading Looks Like

As you read, keep a two-column note: **claim** on the left, **evidence** on the right. The claim is the instructional decision you intended; the evidence is the line of the prompt that specified it and the line of generated code that implemented it. By the end of AIL 606 04.06, your notes should let a reviewer see which decisions stayed with you and which were delegated.

A strong reader of AI-assisted authoring can answer four questions:

1. Which instructional decisions did the prompt fix, and which did it leave open?
2. Does the generated code encode any pedagogy the author did not intend?
3. Which suggestion was rejected, and for what instructional reason?
4. How would the specification change for a different learner or interaction?

## Stronger Artifact Standard

The artifact is strong when the prompt fixes every instructional decision, the generated code passes the pedagogy audit, and each accepted or rejected suggestion is recorded with its reason. Treat "it runs" as the floor, not the standard. Where you are unsure whether the tool made a decision you should have made, mark it with the annotation tools and ask BigAL to compare a goal-level prompt with a specification-level prompt rather than for general prompting tips.

A useful final paragraph for the artifact would sound like this: "I specified the flip-then-reveal interaction, separate content file, and reward-only-on-correct rule, and used Codex to implement them. I rejected its confetti-on-every-click default, because rewarding wrong answers contradicts the formative purpose of the deck."

## Transfer Case

Move the same workflow from a flashcard widget to an auto-graded short-answer question. The implementation Codex can supply changes, but the division of labor does not: you still own the instructional decisions, and they get harder. Now you must specify how strict the matching is (case, whitespace, synonyms), what counts as partial credit, and what feedback a near-miss receives, because a generative tool will default to brittle exact-match grading that fails "Paris" against "paris." Transfer means writing a richer specification for a higher-stakes interaction, not reusing the flashcard prompt. If you understand the division of labor, a higher-stakes interaction visibly demands more decisions from you, not from the tool.
