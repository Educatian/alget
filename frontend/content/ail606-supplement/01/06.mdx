# Choosing a Software Case

![Choosing a Software Case textbook visual](/course-art/deep-exemplars/ail606-supplement/01-06-choosing-a-software-case.png)

## Why This Section Matters

Tool selection is where good instructional design most often goes wrong, because the failure is seductive. A vendor demos a platform full of impressive features, and the design starts from the tool ("what can this do?") instead of the goal ("what must the learner be able to do?"). This is technology determinism, and it produces expensive solutions in search of a problem. This section teaches the inverse discipline: an objective-to-affordance mapping that selects the *least* capable tool that still affords the required learner action, then checks it against the cohort's real constraints. The software case you write is the document that proves the choice was reasoned, not sold to you.

## Learning Targets

- Map a learning objective to the specific affordance it requires before naming any tool.
- Select the least costly tool that affords the required action and survives the constraints.
- Document a bounded AI/software support move with accepted and rejected suggestions.
- Use annotations, support requests, and revision notes to decide what help or design change should come next.

## Opening Case

A selection memo opens with a feature list: "We will use Tool X (a VR platform) because it has avatars, spatial audio, hand tracking, eye tracking, and a scene editor. It is the most advanced option available." Nowhere does it say what the learner must be able to do. The memo has led with capability and never named the objective, so there is no way to tell whether any of those features earns its cost. The decision is not "is Tool X advanced?" It is "what affordance does the objective demand, and what is the cheapest tool that provides it within our constraints?"

## Core Concept

An **affordance** is what a tool lets a learner *do*, not what features it lists. The selection discipline is to derive the required affordance from the objective, then match tools to affordances, then filter by constraints, in that order.

1. **Objective to affordance.** Translate the verb in the objective into the interaction it requires. "Practice giving corrective feedback and read the reaction" requires conditional branching with visible reaction states. That is an affordance, not a product.
2. **Affordance to candidates.** List every tool that provides the affordance, including the humble ones. Many affordances are met by far cheaper tools than the flashy default.
3. **Candidates to constraints.** Filter by the cohort's reality: access (do learners have the hardware?), cost (is there a license budget?), time (does the build fit the window?), support, and accessibility.

Two ideas keep this honest. The **least-capable-sufficient** heuristic says pick the simplest tool that affords the action, because unused capability is cost and complexity with no learning return. And the **constraint filter** is non-negotiable: a tool that fails an access or time constraint is disqualified no matter how well it affords the action.

## Worked Example

A thin claim sells features:

> Tool X is the most advanced option, so we will use it.

A reasoned case maps objective to affordance to constraint:

> The objective needs branching dialogue where a choice changes the simulated employee's response, so the required affordance is conditional branching with visible reaction states. A browser-based branching-scenario tool provides that at far lower cost than the VR platform and meets our no-headset, two-week, free-license constraints. The VR platform's eye tracking serves no stated objective here.

The improvement is that every retained capability now maps to an objective, and the choice is justified against the cohort's real constraints.

### Annotated Before/After: A Tool-Selection Rationale

Here is a software-case selection memo for a module that teaches new managers to give corrective feedback, revised from feature-chasing to goal-first.

**Before.** Memo: "We will use Tool X (a VR headset platform) because it has avatars, spatial audio, hand tracking, eye tracking, and a scene editor. It is the most advanced option available."

The diagnosis: the memo leads with a feature list and never states the learning goal. It is a tool in search of a problem, and the heavy setup is unjustified.

**After (goal-first mapping).** Learning goal: managers practice delivering a corrective-feedback conversation and reading the other person's reaction in real time.

1. Objective to affordance: the goal needs branching dialogue where a choice changes the simulated employee's response. The required affordance is conditional branching with visible reaction states.
2. Candidate fit: Tool X provides branching, but so does a browser-based branching-scenario authoring tool (Tool Y) at far lower cost.
3. Constraint check: cohort of 30 part-time learners, no headsets, 2-week build window, free license required. Tool Y meets all constraints; Tool X fails the access and time constraints.

Decision: select Tool Y. The eye tracking and spatial audio of Tool X are real features but serve no stated objective here.

**Rejected suggestion.** A vendor demo urged adding Tool X "for immersion." Rejected: immersion is not the construct; reading and responding to a reaction is, and Tool Y supports that within the constraints.

The improvement is that every retained capability now maps to an objective, and the choice is justified against the cohort's real constraints.

Select in the order objective, affordance, constraint, never feature-first:

1. **State the objective and derive the affordance.** No tool is named until the required learner action is written as an affordance.
2. **Pick the least capable sufficient tool.** Among tools that afford the action, choose the simplest; extra capability is unjustified cost.
3. **Apply the constraint filter as a veto.** Access, cost, time, support, and accessibility can disqualify any tool regardless of its affordances.

If a feature in your chosen tool maps to no objective, it is decoration you are paying to maintain.

## Common Misreadings

The first misreading is equating "advanced" with "appropriate"; the most capable tool is rarely the best fit and often fails a constraint. The second is letting a tool optimize the surface of a deliverable while the underlying objective-to-affordance mapping is never written, so no one can say why the tool was chosen. The third is treating "immersion" or "engagement" as objectives; they are not constructs, and they cannot justify an affordance on their own.

## Textbook Walkthrough

Reverse-engineer the bad memo. Strip away the feature list and ask what the manager must actually be able to do: deliver corrective feedback and read a reaction that changes based on their choice. That sentence yields exactly one required affordance, conditional branching with visible reaction states. Now list every tool that affords it; both the VR platform and a browser scenario tool qualify, so the affordance does not select VR. Apply the constraints, 30 part-time learners, no headsets, two weeks, free license, and VR is vetoed on access and time while the browser tool survives. Notice that eye tracking never entered the reasoning, because no objective demanded it. The walkthrough exposes feature-chasing as reasoning run backward: it starts from the tool and never reaches the objective, so it cannot tell which features are paid-for decoration.

## What Strong Reading Looks Like

Read every tool claim by asking which objective it serves and which constraint might veto it. A strong reader can take a feature list and sort it into affordances the objective requires versus capabilities that serve no goal here. Keep a two-column note: feature on the left, the objective it serves (or "none") on the right.

A strong reader of choosing a software case can answer four questions:

1. What is the required affordance, stated independently of any product?
2. What is the least capable tool that provides it?
3. Which constraint, if any, vetoes the flashy default?
4. Which features in the chosen tool map to no objective?

## Stronger Artifact Standard

The case is strong when it derives the affordance from the objective, names the least sufficient tool, and shows the constraint filter doing real work (vetoing at least one candidate). "Tool X is advanced" is weak; "objective needs conditional branching; browser tool affords it; VR vetoed on access and time" is strong. If the memo lists features with no objective mapping, mark the gap and ask BigAL to map each feature to an objective rather than to summarize the tool.

A useful final entry would read: "I selected the browser scenario tool because it affords conditional branching within our no-headset, two-week constraints. I rejected the VR platform because its extra affordances map to no objective and it fails the access constraint."

## Transfer Case

Now imagine the objective shifts to "perform a hands-on equipment calibration with correct spatial positioning," and the cohort works at a site that already owns headsets. The required affordance changes to spatial, embodied manipulation, which a browser scenario tool cannot provide, and the constraint that vetoed VR (no hardware) no longer holds. The same objective-affordance-constraint procedure now selects the VR platform, and that is the correct answer, because the objective and constraints changed, not because VR is "better." A designer who reasoned from affordances can flip the choice with confidence; one who picked by feature count cannot explain why VR was wrong before and right now.
